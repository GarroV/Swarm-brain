## 1. Модель данных

Две сущности, не смешиваем:

**`meetings`** — операционный источник истины о встрече. Сюда POST-ит любой агент (сегодня desktop-agent, завтра — что угодно). Слой универсальности.
- `id uuid pk` — серверный id встречи
- `identity_key text`, `identity_kind text` — ключ реальной встречи (`calendar_event_id`+дата экземпляра / id комнаты / `manual:<uuid>` для Telegram-кнопки) и его тип. **`UNIQUE(identity_key)`** где ключ не manual
- `source text` — `desktop-agent` | будущие источники
- `entry_id uuid` FK → `entries` (черновик/запись тезисов, 1:1)
- `transcript jsonb` — сегменты с таймстампами (канонический, от claim-нувшего агента)
- `started_at, ended_at, duration`
- `attendees jsonb` — из календаря, если есть
- `recorders jsonb` — кто реально записал (множество личностей из claim/заливки, с временами) — см. §6
- `claim_owner` — кто транскрибировал
- `status text` — `awaiting_review` | `in_base` (см. §5)
- `agent_version`

**`entries`** (как есть, структуру не ломаем) — тезисы как `content`. Автоматически получают весь существующий даунстрим: эмбеддинги, семантический поиск, изоляцию по `group_id`, приватность `is_private/owner_id`, видимость в боте/MCP, экстракцию задач. Проверка доступа — по entry (через `entries-guard`), к `meetings` ходим только через авторизованный entry → отдельную защиту не дублируем.

`notes_edited_at` — реальная колонка (по ней фильтр защиты от перезаписи), не jsonb. **Черновик тезисов живёт в `meetings.draft_notes_md`; строка `entries` создаётся ТОЛЬКО при публикации (аппрув)** — до этого черновик не попадает в базу знаний/поиск. Точная схема — в миграции `supabase/migrations/20260612000000_meetings.sql` (она авторитетна над списком выше).

**Личные пометки участников — в существующем личном хранилище, без новых таблиц.** Пометки участника = приватная `entries` (`is_private=true`, `owner_id`=он), привязанная к встрече через `metadata.meeting_id`; сырые ts-строки — в `metadata`, плоский текст — в `content` (эмбеддится). У одной встречи: **1 общая entry тезисов** (публикуемая) + **N приватных entry-пометок** (по одной на записавшего). Переиспользуем личное хранилище и поиск «своё + общее» — пометки находятся семантикой в личном сами собой и заведомо не видны другим.

**Транскрипт** (60–100К символов) живёт в `meetings`, не в `entries` → не раздувает строки базы знаний в списках/поиске. В поиске/списках транскрипт сам по себе не нужен; читается только на странице встречи.

**Задачи:** `tasks.meeting_id` привязываем к `meetings.id` единообразно (сейчас там двойная семантика — почистить).

## 2. Скоуп захвата

Только онлайн-звонки:
- **Google Meet, Контур.Толк** — браузерные, id комнаты берётся из URL активной вкладки (надёжнее, чем заголовок окна Zoom).
- **Telegram-звонок** — **кнопка резкого старта** (общий режим «записать что угодно»; сюда же редкие офлайн-записи одним человеком).
- **Zoom — редко, Teams — почти никогда.**

Переговорки/многопользовательский диктофон — **не проектируем**. Запись одним человеком (включая офлайн через кнопку) дедупа не требует в принципе.

Триггер записи: авто-детект звонка (в anarlog есть `plugins/detect` по использованию микрофона) + ручная кнопка.

## 3. Идентичность и дедуп

**Бери лучшую доступную идентичность** (приоритет):
1. `calendar_event_id` + дата экземпляра — запланированные (основная масса синков). Чистый, из EventKit, одинаковый у всех, с моделью повторов.
2. **id комнаты** (Meet-код / Контур-room из URL) — ad-hoc звонок без календаря.
3. `manual:<uuid>` — Telegram/кнопка. Своя встреча, без авто-дедупа.

Почему не «всегда `conference_id`»: его часто нет (Telegram 1:1, офлайн), ненадёжно извлекается, и он не уникален на встречу (Zoom PMI и повторяющиеся ссылки переиспользуют id → ложная склейка). Календарный ключ строго лучше, когда встреча запланирована.

**Авто-схлоп — только по точным ключам** (1, 2). Никакого content-similarity. Для Telegram/кнопки и кросс-источника (granola) — **ручное «объединить»** в вебе как страховка (warn-at-add, §5).

## 4. Сквозной поток

```
1. Записывают ВСЕ участники (дёшево, координации не нужно, N резервных копий)
2. Запись кончилась → агент перед Whisper делает CLAIM на сервер:
   { identity_key, identity_kind, started_at, метаданные }  (личность — из токена)
3. Сервер:
   - ключа ещё нет → создаёт meetings(status=awaiting_review), отдаёт claim=GRANTED
   - ключ уже есть (claim держит другой) → claim=DEFER, агент Whisper НЕ запускает
   - claim берётся по lease с TTL: claimer упал/не доставил → перехватывает следующий
4. GRANTED-агент: Whisper локально → заливает transcript на сервер
5. Сервер: генерит тезисы ОДИН раз (GPT) → создаёт entry-черновик (в поиск НЕ попадает)
   → meetings.entry_id, status=awaiting_review
   → уведомление записавшим: «командная встреча готова к вычитке»
6. Любой из записавших открывает общий черновик → вычитывает/правит →
   АППРУВ + выбор базы (воркспейс команды / личное хранилище)
7. Сохранил → status=in_base, entry публикуется в выбранную базу (confirmed=true) →
   ушло из «на вычитке» У ВСЕХ разом (объект один) → экстракция задач
8. OFFLINE на шаге 2 / нет ключа / granola → агент транскрибирует сам, заливает,
   при добавлении срабатывает «эта встреча уже в базе — сравни, нужен ли твой экземпляр»
```

Ключевые свойства:
- **Одна транскрибация на встречу** (одна CPU-нагрузка, один GPT-вызов), результат — всем. Claim это и обеспечивает.
- **Все записывают** (не «только один») → если claimer сорвался, встреча не потеряна.
- Claim — единственное «поумнение» агента: только координация, **ноль LLM-логики на клиенте**.

## 5. Черновик, вычитка, «не висит у всех»

- **Один общий черновик = один объект с одним статусом.** Не N персональных «подтверди». Лежит одной командной карточкой в «на вычитке».
- Виден **участникам** (записавшим) до публикации, но **не в поиске**. Сохранили → уезжает в выбранную базу и становится искомым.
- **First-come:** кто успел — взял, поправил, сохранил. Пока кто-то вычитывает — у остальных мягкая пометка «X разбирает» (без жёсткого лока; одновременная правка маловероятна; last-write-wins).
- Сохранён → статус перещёлкнулся → **из «на вычитке» ушло у всех разом** (объект один). Дальше любой участник правит запись уже в базе (обычная правка, не «висящее подтверждение»).
- **Защита от перезаписи агентом:** `notes_edited_at != null` → повторная заливка транскрипта не трогает тезисы.
- Ложится на существующий флаг `confirmed`: `awaiting_review` = `confirmed:false` (не в поиске), `in_base` = `confirmed:true`. Отличие от текущего: вычитывает **владелец/участник**, не только админ.

**Пометки во время звонка (`user_notes`) — личные, в личном хранилище** (приватная entry с `metadata.meeting_id`, см. §1). На странице встречи участнику собираем: общие тезисы + его приватные пометки; чужие пометки не отдаются никогда, даже соучастнику той же встречи.

**Усиление тезисов пометками (enhance, фича Granola) — по типу встречи:**
- **Групповая** (общий черновик на всех) → тезисы **только из транскрипта**. Ничьи личные пометки в общий черновик не бьются.
- **Одиночная** (Telegram/кнопка/1:1, свой черновик) → тезисы **усиливаются пометками владельца** — его встреча, его пометки, его черновик, утекать некуда.

## 6. Аутентификация и трекинг записавших — **ЗАЛОЧЕНО: персональный токен**

- Агент аутентифицируется **персональным токеном** (механизм уже в проекте: `smcp_`-токены, `/mytoken`, `/revoketoken`, SHA-256-хэш в `allowed_users`, верификация в swarm-mcp; миграция `20260611000000_mcp_token_lifecycle.sql`).
- Личность (telegram_id, group_id) выводится **из токена**, `owner_telegram_id` из payload игнорируется → нет спуфинга.
- **Трекинг записавших даётся даром:** каждый claim/заливка несёт личность → сервер копит `meetings.recorders` = кто реально записал K. Уведомления шлём им. Это невозможно с анонимным общим секретом — ещё довод за токен.
- **Бонус:** `recorders` = внутренние участники встречи без календаря (ценно для ad-hoc).
- **group_id** резолвится из токена владельца (через `allowed_users`), а не хардкодом `'cee'`, как в read-ai-webhook.

**Один подвопрос к решению:** TTL токена 90 дней заставит агентов молча отваливаться. Варианты: (а) отдельный долгоживущий **agent-токен** (отдельная колонка/тип), (б) явная обработка 401 на агенте (красный значок + нотификация «обнови токен»). Рекомендация — **(а)** долгоживущий agent-токен, хранить в **Keychain** (не в config.json).

## 7. Пересмотренный контракт API

Личность везде — из `Authorization: Bearer <personal-agent-token>`.

### 7.1 `POST /meeting-claim` (новый, до транскрибации)

```jsonc
// request
{
  "identity_kind": "calendar | room | manual",
  "identity_key": "<iCalUID>:<2026-06-12> | meet:abc-defg-hij | manual:<uuid>",
  "started_at": "2026-06-12T14:00:00+03:00",
  "ended_at":   "2026-06-12T14:47:12+03:00",
  "title": "Синк по Болгарии",          // опц. (нет у manual/ad-hoc)
  "attendees": [{ "name": "...", "email": "..." }],  // опц.
  "user_notes": [{ "ts": 312.5, "text": "дедлайн!!" }],  // личные пометки ЭТОГО участника
  "agent_version": "0.1.0"
}
// response
{
  "meeting_id": "<server-uuid>",
  "decision": "transcribe | defer",      // transcribe → грузи транскрипт; defer → стой
  "lease_ttl_sec": 1800                   // на сколько выдан claim (для перехвата)
}
```

Claim — точка регистрации **каждого** участника: сервер заносит его в `meetings.recorders` и сохраняет его `user_notes` как **его приватную entry** (`metadata.meeting_id`). Так личные пометки доезжают и от `defer`-участников, которые транскрипт не льют. `transcribe`-участник дополнительно вызывает `/meeting-ingest`.

### 7.2 `POST /meeting-ingest` (заливка АУДИО — только claimer)

Облачная схема: рекордер шлёт аудиофайл, сервер сам транскрибирует через OpenAI Whisper.

```
POST /meeting-ingest
Authorization: Bearer <personal-agent-token>
Content-Type: multipart/form-data
  meeting_id = <server-uuid>             (из claim)
  audio      = <системный звук, m4a/mp3/…, ≤25 МБ>  (собеседники; обязателен)
  audio_mic  = <микрофон, m4a, ≤25 МБ>              (голос владельца записи; опционален)
```
Две дорожки одной сессии: сервер транскрибирует обе, сводит сегменты по таймстампам (общий старт → порядок реплик) с метками «собеседник»/«я». Если `audio_mic` нет — только системный звук.
```jsonc
// response (202)
{
  "ok": true,
  "meeting_id": "...",
  "web_url": "https://<webapp>/?meeting=<server-uuid>",
  "summary_status": "processing | skipped_human_edit"
}
```
Сервер в фоне (`EdgeRuntime.waitUntil`): OpenAI Whisper (`verbose_json` → сегменты с таймстампами) → `meetings.transcript` → GPT-4o тезисы → `draft_notes_md` → уведомление записавшим. `entry_id` появляется только при публикации (аппрув, §5), не здесь. Лимит OpenAI 25 МБ — длинные встречи резать/жать (TODO). `user_notes` уходят с `claim` (§7.1), не здесь.

### 7.3 Ошибки

| Код | Когда | Агент |
|---|---|---|
| 401 | токен невалиден/протух | красный значок + «обнови токен», не ретраить |
| 403 | claim держит другой (на ingest) | стоп, не ретраить |
| 409 | гонка claim | перечитать claim |
| 429/5xx | сбой | retry с бэкоффом; очередь переживает рестарт |

`defer`-агенты транскрипт не льют; их `user_notes` (если решим хранить) уходят в их личное, не в общий черновик (§5).

## 8. Лимиты и таймауты

- Edge Functions: wall-clock 150s (free)/400s (paid), CPU 2s, 256MB. `EdgeRuntime.waitUntil` доступен, делит wall-clock.
- Синхронная генерация на часовой встрече близко к пределу + в связке с retry даёт дубли → **сразу закладываем 202/`summary_status:processing`** + фоновую генерацию, а не «начнём синхронно».
- Эмбеддинги: один вектор на entry. В MVP эмбеддим **тезисы** (не весь транскрипт чанками — этого «везде в проекте» нет, потребовало бы отдельной таблицы+RPC+правки трёх клиентов). Чанкование транскрипта — после MVP, если поиск по дословным репликам понадобится.
- Видимость нового `source=desktop-agent`: добавить в фильтры в **трёх местах** (swarm-api `GET /meetings`, MCP `get_meetings`, бот `rai_saved`) — иначе встречи невидимы.
