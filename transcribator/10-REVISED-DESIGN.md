## 1. Модель данных

Две сущности, не смешиваем:

**`meetings`** — операционный источник истины о встрече. Сюда POST-ит любой агент (сегодня desktop-agent, завтра — что угодно). Слой универсальности.
- `id uuid pk` — серверный id встречи
- `identity_key text`, `identity_kind text` — ключ реальной встречи (`calendar_event_id`+дата экземпляра / id комнаты / `manual:<uuid>` для Telegram-кнопки) и его тип. **`UNIQUE(identity_key)`** где ключ не manual
- `source text` — `desktop-agent` | будущие источники
- `entry_id uuid` FK → `entries` (запись тезисов, появляется при публикации)
- `transcript jsonb` — `{language, model, segments}` с таймстампами (от claim-нувшего агента, после облачной транскрибации)
- `draft_notes_md text` — черновик тезисов до публикации
- `started_at, ended_at`
- `attendees jsonb` — из календаря, если есть
- `recorders jsonb` — кто реально записал (`[{telegram_id, claimed_at, role}]`) — см. §6
- `claim_owner` — кто получил право транскрибации; `lease_expires_at` — TTL права
- `status text` — `awaiting_review` | `in_base` (см. §5)
- `agent_version`

**`entries`** (как есть, структуру не ломаем) — тезисы как `content`. Автоматически получают весь существующий даунстрим: эмбеддинги, семантический поиск, изоляцию по `group_id`, приватность `is_private/owner_id`, видимость в боте/MCP, экстракцию задач. Проверка доступа — по entry (через `entries-guard`), к `meetings` ходим только через авторизованный entry → отдельную защиту не дублируем.

`notes_edited_at` — реальная колонка (по ней фильтр защиты от перезаписи), не jsonb. **Черновик тезисов живёт в `meetings.draft_notes_md`; строка `entries` создаётся ТОЛЬКО при публикации (аппрув)** — до этого черновик не попадает в базу знаний/поиск. Точная схема — в миграции `supabase/migrations/20260612000000_meetings.sql` (она авторитетна над списком выше).

**Личные пометки участников — в существующем личном хранилище, без новых таблиц.** Пометки участника = приватная `entries` (`is_private=true`, `owner_id`=он), привязанная к встрече через `metadata.meeting_id`; сырые ts-строки — в `metadata`, плоский текст — в `content` (эмбеддится). У одной встречи: **1 общая entry тезисов** (публикуемая) + **N приватных entry-пометок** (по одной на записавшего). Переиспользуем личное хранилище и поиск «своё + общее» — пометки находятся семантикой в личном сами собой и заведомо не видны другим.

**Транскрипт** (60–100К символов) живёт в `meetings`, не в `entries` → не раздувает строки базы знаний в списках/поиске. В поиске/списках транскрипт сам по себе не нужен; читается только на странице встречи.

**Задачи:** `tasks.meeting_id` привязываем к `meetings.id` единообразно (сейчас там двойная семантика — почистить).

## 2. Скоуп захвата

Только онлайн-звонки:
- **Google Meet, Контур.Толк** — браузерные, id комнаты берётся из URL активной вкладки (надёжнее, чем заголовок окна Zoom).
- **Telegram-звонок** — **кнопка резкого старта** (общий режим «записать что угодно»; сюда же редкие офлайн-записи одним человеком).
- **Zoom — редко, Teams — почти никогда.**

Переговорки/многопользовательский диктофон — **не проектируем**. Запись одним человеком (включая офлайн через кнопку) дедупа не требует в принципе.

Триггер записи: ручная кнопка старта; авто-детект звонка (по использованию микрофона/появлению известного домена во вкладке) — фича нашего рекордера, не критична для MVP.

## 3. Идентичность и дедуп

**Бери лучшую доступную идентичность** (приоритет):
1. `calendar_event_id` + дата экземпляра — запланированные (основная масса синков). Чистый, из календаря, одинаковый у всех, с моделью повторов.
2. **id комнаты** (Meet-код / Контур-room из URL) — ad-hoc звонок без календаря.
3. `manual:<uuid>` — Telegram/кнопка. Своя встреча, без авто-дедупа.

Почему не «всегда `conference_id`»: его часто нет (Telegram 1:1, офлайн), ненадёжно извлекается, и он не уникален на встречу (Zoom PMI и повторяющиеся ссылки переиспользуют id → ложная склейка). Календарный ключ строго лучше, когда встреча запланирована.

**Авто-схлоп — только по точным ключам** (1, 2). Никакого content-similarity. Для Telegram/кнопки и кросс-источника (granola) — **ручное «объединить»** в вебе как страховка (warn-at-add, §5).

## 4. Сквозной поток

```
1. Записывают ВСЕ участники (дёшево, координации не нужно, N резервных копий)
2. Запись кончилась → агент перед загрузкой делает CLAIM на сервер:
   { identity_key, identity_kind, started_at, метаданные }  (личность — из токена)
3. Сервер:
   - ключа ещё нет → создаёт meetings(status=awaiting_review), отдаёт decision=transcribe
   - ключ уже есть (право держит другой) → decision=defer, агент аудио НЕ грузит
   - право берётся по lease с TTL: claimer упал/не доставил → перехватывает следующий
4. transcribe-агент: заливает АУДИО (системный звук + опц. микрофон) в meeting-ingest
5. Сервер (в фоне): транскрибирует аудио в облаке (OpenAI whisper-1) → meetings.transcript
   → тезисы ОДИН раз (GPT-4o) → meetings.draft_notes_md (в поиск НЕ попадает)
   → уведомление записавшим: «командная встреча готова к вычитке» (кнопка Открыть)
6. Любой из записавших открывает общий черновик → вычитывает/правит →
   АППРУВ + выбор базы (воркспейс команды / личное хранилище)
7. Сохранил → status=in_base, entry публикуется в выбранную базу (получает эмбеддинг) →
   ушло из «на вычитке» У ВСЕХ разом (объект один) → экстракция задач
8. OFFLINE на шаге 2 / нет ключа / granola → агент пишет/грузит сам,
   при добавлении срабатывает «эта встреча уже в базе — сравни, нужен ли твой экземпляр»
```

Ключевые свойства:
- **Одна транскрибация на встречу** (один облачный вызов, один GPT-вызов), результат — всем. Claim это и обеспечивает.
- **Все записывают** (не «только один») → если claimer сорвался, встреча не потеряна.
- Claim — единственное «поумнение» агента: только координация, **ноль LLM-логики на клиенте**. Агент шлёт аудио, всю транскрибацию и тезисы делает сервер.

## 5. Черновик, вычитка, «не висит у всех»

- **Один общий черновик = один объект с одним статусом.** Не N персональных «подтверди». Лежит одной командной карточкой в «на вычитке».
- Виден **участникам** (записавшим) до публикации, но **не в поиске**. Сохранили → уезжает в выбранную базу и становится искомым.
- **First-come:** кто успел — взял, поправил, сохранил. Пока кто-то вычитывает — у остальных мягкая пометка «X разбирает» (без жёсткого лока; одновременная правка маловероятна; last-write-wins).
- Сохранён → статус перещёлкнулся → **из «на вычитке» ушло у всех разом** (объект один). Дальше любой участник правит запись уже в базе (обычная правка, не «висящее подтверждение»).
- **Защита от перезаписи агентом:** `notes_edited_at != null` → повторная заливка аудио не трогает тезисы (сервер отдаёт `skipped_human_edit`).
- `awaiting_review` = черновик в `meetings`, не в поиске; `in_base` = опубликовано, `entry` в базе знаний. Отличие от текущего: вычитывает **владелец/участник**, не только админ.

**Пометки во время звонка (`user_notes`) — личные, в личном хранилище** (приватная entry с `metadata.meeting_id`, см. §1). На странице встречи участнику собираем: общие тезисы + его приватные пометки; чужие пометки не отдаются никогда, даже соучастнику той же встречи.

**Усиление тезисов пометками (enhance, фича Granola) — по типу встречи:**
- **Групповая** (общий черновик на всех) → тезисы **только из транскрипта**. Ничьи личные пометки в общий черновик не бьются.
- **Одиночная** (Telegram/кнопка/1:1, свой черновик) → тезисы **усиливаются пометками владельца** — его встреча, его пометки, его черновик, утекать некуда.

## 6. Аутентификация и трекинг записавших — **ЗАЛОЧЕНО: персональный токен**

- Агент аутентифицируется **персональным токеном** (механизм уже в проекте: `smcp_`-токены, `/mytoken`, `/revoketoken`, SHA-256-хэш в `allowed_users`, верификация в `_shared/agent-auth.ts::verifyAgentToken`).
- Личность (`telegram_id`, `group_id`) выводится **из токена**, `owner_telegram_id` из payload игнорируется → нет спуфинга личности и воркспейса.
- **Трекинг записавших даётся даром:** каждый claim несёт личность → сервер копит `meetings.recorders` = кто реально записал. Уведомления шлём им. Это невозможно с анонимным общим секретом — ещё довод за токен.
- **Бонус:** `recorders` = внутренние участники встречи без календаря (ценно для ad-hoc).
- **group_id** резолвится из токена владельца (через `allowed_users`), а не хардкодом, как в read-ai-webhook.

**Один подвопрос к решению:** TTL токена 90 дней заставит агентов молча отваливаться. Варианты: (а) отдельный долгоживущий **agent-токен** (отдельная колонка/тип), (б) явная обработка 401 на агенте (красный значок + подсказка «обнови токен через `/mytoken`»). См. §9.

## 7. Пересмотренный контракт API (кратко)

> Авторитетная версия контракта (точные поля, коды, примеры) — **`02-API-CONTRACT.md`** (сверен по коду). Здесь — только суть решений.

Личность агента везде — из `Authorization: Bearer <персональный smcp_-токен>`; веб (`/agent-meetings*`) — веб-сессия роя (`verifyInitData` / JWT httpOnly cookie).

- **`POST /meeting-claim`** (до загрузки) — тело `{identity_kind, identity_key, started_at?, ended_at?, title?, attendees?, user_notes?, agent_version?}`; регистрирует записавшего в `recorders`, сохраняет `user_notes` как приватную entry, выдаёт lease с TTL. Ответ `{meeting_id, decision: transcribe|defer, lease_ttl_sec}`.
- **`POST /meeting-ingest`** (только держатель `transcribe`) — `multipart/form-data`: `meeting_id` + `audio` (системный звук, ≤25 МБ, обязателен) + `audio_mic` (микрофон, ≤25 МБ, опционален). Ответ `202` сразу; в фоне (`EdgeRuntime.waitUntil`): облачная транскрибация обеих дорожек → сведение по таймстампам → `meetings.transcript` → GPT-4o тезисы → `draft_notes_md` → уведомление записавшим. `notes_edited_at != null` → пропуск. Не держатель → `403`. Лимит OpenAI 25 МБ → длинные встречи резать/жать (TODO рекордера).
- **`swarm-api` `/agent-meetings*`** — `GET` очередь/опубликованные, `GET /:id` черновик+транскрипт, `PATCH /:id` правка `draft_notes_md` (ставит `notes_edited_at`), `POST /:id/publish` (`{base: workspace|personal}`) → создаёт `entries` с эмбеддингом, привязывает `entry_id`, `status=in_base`, идемпотентно → авто-извлечение задач (`createMeetingTasks`).

Коды ошибок (агент): `401` токен невалиден/протух — подсказать `/mytoken`, не ретраить; `403` право у другого — стоп; `409` гонка claim — ретрай 1 раз; `413` файл >25 МБ — нарезка/сжатие; `429/5xx` — retry с бэкоффом. Полная таблица — в `02-API-CONTRACT.md`.

## 8. Лимиты и таймауты

- Edge Functions: wall-clock 150s (free)/400s (paid), CPU 2s, 256MB. `EdgeRuntime.waitUntil` доступен, делит wall-clock.
- Синхронная транскрибация+тезисы на часовой встрече близко к пределу + в связке с retry даёт дубли → **сразу закладываем 202/`summary_status:processing`** + фоновую обработку, а не «начнём синхронно».
- Эмбеддинги: один вектор на entry. В MVP эмбеддим **тезисы** (не весь транскрипт чанками — этого «везде в проекте» нет, потребовало бы отдельной таблицы+RPC+правки трёх клиентов). Чанкование транскрипта — после MVP, если поиск по дословным репликам понадобится.
- Видимость нового `source=desktop-agent`: добавлена в фильтры в **трёх местах** (swarm-api `GET /meetings`, MCP `get_meetings`, бот `rai_saved`) — иначе встречи невидимы.

Распространение бинаря между машинами — **открытый вопрос** (формат раздачи .app, доверие к ad-hoc подписи). Минимальная macOS 13, bundle id `io.dodobrands.swarmrecorder`. Детали рекордера — `recorder/README.md`.
7. **Согласие на запись** внешних участников (GDPR/юрисдикции) — политика + не писать внешних.
