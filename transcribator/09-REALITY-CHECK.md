## A. Модель данных и бэкенд (правки к 02/03)

### A1. [CRITICAL → ✅ реализовано] Таблицы `meetings` не существовало
**Тогда:** встречи были строками `entries` с `metadata={meeting_id, title, duration, confirmed, entry_date}` (Read.ai/Granola). Полей под транскрипт/черновик/lease не было; §1 спеки 03 (ALTER TABLE meetings) был неприменим.
**Разворот:** заведена отдельная таблица `meetings` (миграция `20260612000000_meetings.sql` — авторитетна по схеме) как операционная запись встречи: `transcript jsonb {language,model,segments}`, `draft_notes_md`, `claim_owner`, `lease_expires_at`, `recorders jsonb`, `entry_id`, `group_id`, `status`. `entries` остаётся искомым артефактом и **создаётся только при публикации** — до этого черновик живёт в `meetings.draft_notes_md` и в поиск не попадает. Двойного смысла `tasks.meeting_id` в новом флоу нет: задачи извлекаются `createMeetingTasks` из опубликованного черновика с привязкой к `meeting_id` встречи.

### A2. [CRITICAL → ✅ реализовано] Идемпотентность построена на claim/lease
**Тогда:** ни upsert по meeting_id, ни `notes_edited_at`-защиты, ни уникального индекса — в связке с retry-агента каждый таймаут давал дубль.
**Разворот:** дедуп решён на этапе **claim**, а не на ingest. `POST /meeting-claim` регистрирует записавшего в `recorders` и выдаёт `decision: transcribe|defer`; уникальный индекс `meetings_identity_key_uq` (`identity_kind <> 'manual'`) гарантирует один экземпляр на ключ. Транскрибирует только claimer (`decision=transcribe`); остальные получают `defer` и аудио не грузят. `lease_expires_at` (TTL) позволяет перехватить claim, если claimer сорвался. Человеческая правка защищена: `meeting-ingest` пропускает встречу, если `notes_edited_at != null`.

### A3. [HIGH → ✅ реализовано] Воркспейс: `group_id` берётся из токена, не из payload
**Тогда:** `read-ai-webhook` хардкодил `group_id:'cee'`; в контракте 02 `owner_telegram_id` лежал в «опциональном» блоке.
**Разворот:** личность и `group_id` извлекаются **из персонального токена** записавшего (`_shared/agent-auth.ts` → `verifyAgentToken` → `{telegramId, groupId}`), а не из тела запроса — спуфинг исключён. Колонка `meetings.group_id` резолвится из токена владельца; в payload `meeting-claim`/`meeting-ingest` group_id не передаётся.

### A4. [HIGH → ✅ реализовано] Приватность: `is_private` через выбор базы при публикации
**Тогда:** в контракте не было `is_private`; агент по спеке сохранял всё подряд без подтверждения → риск утечки 1:1 и перформанс-ревью всему воркспейсу.
**Разворот:** публикация всегда проходит через ручной аппрув с выбором базы: `POST /agent-meetings/:id/publish {base: workspace|personal}`. `personal` создаёт `entry` с `is_private=true, owner_id=<публикующий>`. Личные пометки участника — отдельная приватная entry (`is_private=true, owner_id`, `metadata.meeting_id`), сохраняется ещё на этапе claim из `user_notes`. До публикации черновик вообще не в `entries` и в поиск не попадает — приватность дефолтная.

### A5. [HIGH → ✅ реализовано] Confirmed-семантика заменена на `status` (awaiting_review/in_base)
**Тогда:** видимость завязана на `metadata.confirmed`; риск, что встреча навсегда зависнет в «Ожидают».
**Разворот:** у `meetings` явный `status` — `awaiting_review` (на вычитке) → `in_base` (опубликовано). Публикация идемпотентна через гонку-гард, проставляет `entry_id` и `status=in_base`, после чего из очереди вычитки встреча уходит у всех записавших разом. Авто-извлечение задач (`createMeetingTasks`) идёт уже после публикации; сбой извлечения не валит публикацию.

### A6. [HIGH → ✅ реализовано] Дедуп задач: извлечение один раз, после публикации
**Тогда:** в Read.ai-флоу задачи создавались дважды (webhook + `mc_`-подтверждение), безусловный insert.
**Разворот:** транскрибация и генерация черновика идут **один раз** (только claimer). Задачи извлекаются `createMeetingTasks` единожды при публикации из `draft_notes_md`, привязываются к `meeting_id`. Двойного пути insert'а в новом флоу нет.

### A7. [HIGH → ⚠️ открытый вопрос] Эмбеддинги: один вектор на entry
**Тогда:** `entries.embedding` — единственная vector(1536), `getEmbedding` режет вход до 8000 символов; часовой транскрипт эмбеддился бы на ~10%.
**Сейчас:** эмбеддинг получает **только публикуемая entry тезисов** (компактный текст), а не сырой транскрипт — текущая модель MVP закрывает основную боль. Полный транскрипт хранится в `meetings.transcript` (jsonb-сегменты) и в семантический поиск намеренно не попадает. Чанкование транскрипта остаётся в бэклоге, если понадобится поиск по сырой расшифровке.

### A8. [MEDIUM → ✅ в основном закрыто] Переиспользование хелперов
**Тогда:** в `_shared/` было мало переиспользуемого; телеграм-хелперы прибиты к ADMIN_CHAT_ID; `chatComplete` всюду gpt-4o-mini с обрезкой входа.
**Сейчас:** появился `_shared/agent-auth.ts`; уведомления записавшим шлются по списку `recorders` (не только админу), с кнопкой «Открыть», если задан `WEB_BASE_URL`. Тезисы делает **GPT-4o** по полному транскрипту, извлечение задач — GPT-4o-mini. Деплой функций с `_shared` — только через supabase CLI (MCP-деплой ломает импорты) — правило в силе.

### A9. [MEDIUM → ✅ реализовано] `source='desktop-agent'` видим во всех выборках
**Разворот:** фильтры поправлены в трёх местах: `swarm-api` GET /meetings (`.in("source", ["read_ai","granola","desktop-agent"])`, index.ts:889), MCP `get_meetings` (`.in("source", ["read_ai","granola","desktop-agent"])`, index.ts:324), бот `rai_saved`. Granola при этом тоже не теряется (прежний баг MCP закрыт).

### A10. [MEDIUM → ✅ реализовано] Правка тезисов — через swarm-api с веб-сессией
**Тогда:** старый PATCH /meetings/:id не пересчитывал embedding, не проверял владельца, искал по entries.id; вариант «прямой Supabase client с RLS из Next.js» противоречил архитектуре (RLS на entries не включён, защита — код + SERVICE_ROLE).
**Разворот:** правка идёт через swarm-api (аутентификация — веб-сессия роя: `verifyInitData` / JWT httpOnly cookie): `PATCH /agent-meetings/:id` пишет `draft_notes_md` и проставляет `notes_edited_at` (защита человеческой правки). Видны/правятся встречи только записавшим или админу.

### A11. [MEDIUM → ✅ реализовано] Таймаут + retry: ответ 202 + фон
**Тогда:** синхронная цепочка GPT-4o упиралась в wall-clock Edge Functions, клиент отваливался → ретрай → дубль.
**Разворот:** `meeting-ingest` отвечает **202** сразу, тяжёлую обработку (транскрибация обеих дорожек → сведение сегментов → GPT-4o → `draft_notes_md` → уведомление) выносит в фон через `EdgeRuntime.waitUntil`. Дедуп на claim снимает риск размножения при ретрае. Двойного включения транскрипта в промпт в новом пайплайне нет.

## C. Локальная транскрибация на машинах пользователей (правки к 04) — ⛔ ВСЯ СЕКЦИЯ СНЯТА РАЗВОРОТОМ

> Весь раздел относился к плану «форк `fastrepl/anarlog` (Tauri/Rust) + локальный Whisper». **Этот план отменён.** Транскрибация ушла в облако (OpenAI `/v1/audio/transcriptions`, модель `whisper-1`, `verbose_json` → сегменты с таймстампами), рекордер — собственное лёгкое macOS-приложение (Swift/AppKit, `recorder/`), которое шлёт **аудио** (две дорожки AAC m4a), а не транскрипт. Никакого локального ML/GPU на машинах пользователей. Шаг транскрибации сменный: при появлении машины с NVIDIA-GPU можно переехать на локальный Whisper без смены контракта — но это **не текущий план, лишь возможность**. Пункты ниже сохранены только как след истории; к текущей архитектуре неприменимы.

### C1. ⛔ снято разворотом
Batch/live-режимы апстрима, его ретеншен записей — неактуальны: своего форка нет, локальной транскрибации нет.

### C2. ⛔ снято разворотом
Спор про STT-движок апстрима (Soniqo / Parakeet-TDT, whisper.cpp за фиче-флагом, GGML q8 vs GGUF q5) полностью неактуален: локальный Whisper/whisper.cpp/large-v3/GGUF в проекте отсутствует. Транскрибация — облачный `whisper-1`.

### C3. ⛔ снято разворотом
Пометки с таймстампами в редакторе апстрима — неактуально: чужого Tiptap-редактора нет. Пометки владельца — обычный приватный текст (`user_notes` → приватная entry на claim). Сведение «собеседник/я» по таймстампам делает **сервер** из двух аудио-дорожек.

### C4. ⛔ снято разворотом
Темп релизов апстрима и стратегия пинов/черри-пиков/rebase — неактуально: от форка отказались, своего апстрима у рекордера нет.

### C5. ⛔ снято разворотом
Тяжесть сборки апстрима (Rust 1.94 + pnpm 11 + обязательный Swift/Xcode, репо ~620 МБ, DMG 165 МБ, Core Audio process tap → macOS 14.2) — неактуально. Собственный рекордер: SwiftPM + ручная сборка `.app` (`build-app.sh`), **полный Xcode не нужен**, минимальная macOS **13**. Системный звук — ScreenCaptureKit (TCC Screen Recording), микрофон — AVAudioRecorder (`NSMicrophoneUsageDescription`).

## D. Безопасность и операционка (правки к 01/06/07)

### D1. [CRITICAL → ✅ реализовано] Внедрён per-user токен вместо статического секрета
**Тогда:** один статический секрет на команду (доставался из pkg, спуфил owner_telegram_id, не отключался при offboarding; ротация была сломана самой спекой 06).
**Разворот:** аутентификация агента — **персональный smcp-токен** (`Authorization: Bearer`), SHA-256-хэш в `allowed_users`, верификация в `_shared/agent-auth.ts` (`verifyAgentToken` → `{telegramId, groupId}`). Личность и `group_id` — из токена, не из payload (спуфинга нет). Это **не** статический общий секрет.
**⚠️ Открытый вопрос:** у токена есть срок жизни (90 дней) и ревокация — при истечении нужен либо долгоживущий agent-токен, либо явная обработка 401 на стороне рекордера (видимый сигнал пользователю). Хранение токена — на стороне пользователя, не в общем конфиге.

### D2. [HIGH → ⚠️ открытый вопрос] Согласие на запись
Тема остаётся актуальной и при облачной транскрибации: записываем онлайн-звонки, собеседники (включая внешних) могут не знать. Скоуп захвата сужен до онлайн-звонков (Google Meet, Контур.Толк, Telegram-звонок, редко Zoom). Минимум прежний: внутрикомандная политика, осторожность со внешними участниками, возможность не записывать конкретную встречу. Данные attendees доступны для фильтрации, когда есть из календаря.

### D3. [HIGH → ⛔ снято разворотом] postinstall от root
Неактуально: **pkg-инсталлера нет**. Распространение через pkg / postinstall от root в проекте отсутствует. Рекордер — `.app`-бандл, ставится в пользовательский home без root-скриптов.

### D4. [HIGH → ⛔ снято разворотом] Ad-hoc подпись и платный Apple Developer
Подпись рекордера — **ad-hoc codesign** (`build-app.sh`). Рекомендация «$99/год Apple Developer (Developer ID + нотаризация)» из прежней версии **полностью снята** — платный аккаунт Apple и нотаризацию не закладываем даже как возможность. Известное неудобство: после пересборки бандла macOS может потребовать заново выдать TCC-разрешения (Screen Recording, микрофон) — пользователь делает это при первом запуске и, возможно, повторно после обновления. Это принимаем как издержку, без перехода на платный аккаунт. Способ распространения бинаря без платного аккаунта — **открытый вопрос**, решается отдельно.

### D5. [MEDIUM → ⛔ снято разворотом] SMB-обход Gatekeeper
Неактуально: раздачи pkg по SMB-шаре нет (инсталлера нет вовсе). Supply-chain-вектор через подмену pkg в шаре к текущей архитектуре не относится.

### D6. [HIGH → ✅ реализовано] Дедуп между участниками
**Тогда:** meeting_id генерился каждым агентом локально → N участников = N записей/генераций/задач.
**Разворот:** дедуп серверный, на этапе **claim**. Приоритет ключа идентичности: `calendar` (`<iCalUID>:<YYYY-MM-DD>` с датой экземпляра) → `room` (`meet:<code>` / `kontur:<room>` из URL звонка) → `manual:<uuid>` (Telegram/кнопка, без авто-дедупа). Уникальный индекс по `identity_key` (кроме manual) + `decision: transcribe|defer` гарантируют, что транскрибирует и генерит тезисы **ровно один** записавший. Кросс-источник (granola) и manual — ручное «Объединить» в вебе.

### D7. [MEDIUM → ⚠️ частично] Жизненный цикл приложения на macOS
Часть рисков снята сменой стека: рекордер — меню-бар `LSUIElement`, не LaunchAgent с pkg. Остаются практические нюансы рекордера (single-instance, поведение при логауте/выключении во время записи, целостность недописанного аудиофайла) — учитываются в `recorder/`, режим `--selftest` прогоняет полный цикл e2e. Конкретику смотреть в коде `recorder/`, не в этом доке.

### D8. [LOW → ⛔ в значительной части снято] Whisper/аудио на M1/8GB
Оценки локальной транскрибации (минуты/час, Metal, очередь «не транскрибировать пока идёт запись») неактуальны — транскрибация в облаке. Остаётся забота об **аудио** на клиенте: компактный AAC m4a (~10 МБ/час), лимит файла OpenAI 25 МБ → длинные встречи резать/жать (это **TODO**). Рекордер пишет две дорожки AAC (системный звук + микрофон) и грузит их; локального хранения тяжёлых WAV нет.

1. **Сосуществование трёх источников** (Read.ai → выключаем в конце месяца; Granola — продолжает работать, отключим сами после запуска своего софта; desktop-agent — новый) в UI/боте/MCP. → **Закрыто механически:** source-фильтры включают все три в боте/вебе/MCP. Остаётся операционная коммуникация с командой.
2. **Миграция исторических данных** Read.ai/Granola — зафиксировать, мигрируем ли. Открыт.
3. **Идентичность встречи из браузера:** id комнаты Google Meet / Контур.Толк берём из URL вкладки; календарный ключ — когда есть событие. Надёжность извлечения для разных клиентов — проверить на пилоте.
4. **Нужен ли шаг подтверждения задач** от desktop-agent встреч отдельно от аппрува самой встречи. Сейчас задачи извлекаются автоматически при публикации (`createMeetingTasks`); вопрос — нужна ли отдельная вычитка задач.
5. **Стоимость потока:** облако ≈ **$0.36/час** встречи (whisper-1) + центы на тезисы (GPT-4o) и извлечение задач (GPT-4o-mini); ~20 чел. Снять реальную метрику после пилота.
6. **Тестовая стратегия backend:** нужны фикстуры «ретрай после таймаута» и «двойная отправка двух участников» (claim → defer). Режим `--selftest` рекордера доказывает e2e-цикл со стороны клиента.
7. **Распространение рекордера без платного Apple-аккаунта** (см. D4) — открытый вопрос: как доставлять `.app` команде и как минимизировать повторную выдачу TCC-разрешений после обновлений, не прибегая к Developer ID/нотаризации.
