# 09 — Сверка с реальностью: несостыковки спек и подводные камни

Результат анализа пакета 00–07 против реального кода Swarm Brain (sandbox_vas, 2026-06-12) и апстрима fastrepl/anarlog. Ключевые находки по miniapp верифицированы адверсариальной проверкой. Этот документ — эррата: при работе по спекам 02–06 сверяться с ним, противоречие решать в пользу реальности кода.

## A. Модель данных и бэкенд (правки к 02/03)

### A1. [CRITICAL] Таблицы `meetings` не существует
Встречи — строки `entries` с `metadata={meeting_id, title, duration, confirmed, entry_date}` (см. `read-ai-webhook/index.ts:245-257`; granola — тоже entries, `source='granola'`). Полей `meeting_uid/transcript/user_notes/notes_md/notes_edited_at/owner_telegram_id/agent_version` нет нигде. §1 спеки 03 (ALTER TABLE meetings) неприменим целиком.
**Развилка:** расширять `entries` (колонки или metadata jsonb + функциональный уникальный индекс по `metadata->>'meeting_id'`) ИЛИ новая таблица — но новая таблица выпадает из entries-guard/visibilityFilter/поиска и потребует дублирования всей защитной механики. Рекомендация: оставаться в `entries`.
Дополнительно: `tasks.meeting_id` (text) уже двусмыслен — webhook пишет туда session_id Read.ai, бот при подтверждении — entryId (`read-ai-webhook/index.ts:134` vs `swarm-bot/tasks/handlers.ts:186`).

### A2. [CRITICAL] Идемпотентности нет — её надо строить с нуля
Upsert по meeting_id, `notes_edited_at`-защита, 409 — ничего из контракта 02 не существует: оба пути записи — голый insert, уникального индекса нет. В связке с retry-агента (бэкофф до 6ч) каждый таймаут сервера = дубль встречи + дубль задач. Уникальный индекс + findByUid + ветка humanEdited — обязательны ДО подключения агента.

### A3. [HIGH] Воркспейс: в payload нет group_id, «образец» хардкодит 'cee'
Всё фильтруется по `group_id`. `read-ai-webhook` хардкодит `group_id:'cee'` и шлёт уведомления только админу — копировать нельзя. Правильно: резолв `allowed_users.group_id` по owner_telegram_id (как `swarm-api/index.ts:172-180`). В контракте 02 `owner_telegram_id` лежит в «опциональном» блоке — сделать обязательным, иначе entry с `group_id=null` невидима всем.

### A4. [HIGH] Приватность: в контракте нет `is_private`
Оба текущих флоу дают выбор «💾 В базу / 🔒 В личное» перед сохранением. Агент пишет всё подряд (включая 1:1 и перформанс-ревью) и по спеке сохраняет без подтверждения → транскрипты видимы всему воркспейсу. Ошибка в 05: «admin видят всё» — в entries-guard НЕТ admin-байпаса для приватных. Нужно: `is_private` в payload + переключатель в окне записи + дефолт «приватно» для встреч ≤2 участников.

### A5. [HIGH] «Существующая серверная проверка тезисов» = `metadata.confirmed`
Флоу: webhook сохраняет `confirmed:false` → Telegram-кнопки `mc_` → `confirmed:true` + ТОЛЬКО ТОГДА `analyzeAndCreateTasks`. Если meeting-ingest пишет `confirmed:false` и не шлёт подтверждение — встречи навсегда зависнут в «Ожидают» (miniapp/API фильтруют по этому флагу). Писать `confirmed:true` явно. Открытый вопрос: задачи имеют СВОЙ `confirmed` (default false, не попадают в dueToday) — кто подтверждает задачи от desktop-agent встреч?

### A6. [HIGH] Дедупа задач нет; в Read.ai-флоу задачи уже создаются ДВАЖДЫ
`extractAndSaveTasks` в webhook (сразу) + `analyzeAndCreateTasks` при `mc_` — существующая мина. Все пути — безусловный insert. Для meeting-ingest: при повторном upsert удалять старые задачи по meeting_id перед пересозданием (паттерн `md_`-удаления) или сверка по хешу.

### A7. [HIGH] Эмбеддинги: один вектор на entry; хелперы режут вход до 8000 символов
«Транскрипт чанками по 800 токенов как везде» — такого нигде нет: `entries.embedding` — единственная vector(1536), `match_entries` ищет только по entries, `getEmbedding` всюду `slice(0,8000)`. Часовой транскрипт (~60–100К символов) сейчас эмбеддился бы на ~10%, а `content` у read-ai хранит только первые 8000 символов — «полный транскрипт хранится» для текущего кода неверно. Чанки = либо отдельная таблица + новый RPC + правка трёх поисковых клиентов, либо решение «эмбеддим только тезисы» в MVP.

### A8. [MEDIUM] «Переиспользовать хелперы» = вынести в _shared и адаптировать
В `_shared/` реально есть только countries, jwt, search, tasks/*. Телеграм-хелперы webhook прибиты к ADMIN_CHAT_ID (per-user образец — в `granola-poller`); `chatComplete` везде gpt-4o-mini + обрезка входа 5–12К символов + max_tokens 2000 — для GPT-4o по полному транскрипту переписывать. Деплой функций с `_shared` — только supabase CLI (MCP-деплой ломает импорты).

### A9. [MEDIUM] source='desktop-agent' невидим во всех выборках
Править фильтры в трёх местах: `swarm-api` GET /meetings (`.in('source',['read_ai','granola'])`), MCP `get_meetings` (`.eq('source','read_ai')` — granola там уже потеряна, существующий баг), бот `rai_saved`.

### A10. [MEDIUM] PATCH-правка тезисов: существующий PATCH не годится, «RLS из Next.js» нереализуем
PATCH /meetings/:id меняет только summary/confirmed/countries, НЕ пересчитывает embedding, не проверяет владельца, ищет по entries.id (не по meeting_uid). RLS на entries не включён вообще (вся защита — код + SERVICE_ROLE) — вариант «прямой Supabase client с RLS» из 03 §4 противоречит архитектуре. Путь один: расширять swarm-api (+ веб-сессия httpOnly cookie из R-5, requireOwner-паттерн).

### A11. [MEDIUM] Таймаут + retry = размножение встреч
Лимиты Edge Functions: wall-clock 150s (free) / 400s (paid), CPU 2s, 256MB; `EdgeRuntime.waitUntil` доступен, но делит wall-clock. Синхронная цепочка GPT-4o (30–90s) + задачи + эмбеддинги — впритык; клиент агента отвалится раньше и приедет ретрай. «Начать с синхронного» из 03 опасно именно в связке с retry: сразу закладывать 202/`summary_status:processing` + waitUntil/очередь, либо сначала A2. Промпт 03 §3 включает транскрипт дважды (окна ±120с + полный) — раздувает токены.

## B. Веб (правки к 05) — всё верифицировано

### B1. [CRITICAL] Deep link `/meetings/[uid]` сейчас невозможен — блокер №1
Четыре причины: (1) SPA на `useState`, URL не читается нигде; (2) `output:"export"` — динамический роут не собирается, на CF Pages будет 404; (3) `start_param`/`startapp` не парсится (0 совпадений по src/); (4) после `/login` CF-функция всегда редиректит на `/` — return-to нет. Решения — в 08-UI-UX.md, шаг 3 миграции. Решить до вёрстки страницы встречи.

### B2. [HIGH] «Times» — сломанный пайплайн шрифтов
`--font-sans: var(--font-sans)` в `globals.css:10` — циклическая самоссылка (Tailwind эмитит её в :root → guaranteed-invalid → UA-дефолт serif); `next/font` не подключён вовсе. Фикс — полчаса (08-UI-UX.md шаг 1).

### B3. [HIGH] Десктоп-адаптации нет совсем
Ноль md:/lg: и max-w в экранах, BottomNav fixed на любой ширине, канбан — одна колонка через табы со свайпами даже на 2560px. Каркас не «недоделан» — не начат.

### B4. [HIGH] Дизайн-токены = дефолт shadcn-init
Вся палитра с хромой 0 («серое-на-белом»), `.dark` определён, но класс нигде не выставляется (тема мертва), `themeColor:"#0b0b0b"` конфликтует со светлым UI, title «Рой — задачи» устарел.

### B5. [HIGH] До страницы-редактора по 05 — почти всё с нуля
Переиспользуемы: api-слой (fetchMeeting/patchMeeting) и confirm-флоу. Нет: роута, markdown-редактора, полей нового пайплайна в types (transcript/user_notes/summary_status/notes_edited_at/participants/duration), конфликт-детекции, задач встречи, спойлеров, перегенерации, processing-поллинга. Текущий MeetingDetailDialog покрывает <20% спеки.

### B6. [MEDIUM] Гигиена кода miniapp
5+ копий карточки-пилюли, 6 копий шапки, fetch-в-useEffect без слоя данных (7-й раз изобретать для поллинга processing); сырые telegram ID в TaskCard (костыль есть только в TeamScreen); RU/EN-винегрет без словаря; 44 ветки DEV_MODE + моки с внутренней фактурой в прод-бандле (571 строка api.ts); sw.js cache-first отдаёт старую оболочку после деплоя; URL не несёт состояния (ссылку коллеге не скинуть).

## C. Desktop Agent / anarlog (правки к 04)

### C1. [+] Главный страх спеки снят: batch-режим есть и для русского он единственный
`TranscriptionMode {Live, Batch}` — первоклассный; live локально только для английского. Русская локальная транскрибация в апстриме УЖЕ работает «запись в файл → batch после». Ретеншен записей тоже есть (services/audio-retention). Патчить пайплайн не нужно — настроить.

### C2. [HIGH] Спека ошибается в STT-движке
Апстрим мигрировал локальный STT на собственный движок **Soniqo** (Swift/CoreML): Parakeet-TDT-v3 INT8 — batch, 25 языков ВКЛЮЧАЯ русский. whisper.cpp остался за фиче-флагом `whisper-cpp`, который в дефолтной сборке ВЫКЛЮЧЕН; large-v3-turbo существует только как GGML **q8_0 (~874 МБ)**, не GGUF q5 (~600 МБ); кастомный файл модели без патча не подключить (фиксированный enum). План §5 пересмотреть: сначала тестировать soniqo-parakeet-batch на русском, Whisper q8 — запасной путь с патчем Cargo.toml. Sonique свежий и сырой (краши CoreML чинились в июне 2026) — этап 0 (тест-созвон) обязателен, сравнить оба движка на одном аудио.

### C3. [HIGH] Пометок с таймстампами в апстриме НЕТ
Заметки — единый Tiptap-JSON без привязки ко времени. Таймстампы есть только у сегментов транскрипта. Фичу «строка пометки получает ts» писать с нуля — проще своё компактное окно вне их редактора. Увеличить оценку plugin-swarm.

### C4. [MEDIUM] Темп апстрима противоречит «подтягивать 1–2 раза в год»
~10 релизов за 12 дней, 100+ коммитов в lib.rs (наш файл патча) с января, STT-слой уже один раз заменили целиком. Команда fastrepl сместила фокус на закрытый char.com. Стратегия: пин на SHA, point-fixes черри-пиком (аудио), полный rebase — осознанный мини-проект, не рутина.

### C5. [MEDIUM] Сборка и требования тяжелее заявленных
Rust 1.94 + pnpm 11 + **обязательный Swift/Xcode** (swift-rs в крейтах soniqo/tcc/notification). Репо ~620 МБ, DMG апстрима 165 МБ — «тонкий агент» по объёму таким и будет. System audio через Core Audio process tap → **минимальная macOS 14.2** — проверить парк машин, добавить в 06.
Мелочи: плагины без префикса plugin- (plugins/local-stt); owhisper-client — не «облачные провайдеры», а адаптерный слой, выпиливать нельзя; авто-старт/стоп записи по календарю в апстриме уже есть (settings auto_start_scheduled_meetings).

## D. Безопасность и операционка (правки к 01/06/07)

### D1. [CRITICAL→решение есть] Один статический секрет на команду — заменить на per-user токены
Секрет достаётся из pkg за минуту (pkgutil --expand), лежит plaintext в config.json, owner_telegram_id спуфится любым носителем секрета, offboarding не отключает доступ. **Ротация сломана самой спекой:** 06 фиксирует «postinstall не перезатирает config.json» → новый pkg с новым секретом не доставит его никому, а на 401 агент по контракту «не ретраит» → вся команда молча отвалится. В проекте УЖЕ есть per-user механизм: smcp_-токены (выдача /mytoken, ревокация, SHA-256-хэш, TTL 90 дней — миграция 20260611000000). Решение: аутентифицировать meeting-ingest персональным токеном (онбординг: вставка токена вместо ввода Telegram ID; identity из токена, owner_telegram_id из payload игнорировать). Нюанс: TTL 90 дней → нужен либо долгоживущий agent-токен, либо явная обработка 401 (красный значок + нотификация). Хранить в Keychain, не в config.json.

### D2. [HIGH] Согласие на запись
Скрытая автозапись system audio всех звонков; собеседники (включая внешних: кандидаты, партнёры) не знают. ЕС/GDPR-юрисдикции в команде. Минимум: внутрикомандная политика, НЕ записывать встречи с внешними (фильтр по доменам attendees — данные в payload уже есть), кнопка «не записывать эту встречу» в окне агента.

### D3. [HIGH] postinstall выполняется от root
«~/Library» в postinstall = /var/root/Library — config и LaunchAgent уедут root'у, запуск приложения от root. Нужно: `loggedInUser=$(stat -f%Su /dev/console)`, писать в его home, `chown` + `chmod 600`, `launchctl bootstrap gui/$(id -u $loggedInUser)`, запуск `sudo -u "$loggedInUser" open -a`. Чек-лист «чистый пользователь» это поймает, но лучше заложить сразу.

### D4. [HIGH] Ad-hoc подпись: TCC-разрешения слетают при КАЖДОМ обновлении
Ad-hoc = новая identity на каждую сборку → каждый релиз вся команда заново выдаёт 3 разрешения (часть забудет → встречи молча не пишутся), в плохом случае TCC «застревает» до tccutil reset из терминала. На Sequoia — периодические переподтверждения захвата экрана/звука для всех persistent-захватчиков. **Рекомендация: $99/год Apple Developer (Developer ID + нотаризация) — дешевле одного дня поддержки**; убирает re-grants, SMB-костыль и supply-chain-дыру (см. D5). Если всё же без аккаунта — самодельный сертификат из общего keychain (стабильнее ad-hoc) + проверка разрешений перед КАЖДОЙ записью (07 проверяет только при старте).

### D5. [MEDIUM] SMB-обход Gatekeeper = supply-chain-вектор
Факт верен (сетевые тома без quarantine), но: любой с правом записи в шару подменяет pkg → его postinstall выполнится от root у всей команды без единой проверки подписи. Митигация: право записи только релиз-инженеру, SHA-256 рядом с pkg; лучше — нотаризация. Учесть: pkg, скачанный браузером/Telegram (будет происходить), на Sequoia+ требует Privacy & Security → Open Anyway — включить в инструкцию заранее.

### D6. [HIGH] Дедуп между участниками: одна встреча × N агентов = N записей
meeting_id генерится каждым агентом локально → 5 участников = 5 транскриптов, 5 GPT-генераций, 5 наборов задач-дублей, мусор в поиске. calendar_event_id «опционально для дедупа» — серверной логики нет, iCal UID между календарями не гарантирован. Решить до пилота: «пишет только организатор» / серверный дедуп по (calendar_event_id, started_at±5мин) / хотя бы пометка дублей. Деньги вторичны (GPT-4o ≈ $0.04–0.08/встреча).

### D7. [MEDIUM] LaunchAgent + GUI-приложение
Single-instance guard (LaunchAgent + ручной запуск = два инстанса); KeepAlive=false (иначе незакрываемый зомби); macOS 13+ покажет «Background Items Added» — пользователь может отключить одним кликом (проверка в онбординг). Логаут/выключение во время записи: SIGTERM → битый WAV — нужен обработчик (финализация файла) или формат, переживающий обрыв (raw PCM + финализация при следующем старте / CAF).

### D8. [LOW] Whisper/аудио на M1/8GB
Оценка 3–5 мин/час реалистична (Metal, ~10× реалтайма). Не учтено: транскрибация сразу после встречи при открытом Zoom = memory pressure (просто медленнее); back-to-back встречи — транскрибация №1 совпадёт с записью №2 → очередь с правилом «не транскрибировать пока идёт запись» + QoS background. Аудио: исключить recordings/ из Time Machine (tmutil addexclusion), писать FLAC/Opus вместо WAV (час WAV = 100–600 МБ, за 7 дней до 15 ГБ), проверка FileVault в онбординге.

## E. Открытые вопросы (в спеках не покрыто)

1. **Сосуществование трёх источников** (Read.ai → выводится, Granola, desktop-agent) в UI/боте/MCP на переходный период — фильтры, бейджи, что показывает «Ожидают».
2. **Миграция исторических данных** Read.ai/Granola — ничего не мигрируем? Зафиксировать.

4. **Кто подтверждает задачи** из desktop-agent встреч (см. A5) и нужен ли вообще шаг подтверждения встречи при доверенном источнике + выборе приватности.
5. **Стоимость потока:** ~20 чел × ~3 встречи/нед × GPT-4o ≈ $10–30/мес — ок, но эмбеддинги чанков и перегенерации добавят; снять метрику после пилота.
6. **Тестовая стратегия backend:** curl-фикстуры есть в 03 §5, но нет фикстуры «ретрай после таймаута» и «двойная отправка двух участников» — добавить.
7. **Контракт зафиксирован до разведки** (02 «фиксируем до начала разработки») — после этого документа контракт НУЖНО пересмотреть: +group_id-резолв, +is_private, обязательный owner (или токен вместо него), confirmed-семантика, 202/processing.
