## 🔴 Приватность очереди ревью — встречи «на согласовании» видны слишком широко

> Найдено 2026-06-25 (юзер увидел чужие встречи в «Ревью встреч»). Проверено по коду swarm-api.

**Проблема — pending-встречи видны не только записавшему:**
- **Granola / Read.ai** (`GET /meetings?confirmed=false`): `buildEntriesQuery` фильтрует только воркспейс + приватность, а записи создаются `is_private=false` → **весь воркспейс видит ВСЕ чужие импорты «на согласовании»**. Утечка для всех, не только админа.
- **Рекордер** (`GET /agent-meetings`): `if (!isAdmin) recorders contains telegram_id` — обычный юзер видит только свои, но **админ видит ВСЕ** pending.

**Желаемая модель (юзер):** встреча изначально доступна **только записавшему/импортёру**, и лишь после публикации/подтверждения уходит в базу воркспейса.

**Дизайн фикса:**
- **Granola:** poller пишет pending как `is_private=true, owner_id=<импортёр telegram_id>` (он известен); при подтверждении (`PATCH confirmed=true`) → `is_private=false` (публикация в воркспейс). `buildEntriesQuery` уже энфорсит → авто-скоуп без новых фильтров. Ручной `/granola` save (`confirmed=true`) уже опубликован.
- **Рекордер:** уже recorder-scoped для обычных; убрать/опционализировать admin-sees-all (дефолт «Мои», админ-тоггл «Все»).
- **Публикация флипает приватность:** `PATCH /meetings/:id {confirmed:true}` должен ставить `is_private=false`. Для рекордера publish уже создаёт entries с нужной приватностью.

**Решения до реализации:**
1. **Read.ai** — вебхук без конкретного импортёра (общий OAuth, `group_id='cee'`). Кто «владелец» pending: админ / настраиваемый ревьюер / оставить воркспейс-видимым (общая интеграция)? Без решения нельзя скоупить (owner_id=null + is_private=true → не видно никому).
2. **Админ** — видит ВСЕ pending (сейчас) или только свои (строго recorder-only) + опциональный тоггл «Все»?

**Объём:** write-пути granola-poller + read-ai-webhook, флип приватности в PATCH confirm, политика admin в `GET /agent-meetings`, миграция существующих ~36 pending (бэкфилл owner/is_private или оставить как есть). Granola-часть чистая и реализуема сразу после решения по п.1–2.

## Единый контракт транскрибаторов (pluggable sources) — большой рефактор

> Карта кода 2026-06-25. **Вердикт: транскрибаторы НЕ единообразны.** Рекордер (`desktop-agent`) — спецкейс на отдельном пути; Granola/Read.ai — на другом. Их объединяет только точка назначения (`entries`, `entry_type='meeting'`), не вход и не ревью.

**Как сейчас (две параллельные семьи):**
- **Granola / Read.ai** → пишут сразу в `entries` (`metadata.confirmed=false`), эмбеддинг+тезисы на ингесте; ревью = флаг `confirmed`; аппрув = `PATCH /meetings/:id {confirmed:true}` (флип на месте). Статус «На согласовании».
- **desktop-agent (рекордер)** → двухшаговый протокол в отдельной таблице `meetings` (`meeting-claim` → `meeting-ingest`); эмбеддинг только на publish; ревью = `meetings.status='awaiting_review'`; аппрув = `POST /agent-meetings/:id/publish` (вставляет новую `entries`). Статус «На вычитке».
- Нет общего контракта ингеста, нет реестра источников — список `['read_ai','granola','desktop-agent']` захардкожен по местам (swarm-mcp `.in()`, статистика бота, visibility-фильтры).

**Целевой дизайн (8 шагов, инкрементально, НЕ блайнд-миграцией прод):**
1. `meetings` — единая таблица входа для ВСЕХ источников; `source` = свободный id программы (`granola`/`read_ai`/`swarm-recorder`/`otter`/…), не дефолт `desktop-agent`.
2. Один контракт `TranscriberAdapter`: `claim(identity)` (тривиальный create-or-find по `external_id` для push/poll-источников; реальный lease — для device-рекордеров), `ingest({transcript,summary?,attendees,started_at,source,external_id})`, нормализованный identity (+`identity_kind='external'` для дедупа по note/meeting-id).
3. Тезисы+эмбеддинг — в ОДИН общий пост-ингест шаг (убрать дубль `GRANOLA_TEZISY_PROMPT` в granola.ts/read-ai-webhook).
4. Ревью — на `meetings.status` (`awaiting_review`→`in_base`), retire `metadata.confirmed`; `GET /meetings?confirmed=false` → `GET /agent-meetings?status=awaiting_review` для всех.
5. Publish — один эндпоинт `POST /agent-meetings/:id/publish` для всех (вставляет `entries` confirmed:true, линкует, извлекает задачи). `entries` остаётся финальным артефактом (downstream: поиск, страны, тезисы — не ломаем).
6. Реестр `SOURCES` + общий `sourceLabel()` (сервер+miniapp) вместо хардкод-списка. Новый рекордер = одна запись в реестр + адаптер, ноль правок в запросах.
7. Сквозная идентичность программы записи: `meetings.source` = конкретная программа на claim; UI рендерит `sourceLabel(source)` (после 1–6 вид один → метка выводится единообразно).
8. Миграция: новые встречи — через `meetings`; старые `confirmed=false` записи Granola/Read.ai — оставить как есть ИЛИ разовый бэкфилл. Опубликованные не трогать.

**Открытые вопросы (решить до миграции):**
- `entries` остаётся финальным артефактом (доки: «не ломаем структуру») — подтвердить, что унифицируем только вход+ревью, не схлопываем всё в `meetings`.
- Granola manual-save сейчас авто-публикуется (`confirmed=true`, минует ревью) — оставить bypass или гнать через вычитку?
- Read.ai `group_id` захардкожен `'cee'` — для push/webhook-источников без per-user JWT нужна per-integration workspace-маппинг.
- Один `claim()` с no-op для web-источников, или два тира контракта (coordinated/uncoordinated)?
- Нужна ли РАЗЛИЧАЕМОСТЬ программы записи на карточке (наш рекордер vs будущий 3rd-party), или достаточно «device recording»? (Решает: per-program `source` vs `desktop-agent`+`metadata.recorder_app`.)

**Сделано из этого блока (2026-06-25):** метка источника на карточках вычитки (`sourceLabel`, `desktop-agent`→«Рекордер») + polling статуса на экране вычитки.

## Тезисы встречи на вычитке идут «одним полотном» — рендер блоков (miniapp)

> Найдено 2026-06-25 при ревью экрана «Ревью встреч». Тезисы хранятся как markdown (`### Тема\n- тезис\n- тезис`) ВСЕМИ путями (granola/read-ai генерят, рекордер `draft_notes_md`, бот-правка `meetings.ts:448` — тот же формат), но в вебе рендерятся как сырой текст без разбора markdown.

**Симптом (со скрина):** на «Ревью встреч» саммари показывается сплошной стеной с литеральными `###` внутри строки, без разбивки на разделы/пункты. В боте при вычитке тезисы выглядят как список (Telegram сохраняет переносы строк), в вебе — нет.

**Две причины:**
1. 🔴 **Баг (быстрый фикс):** [`MeetAdminScreen.tsx:461`](../miniapp/src/components/roy/screens/MeetAdminScreen.tsx#L461) рендерит `e.summary` в обычном `<p>` **без** `whitespace-pre-wrap` → переносы строк схлопываются в пробелы → худшее «полотно». Все остальные экраны деталей ([`MeetingDetail:132`](../miniapp/src/components/roy/screens/MeetingDetail.tsx#L132), [`RecordDetail:75`](../miniapp/src/components/roy/screens/RecordDetail.tsx#L75), `AgentMeetingDetail:543`) уже используют `whitespace-pre-wrap` — там хотя бы сохраняются строки. Достаточно добавить класс, чтобы убрать стену.
2. 🟡 **Фича (по сути запроса):** даже с `whitespace-pre-wrap` `###` и `-` показываются литерально — markdown нигде не парсится (в miniapp нет markdown-зависимости). Нужно **разбивать тезисы на логические блоки для вычитки**: заголовки `### Тема` → секции, `- пункт` → список. Варианты: лёгкий собственный парсер (`### ` / `- ` построчно, без зависимости — наш формат стабилен и узкий) ИЛИ `react-markdown`+sanitize (тяжелее, CSP/bundle-бюджет). Сделать **общий компонент** `<TezisyBlocks summary={…}/>` и переиспользовать во ВСЕХ местах рендера тезисов (MeetAdmin, MeetingDetail, RecordDetail, AgentMeetingDetail) — единый вид, единый источник (DRY).

**Заодно (единообразие рендера):** сейчас саммари рисуется 4-мя слегка разными `<p>` — свести к одному компоненту, чтобы вычитка везде выглядела одинаково.

Минимальная конвергенция без большого рефактора: (а) общий компонент рендера тезисов (секция выше), (б) при возможности — один путь извлечения задач (свести бот на `gptExtractTasks` или наоборот). ## Рефреш страницы сбрасывает на главную — сохранять текущий экран (miniapp)

> Найдено 2026-06-25. Симптом: открыл, напр., «Ревью встреч» (или любую деталь) → F5/перезагрузка → выкидывает на корень таба (на десктопе таб `search` → дашборд «главная»). Должно: остаться там, где были.

**Причина (по коду [`RoyApp.tsx`](../miniapp/src/components/roy/RoyApp.tsx)):** навигация — это `tab` + push-стек `stack: RoyRoute[]` (детальные экраны: `meetAdmin`/`recordDetail`/`taskDetail`/`meetingDetail`/…), оба в in-memory `useState`. Активный **таб** персистится в `sessionStorage` (`roy_tab`, restore на маунте) и переживает рефреш, а **стек НЕ персистится** — всегда стартует с `[]` → деталь теряется, остаётся только корень таба. Плюс `RoyApp` намеренно затирает URL (`history.replaceState({}, "", pathname)`), а приложение — `output:"export"` (одностраничное, без per-route URL), поэтому маршрут не восстановить и из адреса.

**Варианты фикса:**
- 🟢 **Лёгкий (в духе текущего кода):** персистить `stack` в `sessionStorage` рядом с `roy_tab` (сериализовать `RoyRoute[]` — там примитивные params: id/query), восстанавливать на маунте. Минимальная правка, без роутера, вписывается в static-export. Edge-кейс: восстановленная деталь по `id` может уже не существовать (удалена) — экран должен мягко падать в корень, а не в белый экран.
- 🟡 **Через URL (hash/query):** кодировать текущий маршрут в `#`/`?` вместо `replaceState` пустого URL → бонусом рабочая кнопка «назад» браузера и шаринг ссылки. Больше работы, надо аккуратно с Telegram WebView.

Рекомендация: начать с лёгкого (sessionStorage-стек), URL-роутинг — если понадобится шаринг/back-кнопка.

## Тезисы desktop-agent зависают в «готовятся» (processing) — надёжность

> 2026-06-25: тестовая запись (ТВ рядом, без звонка) застряла на `summary_status=processing`, рефреш не помог → бэкенд не дописал тезисы.

- **Корень (ведущая гипотеза):** фон транскрибации+тезисов (`meeting-ingest`, `EdgeRuntime.waitUntil`) убит по wall-clock воркера (~150с) до `done` и до `catch`(→`failed`). Длинная запись = вечное «готовятся». Документированный риск (durable-обработка не сделана).
- 🟡 **Watchdog:** помечать `summary_status='failed'`, если фон не завершился за N минут (не висеть «готовятся» вечно). В `meeting-ingest` — деплой связан с миграцией `mic_start_offset` (#10).
- ✅/🟡 **Polling на экране вычитки** — делается (frontend), статус сам обновляется + показывает `failed`.
- 🔴 **Durable-обработка (long-term):** аудио в Storage на ingest (202 сразу) + cron/queue-воркер, добивающий транскрибацию инкрементально (переживает рестарт). Снимает wall-clock-потолок для длинных встреч. Внимание: сырое аудио в Storage = приватность (signed URLs).

## Бот: фрагментация и дедуп сохранения в базу (knowledge ingestion)

> Найдено при ревью встреч 2026-06-19 (запросы к prod-БД). Пользовательская формулировка: пересланный/вставленный текст — это «сырой контекст на будущее», должен лежать как ОДНА запись, а не дробиться/дублироваться.

**Проблема:** бот сохраняет КАЖДОЕ входящее telegram-сообщение отдельной записью, без группировки и без дедупа. Это даёт фрагментацию и дубли:
- 11 июня: один логический текст про договорённости с Павлом (Испания) лёг **3 записями** за ~2 мин (заголовок-одиночка → note/General; тело → meeting/**RS** (ошибка страны); заголовок+тело → meeting/ES).
- 18 июня: один методологический док (~1850 симв) сохранён **дважды** за **25 секунд** — это **полные дубликаты** (1852 vs 1843 симв), а НЕ разные секции. В списке выглядят как разные темы только из-за заголовка (UI берёт первую строку `### …`, а у копий первая `###`-секция разная). Бот не дедуплицирует → две одинаковые записи LT.

**Сопутствующее (LLM-классификаторы swarm-api `POST /entries`):**
- `entry_type` meeting/note непостоянен (заметка-со-ссылками или заголовок-одиночка → meeting → попадает в очередь «Ревью встреч»).
- Страна мис-тег (Испания/Сабадель → RS).

**Желаемое поведение (к обсуждению дизайна):**
- ✅ **Группировка фрагментов реализована (2026-06-22, прод):** подряд идущие сообщения одного автора в окне **60 с** (source `telegram`) дописываются к той же записи с переиндексацией (`saveEntry`). Multi-message форварды кусками → одна запись.
- ✅ **Дедуп реализован (2026-06-19 точный + 2026-06-22 near-identical, прод):** за **7 дней** на уровне воркспейса (`saveEntry`, sources `telegram`/`note`) — точный матч по нормализации (любая длина) ИЛИ триграм-сходство ≥95% (для текста >100 симв). Повторная отправка/вставка и отложенный дубль коллеги не плодят запись; реальная правка (<95%) сохраняется как вариант. `document`/`voice`/`read_ai`/`digest` НЕ дедупятся (документ — чанки в цикле).
- Для «сырого контекста» (форвард/вставка) — более лёгкий путь: сохранять как один note как есть, без агрессивной meeting-классификации; meeting-тип — только для явных транскриптов. _(частично снято группировкой)_

### Дедупликация встреч Granola при нескольких участниках

### Админка — контроль трафика и расходов по инструментам
> Зафиксировано 2026-06-12 при выборе облачной транскрибации для Swarm Meetings.

С переходом на облако расходы идут **по факту использования** (OpenAI: транскрибация по минутам аудио, тезисы и эмбеддинги по токенам). Нужна видимость и контроль, чтобы не улетать по бюджету и видеть, что сколько потребляет.

**Scope:**
- **Учёт по инструменту/функции:** транскрибация (Whisper, минуты), тезисы (GPT, токены), эмбеддинги, поиск и т.д. — количество вызовов + расчётная стоимость, разбивка по периодам.
- **Разбивка по воркспейсу и пользователю** — кто/какой воркспейс сколько генерит трафика и денег.
- **Лимиты/квоты и алерты** (опц.): месячный потолок по инструменту/воркспейсу, уведомление при подходе к лимиту, мягкая остановка при превышении.
- **Переключение моделей без передеплоя** (опц.): напр. тезисы `gpt-4o` ↔ `gpt-4o-mini`, выбор модели транскрибации — из конфига/админки.

**Как считать:** логировать каждый внешний вызов (инструмент, модель, единицы — минуты/токены, расчётная стоимость, `telegram_id`, `group_id`, время) в таблицу `api_usage`; админка агрегирует. Прайс — в конфиге (per-model rates), пересчёт стоимости на лету.

**Форм-фактор:** страница в miniapp (раздел «Админ», `is_admin`) поверх swarm-api, либо суперадмин-команды. Дополняет «Админка — управление пользователями и интеграциями».

**Приоритет:** заводить вместе с запуском Swarm Meetings — облачная транскрибация = реальные деньги по факту, без учёта легко не заметить рост.

## MCP — доступ из Claude через орг-коннектор (Team, OAuth)

> Контекст собран 2026-06-11. Команда переходит на **корпоративные Claude-аккаунты, тариф Team.**
> Цель: подключить `swarm-mcp` к Claude так, чтобы доступ был только у нужных людей.

### Почему нельзя как сейчас
- На Team/Enterprise **кастомный коннектор добавляет только Owner орга** — рядовой участник не может подключить MCP-сервер сам.
- **Орг-коннектор = только OAuth.** В UI нет поля для статического `Authorization: Bearer`-токена (Anthropic закрыла запрос как «not planned», issue anthropics/claude-ai-mcp #112). Claude ходит на сервер из облака Anthropic; при `401` ждёт OAuth-discovery (`/.well-known/oauth-*`).
- **Нет пер-юзерного гейта** у орг-коннектора: Owner включил → подключиться может любой член орга. Ограничить доступ на стороне Claude нельзя.
- Наш статический `smcp_`-токен работает только через локальный путь — Claude Desktop `claude_desktop_config.json` + `mcp-remote --header`. Но локальный MCP корп-IT может вырубить политикой (`isLocalDevMcpEnabled=false` через MDM) → как командное решение ненадёжен.

### Вывод
Единственный санкционированный путь на Team — **Owner добавляет swarm-mcp в орг-список**, а это требует **OAuth на нашем сервере**. Гейт «нежелательных» обязан жить **внутри swarm-mcp, в шаге `authorize`**: пропускаем только тех, чья личность есть в `allowed_users`, остальным членам орга — отказ.

### Предлагаемая архитектура (переиспользуем R-5)
В R-5 уже сделан веб-вход через **Telegram Login Widget → JWT с `telegram_id`** (CF Pages Functions, httpOnly cookie). Это готовый identity-слой для OAuth-флоу:
```
Claude (орг-коннектор) → authorize на swarm-mcp
  → редирект на R-5 Telegram-login страницу (уже есть)
  → знаем telegram_id → проверяем allowed_users → нет → отказ
  → минтим MCP access-token, привязанный к telegram_id
swarm-mcp валидирует OAuth-токен (вместо/поверх текущего smcp_)
```
`allowed_users` (ключ `telegram_id`) ложится идеально, маппинг email↔telegram не нужен.

### Объём работ (для будущей дизайн-сессии)
- `swarm-mcp`: эндпоинты `/.well-known/oauth-protected-resource` + `/.well-known/oauth-authorization-server`, `authorize`, `token`, PKCE.
- `authorize`: гейт по `allowed_users`; источник личности — R-5 Telegram-login.
- Хранение OAuth-кодов/токенов (новая таблица или переиспользовать `oauth_tokens`).
- Owner орга добавляет коннектор: Organization settings → Connectors → Add → Custom → Web.

### Что уже сделано (groundwork, prod 2026-06-11)
- ✅ Token lifecycle: миграция `mcp_token_lifecycle` — `claude_mcp_token_expires_at` (срок 90 дней), `revoke_mcp_token()`; enforce expiry в `swarm-mcp`; `/mytoken` со сроком + `/revoketoken` в боте. Это усиливает локальный (config.json) путь и пригодится как fallback.

## Общая база между воркспейсами (cross-workspace shared entries)

> Контекст собран 2026-06-12 (brainstorm-сессия, припарковано до появления необходимости).
> Идея: часть записей — заметки-инструкции вида «добавь в базу: инструкция по ТВ бордам *ссылка*» — должна быть видна **во всех воркспейсах**, а не только в своём.

### Решения, принятые в обсуждении
- **Триггер лингвистический:** «добавь в **общую** базу» = на все воркспейсы; «добавь в базу» (дефолт) = свой воркспейс. Тот же паттерн, что у `save_private` («личное», «только для меня»), только в другую сторону. Итоговая шкала видимости: **личное → воркспейс (дефолт) → общая**.
- **Модель данных:** `ADD COLUMN entries.is_shared boolean DEFAULT false` (имя уточнить — возможно `is_global`, см. конфликт нейминга ниже). `group_id` остаётся «родным» воркспейсом записи. Миграция данных не нужна — существующие записи не трогаются.
- **Ретроактивный шеринг тривиален:** любую старую запись можно сделать общей одним `UPDATE ... SET is_shared = true` по id (или кнопкой «опубликовать» постфактум). Что нельзя автоматизировать — *решить*, какие старые записи общие: ручная разметка либо разовый LLM-проход по заметкам/ссылкам с подтверждением.

### Открытый вопрос (обсуждение прервано здесь)
- **Права на общую запись для чужого воркспейса.** Склонялись к **read-only** (мутации — только владелец + суперадмин, как текущий `requireOwner`), но окончательно не утвердили. Альтернативы: вики-режим (править могут все, удалять — владелец) / полный доступ.

### Точки интеграции (разведаны)
- **Фильтры видимости** — три места, где `.eq("group_id", groupId)` меняется на `.or(group_id.eq.X, is_shared.eq.true)`:
  - `swarm-api/entries-guard.ts` — `getEntrySecure` (layer 1) + `buildEntriesQuery`;
  - `_shared/search.ts` — `matchEntries` (фильтр поверх RPC `match_entries`);
  - листинги в swarm-bot (`lib/storage.ts`).
- **Regex fast-path** `swarm-bot/index.ts` (~198): «добавь в общую базу» сейчас **НЕ** матчится (`в\s+базу` ломается словом между «в» и «базу») и уйдёт в GPT как вопрос — нужен отдельный паттерн до общего.
- **GPT-тулзы** `swarm-bot/handlers/knowledge.ts`: ⚠️ конфликт нейминга — существующий тул `save_shared` означает «общий **внутри** воркспейса». Новое понятие развести как `global`/`is_global` либо переименовать scope-параметром (`scope: workspace | global | private`).
- **MCP `add_knowledge`** — опциональный параметр + строчка в инструкцию Claude Desktop («добавь в общую базу» → ставить флаг).
- **MCP `update_entry`** — тоже принимает флаг: обязательный сценарий — **точечный перевод существующих записей в глобал по запросу через Claude** («сделай запись про ТВ борды общей» → `search_knowledge` находит id → `update_entry` ставит флаг). Права: владелец/суперадмин.

## ~~Таксономия записей — встреча vs заметка~~ ✅ реализовано 2026-06-17

Связано с памятью `project-taxonomy-tasks-notes-types`. Поводом стал баг правки записей из чата: «замени ссылку в форме … стандартов» тащило транскрипты встреч — фильтры по источнику текли.

### Диагноз (по факту в БД, 2026-06-17)
- **`source` засорён свободным текстом**: помимо контролируемых (`telegram/granola/read_ai/link/note/voice/digest`) лежат строки-заголовки и имена файлов — `«Болгария — встреча 14.05.2026»`, `«20cm_Pizzas_Presentation.pptx»`, `«transcript_хорватия_арина…»`, `«справка / инструкция пользователя»`. → любой фильтр «это встреча?» по `source` течёт.
- **`entry_type` размыт (5 типов)**: ссылки и как `document` (24), и как `note` (21); Granola и `meeting` (37), и `note` (15); плюс `summary` (10) и `transcript` (8).
- **`meeting_id` почти не проставлен** (1 запись) → связка встреча↔задачи едва работает.

### Целевая модель — ДВА типа (решение: «только Встреча/Заметка»)
- **Встреча** — `entry_type='meeting'`: транскрипт/тезисы созвона. Источники: granola, read_ai, recorder. Раздел «Встречи».
- **Заметка** — `entry_type='note'`: всё остальное знание (текст, данные, пароль, ссылка, файл). Раздел «База».
- **Подвиды заметки — фасеты через `metadata`, НЕ отдельные типы:** ссылка = `metadata.url`, файл = `metadata.file_name`/`file_type`. UI-тег рисуется по фасету (встреча/ссылка/файл/заметка).
- **`source` = канал** (контролируемый enum: `telegram · web · granola · read_ai · recorder · upload · mcp`). Свободный текст (заголовок встречи, имя файла) → в `metadata.title`/`metadata.file_name`, никогда не в `source`.
- Граница встреча↔заметка проводится **по `entry_type`, не по источнику**.

### ✅ Реализовано 2026-06-17 (prod)
1. ✅ **Бэкфилл-миграция** `entries`: `entry_type` → {meeting, note} (файлы по расширению → note даже при transcript/summary; granola/read_ai/recorder/«встреча…» → meeting). Исходный тип в `metadata.legacy_entry_type`. + **CHECK-инвариант** `entry_type IN (meeting, note)` (миграции `20260617110000`, `20260617140000`).
2. ✅ **Write-пути** ставят только meeting|note (с клампом): классификатор `storage.ts`, granola→meeting, read-ai→meeting, meeting-claim личные пометки→note, swarm-api upload→note/publish→meeting/POST extract, swarm-mcp промпты+клампы.
3. ✅ **UI**: `entryTagKey` по фасету (встреча/ссылка/файл/заметка) + тег `link`; фильтры Базы `entryFacet` (Все/Заметки/Ссылки/Файлы). Фильтры База/Встречи на бэке — по `entry_type` (`GET /entries`='note', `GET /meetings`='meeting').
4. ✅ **manage-флоу**: стопгап убран — правка/удаление ищет по всем записям точно (порог 0.4 + тема); встречи тоже правятся.

**Не сделано (хвосты):**
- `source` НЕ нормализовал в строгий enum — оставил как есть (фильтры теперь по `entry_type`, source = просто метка; чистить нет нужды). Свободный текст в source остался у старых записей.
- Связь `meeting_id` (встреча→задачи) — заодно не чинил, отдельно.

### Вывод по Graphify (knowledge-graph скилл, github.com/safishamsi/graphify)

**❌ Не подключать к Swarm Brain.** Реальный рабочий тул (Tree-sitter → NetworkX → Leiden, проверено по исходникам), но:
- **Приватность:** код/SQL парсятся локально (ок), НО доки/markdown/PDF/картинки уходят LLM-провайдеру на семантику (в сессии Claude Code → Anthropic; headless CLI → дефолт Google Gemini). Артефакты `graphify-out/` встраивают извлечённое содержимое и проект рекомендует **коммитить их в git**; баг v0.8.42 — `.graphifyignore` отключал `.gitignore`, secret-файлы (`prod-dump.sql`, `customer-data.json`) попадали в коммит (пофикшено, паттерн остаётся). Критично для репо с личными данными.
- **Дубль by design:** ставит в CLAUDE.md «MANDATORY: before Read/Grep/Glob you MUST run graphify first» + PreToolUse-хук, перехватывающий встроенный поиск. Конкурирует с Explore/grep/subagents (уже есть) + Context7 + superpowers.
- **Эффект = хайп-adjacent:** единственная цифра — токен-экономия ~71.5× (автор, свои корпуса, без независимого бенчмарка и без метрики качества). «Дешевле» ≠ «понимает лучше».
- **Незрелость:** ~2.5 мес, один мейнтейнер, 15 релизов за 2.5 недели, 171 open issue (в осн. краши/регрессии). Bus factor = 1.
- **Не тот scope:** граф КОДА для агента ≠ идея графа КОНТЕНТА в стиле Obsidian + pgvector для веба (см. «Веб-интерфейс — граф знаний»). Obsidian тут — лишь формат экспорта. Эту идею он НЕ закрывает.
- Безопасный режим (если щупать на pet-проекте без личных данных): code-only корпус, `--backend ollama`, `graphify-out/` в `.gitignore`.
