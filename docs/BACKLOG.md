## Единый инструментарий: доконсолидация домена в `_shared/` (не пересборка)

> Ресёрч 2026-06-27 (код + GitHub + паттерны, 3 независимых агента). Вопрос был: оставлять текущую конфигурацию или пересобирать систему «под общие рельсы». **Вывод: текущая архитектура верна, пересобирать НЕ надо. Нужно лишь доконсолидировать дрейфующие решения в `_shared/`.**

### Вердикт (совпал с трёх сторон)
1. **Канон Supabase Edge Functions:** общий код в `_shared/` + тонкие обработчики на функцию — рекомендованный паттерн; «fat functions» (мало крупных). **Вызов функции из функции по HTTP ради переиспользования логики — анти-паттерн.** «Единого core-сервиса, к которому все ходят», в каноне нет. → отдельное «ядро-сервис» строить НЕ надо. ([supabase.com/docs/guides/functions/development-tips](https://supabase.com/docs/guides/functions/development-tips))
2. **Реальные проекты (GitHub):** bot + web + MCP на одном домене строят как «общее ядро + тонкие адаптеры». Примеры: **CopilotKit** (движок + `PlatformAdapter`, адаптеры telegram/discord/slack тонкие, MCP/веб поверх) и **subbrain** (почти наш кейс: `packages/core` домен+БД, `server` веб-API, `agent/mcp` MCP-адаптер, Telegram — всё над одним core). MCP везде = «ещё один адаптер, регистрирующий те же доменные операции как тулзы».
3. **Ports & adapters + правило «когда сводить»:** ядро = домен без знания о поверхностях/инфре; двери = переводчики; зависимости смотрят внутрь. Сводить дубль **сейчас**, если это *решение* (доступ/валидация/бизнес-правило) ИЛИ копии уже разъехались. (Fowler: rule of three; YAGNI для спекулятивных абстракций.)

### Что это значит у нас
`_shared/` — это и есть доменное **ядро**; `swarm-bot` / `swarm-api` / `swarm-mcp` / `meeting-*` — **двери-адаптеры** (каждая ходит в общую БД напрямую, импортируя общий код; друг друга не вызывают). Архитектура уже индустриально-правильная — **ядро просто недозаполнено**: часть решений дублируется в дверях и уже дрейфует.

### Свести в `_shared/` сейчас (решения, которые уже разъехались)
- 🟡 **Извлечение задач** — два пути/промпта: `analyzeAndCreateTasks` (swarm-bot, богатый) vs `gptExtractTasks` (swarm-api, простой). Дубль ВНУТРИ swarm-api убран (2026-06-27: `/tasks/extract` → `gptExtractTasks`). Полная унификация бот↔api — решение-гейт (разные форма/качество + фронт-потребитель), см. секцию «Единообразие бот↔десктоп».
- 🔴 **Сохранение/ингест записи** (дедуп + классификация + эмбеддинг) — живёт в `swarm-bot/lib/storage.ts` (`saveEntry`), а `granola.ts` делает прямой `insert` в обход → один `_shared/entries/save.ts`, через который ходят ВСЕ (бот/api/granola/read-ai). (Пересекается с «Единый контракт транскрибаторов» ниже — там вход встреч; здесь общий путь сохранения любой записи.)
- 🟡 **Промпт тезисов** — дубль `GRANOLA_TEZISY_PROMPT` в `granola.ts` и `read-ai-webhook` → один `_shared/meetings/tezisy.ts`.

### Оставить в дверях (это форма, а не решение — там и должно быть)
- Telegram-разметка (`swarm-bot`), схемы MCP-инструментов (`swarm-mcp`), JSON-ответы/CORS веба (`swarm-api`), рендер тезисов во фронте (`miniapp`).

### Дисциплина вперёд (чтобы дрейф не возвращался)
Новая доменная способность → реализуется **один раз в `_shared/`**, двери только переводят вход/выход. Дверь не должна содержать бизнес-решение, которого нет в `_shared/`.

### Как делать (низкий риск, инкрементально)
По одному пункту за раз: вынести логику в `_shared/`, переключить потребителей на неё, `deno check` всех затронутых функций + смоук реального флоу каждой двери, и только потом удалять старую копию. Не блайнд-рефактор всего сразу. Каждый пункт = отдельный коммит.

## 🟡 Создание задач из чата-бота свободным текстом («добавь задачу: …»)

**Симптом:** «добавь/создай мне задачу: X» бот понимает как ПОИСК задач (`smartTaskSearch` → ответ «Задачи по запросу:»), а не как создание.

**Причина (по коду):** создание задач в боте есть только через wizard `/addtask` (`tasks/handlers.ts`) и авто-извлечение из встреч (`analyzeAndCreateTasks`). Свободнотекстового пути «создать задачу» нет — GPT-агент бота умеет искать (`get_tasks`/`smartTaskSearch`), но НЕ создавать, поэтому запрос деградирует в поиск.

**Желаемое:** распознавать намерение «создать задачу» из свободного текста («добавь/создай/поставь [мне/имя] задачу: …», «напомни …») → создавать задачу: заголовок из текста, исполнитель по умолчанию = отправитель («мне» → себе) либо резолв имени, срок/страна если указаны; подтверждение карточкой. Чётко отделять от ПОИСКА: «какие у меня задачи по Сербии?» → поиск; «добавь задачу …» → создание.

**Связь:** ложится на единый путь извлечения задач (`analyzeAndCreateTasks` vs `gptExtractTasks`) — см. «доконсолидация домена в `_shared/`» выше.

- Нет общего контракта ингеста, нет реестра источников — список `['read_ai','granola','desktop-agent']` захардкожен по местам (swarm-mcp `.in()`, статистика бота, visibility-фильтры).

**Целевой дизайн (8 шагов, инкрементально, НЕ блайнд-миграцией прод):**
1. `meetings` — единая таблица входа для ВСЕХ источников; `source` = свободный id программы (`granola`/`read_ai`/`swarm-recorder`/`otter`/…), не дефолт `desktop-agent`.
2. ## 🔴→✅ ВСЕ загрузки рекордера падали: `meeting-ingest` потеряла `--no-verify-jwt` (2026-06-30)

> Симптом (владелец, «красный уровень»): встреча «Google Meet — Jurica / Vasiliy» (60 мин) в ревью с «⚠ Не удалось обработать запись». На диске рекордера в `failed/` лежало **5 незалитых записей** (today + 29 июня), у всех `uploaded:false`, `attempts:0`.

**Root cause:** `meeting-ingest` была передеплоена БЕЗ `--no-verify-jwt` → шлюз Supabase включил gateway-verify_jwt → рекордер шлёт `Authorization: Bearer <opaque recorder-token>` (НЕ JWT) → шлюз отбивает **401 `UNAUTHORIZED_INVALID_JWT_FORMAT` ещё ДО функции**. Рекордерный `UploadQueue.drain` классифицирует не-5xx/429 как постоянный сбой → `moveToDeadLetter` БЕЗ инкремента attempts (отсюда `attempts:0` в `failed/`). Это рубило **каждую** загрузку, не только эту.

**Восстановление (без потери данных):** аудио было ЦЕЛО на диске (`~/Library/Application Support/SwarmRecorder/failed/<id>/`, mic+sys дорожки). Передеплоил `meeting-ingest --no-verify-jwt` → дозалил части напрямую в `meeting-ingest` (тот же контракт: `meeting_id` + `sys_parts`/`mic_parts` JSON-манифест + файлы; offset'ы из `afinfo`) → `202 processing` → durable-обработка → `done`, полный транскрипт 695 сегментов / 60 мин восстановлен. (Тезисы вышли «нет содержания» — англоязычная встреча + русский промпт; лечится «Переобработать».)

**Durable-фикс (чтобы не повторилось):** закрепил `verify_jwt = false` для ВСЕХ 15 функций в `supabase/config.toml` (`[functions.<name>]`). Теперь `supabase functions deploy` не зависит от ручного флага `--no-verify-jwt` и не может его молча потерять. **При деплое любой функции этого проекта флаг больше не нужен — конфиг закрепляет публичность шлюза.**

**🟡 Остаётся:** 4 другие записи 29 июня всё ещё в `failed/` на диске (короткие, 1–7 мин) — теперь, когда ingest починен, рекордер дозальёт их сам при дрейне (или вернуть `failed/→pending/`). Проверить, что они того стоят (возможно тесты).

### Дедупликация встреч Granola при нескольких участниках

### Админка — контроль трафика и расходов по инструментам
> Зафиксировано 2026-06-12 при выборе облачной транскрибации для Swarm Meetings.

С переходом на облако расходы идут **по факту использования** (OpenAI: транскрибация по минутам аудио, тезисы и эмбеддинги по токенам). Нужна видимость и контроль, чтобы не улетать по бюджету и видеть, что сколько потребляет.

**Scope:**
- **Учёт по инструменту/функции:** транскрибация (Whisper, минуты), тезисы (GPT, токены), эмбеддинги, поиск и т.д. — количество вызовов + расчётная стоимость, разбивка по периодам.
- **Разбивка по воркспейсу и пользователю** — кто/какой воркспейс сколько генерит трафика и денег.
- **Лимиты/квоты и алерты** (опц.): месячный потолок по инструменту/воркспейсу, уведомление при подходе к лимиту, мягкая остановка при превышении.
- **Переключение моделей без передеплоя** (опц.): напр. тезисы `gpt-4o` ↔ `gpt-4o-mini`, выбор модели транскрибации — из конфига/админки.

**Как считать:** логировать каждый внешний вызов (инструмент, модель, единицы — минуты/токены, расчётная стоимость, `telegram_id`, `group_id`, время) в таблицу `api_usage`; админка агрегирует. Прайс — в конфиге (per-model rates), пересчёт стоимости на лету.

**Форм-фактор:** страница в miniapp (раздел «Админ», `is_admin`) поверх swarm-api, либо суперадмин-команды. Дополняет «Админка — управление пользователями и интеграциями».

**Приоритет:** заводить вместе с запуском Swarm Meetings — облачная транскрибация = реальные деньги по факту, без учёта легко не заметить рост.

### Вывод
Единственный санкционированный путь на Team — **Owner добавляет swarm-mcp в орг-список**, а это требует **OAuth на нашем сервере**. Гейт «нежелательных» обязан жить **внутри swarm-mcp, в шаге `authorize`**: пропускаем только тех, чья личность есть в `allowed_users`, остальным членам орга — отказ.

```
Claude (орг-коннектор) → authorize на swarm-mcp
  → редирект на R-5 Telegram-login страницу (уже есть)
  → знаем telegram_id → проверяем allowed_users → нет → отказ
  → минтим MCP access-token, привязанный к telegram_id
swarm-mcp валидирует OAuth-токен (вместо/поверх текущего smcp_)
```
`allowed_users` (ключ `telegram_id`) ложится идеально, маппинг email↔telegram не нужен.

## Общая база между воркспейсами (cross-workspace shared entries)

> Контекст собран 2026-06-12 (brainstorm-сессия, припарковано до появления необходимости).
> Идея: часть записей — заметки-инструкции вида «добавь в базу: инструкция по ТВ бордам *ссылка*» — должна быть видна **во всех воркспейсах**, а не только в своём.

### Решения, принятые в обсуждении
- **Триггер лингвистический:** «добавь в **общую** базу» = на все воркспейсы; «добавь в базу» (дефолт) = свой воркспейс. Тот же паттерн, что у `save_private` («личное», «только для меня»), только в другую сторону. Итоговая шкала видимости: **личное → воркспейс (дефолт) → общая**.
- **Модель данных:** `ADD COLUMN entries.is_shared boolean DEFAULT false` (имя уточнить — возможно `is_global`, см. конфликт нейминга ниже). `group_id` остаётся «родным» воркспейсом записи. Миграция данных не нужна — существующие записи не трогаются.
- **Ретроактивный шеринг тривиален:** любую старую запись можно сделать общей одним `UPDATE ... SET is_shared = true` по id (или кнопкой «опубликовать» постфактум). Что нельзя автоматизировать — *решить*, какие старые записи общие: ручная разметка либо разовый LLM-проход по заметкам/ссылкам с подтверждением.

### Открытый вопрос (обсуждение прервано здесь)
- **Права на общую запись для чужого воркспейса.** Склонялись к **read-only** (мутации — только владелец + суперадмин, как текущий `requireOwner`), но окончательно не утвердили. Альтернативы: вики-режим (править могут все, удалять — владелец) / полный доступ.

### Точки интеграции (разведаны)
- **Фильтры видимости** — три места, где `.eq("group_id", groupId)` меняется на `.or(group_id.eq.X, is_shared.eq.true)`:
  - `swarm-api/entries-guard.ts` — `getEntrySecure` (layer 1) + `buildEntriesQuery`;
  - `_shared/search.ts` — `matchEntries` (фильтр поверх RPC `match_entries`);
  - листинги в swarm-bot (`lib/storage.ts`).
- **Regex fast-path** `swarm-bot/index.ts` (~198): «добавь в общую базу» сейчас **НЕ** матчится (`в\s+базу` ломается словом между «в» и «базу») и уйдёт в GPT как вопрос — нужен отдельный паттерн до общего.
- **GPT-тулзы** `swarm-bot/handlers/knowledge.ts`: ⚠️ конфликт нейминга — существующий тул `save_shared` означает «общий **внутри** воркспейса». Новое понятие развести как `global`/`is_global` либо переименовать scope-параметром (`scope: workspace | global | private`).
- **MCP `add_knowledge`** — опциональный параметр + строчка в инструкцию Claude Desktop («добавь в общую базу» → ставить флаг).
- **MCP `update_entry`** — тоже принимает флаг: обязательный сценарий — **точечный перевод существующих записей в глобал по запросу через Claude** («сделай запись про ТВ борды общей» → `search_knowledge` находит id → `update_entry` ставит флаг). Права: владелец/суперадмин.

## ~~Таксономия записей — встреча vs заметка~~ ✅ реализовано 2026-06-17

Связано с памятью `project-taxonomy-tasks-notes-types`. Поводом стал баг правки записей из чата: «замени ссылку в форме … стандартов» тащило транскрипты встреч — фильтры по источнику текли.

### Диагноз (по факту в БД, 2026-06-17)
- **`source` засорён свободным текстом**: помимо контролируемых (`telegram/granola/read_ai/link/note/voice/digest`) лежат строки-заголовки и имена файлов — `«Болгария — встреча 14.05.2026»`, `«20cm_Pizzas_Presentation.pptx»`, `«transcript_хорватия_арина…»`, `«справка / инструкция пользователя»`. → любой фильтр «это встреча?» по `source` течёт.
- **`entry_type` размыт (5 типов)**: ссылки и как `document` (24), и как `note` (21); Granola и `meeting` (37), и `note` (15); плюс `summary` (10) и `transcript` (8).
- **`meeting_id` почти не проставлен** (1 запись) → связка встреча↔задачи едва работает.

### Целевая модель — ДВА типа (решение: «только Встреча/Заметка»)
- **Встреча** — `entry_type='meeting'`: транскрипт/тезисы созвона. Источники: granola, read_ai, recorder. Раздел «Встречи».
- **Заметка** — `entry_type='note'`: всё остальное знание (текст, данные, пароль, ссылка, файл). Раздел «База».
- **Подвиды заметки — фасеты через `metadata`, НЕ отдельные типы:** ссылка = `metadata.url`, файл = `metadata.file_name`/`file_type`. UI-тег рисуется по фасету (встреча/ссылка/файл/заметка).
- **`source` = канал** (контролируемый enum: `telegram · web · granola · read_ai · recorder · upload · mcp`). Свободный текст (заголовок встречи, имя файла) → в `metadata.title`/`metadata.file_name`, никогда не в `source`.
- Граница встреча↔заметка проводится **по `entry_type`, не по источнику**.

1. ✅ **Бэкфилл-миграция** `entries`: `entry_type` → {meeting, note} (файлы по расширению → note даже при transcript/summary; granola/read_ai/recorder/«встреча…» → meeting). Исходный тип в `metadata.legacy_entry_type`. + **CHECK-инвариант** `entry_type IN (meeting, note)` (миграции `20260617110000`, `20260617140000`).
2. ✅ **Write-пути** ставят только meeting|note (с клампом): классификатор `storage.ts`, granola→meeting, read-ai→meeting, meeting-claim личные пометки→note, swarm-api upload→note/publish→meeting/POST extract, swarm-mcp промпты+клампы.
