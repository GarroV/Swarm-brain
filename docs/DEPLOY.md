**Тестовый стек на MUSPELHEIM** (с 25.09.2026, решение владельца: регулярные стенды — на сервере, на Маке только временные, канон `dotfiles/claude/decisions/2026-09-25-stendy-na-muspelheim.md`). На нём идут тесты базы всех сессий Swarm. `./scripts/with-local-db` сперва ищет стек на своей машине (так работает CI), а если его нет — поднимает туннель к серверу; `SWARM_TEST_STAND=local` отключает поход на сервер. Ключи стандартные для `supabase start`, поэтому порты 54320–54329 закрыты для входящих правилом брандмауэра «Swarm test stand: no external access» — стек доступен только через туннель. Запуск на сервере — без studio, аналитики, vector и pg_meta: для тестов не нужны, а ядра ели: `supabase start -x 'studio,logflare,vector,postgres-meta,imgproxy'` — в PowerShell список **в кавычках**, иначе он рассыпается на отдельные аргументы и исключение молча не срабатывает. Схема на сервере — миграции `main`; чтобы прогнать тесты на миграциях своей ветки: `./scripts/with-local-db sh -c 'supabase db reset --db-url "$SUPABASE_DB_URL"'` (стек общий — сбрасывая, сбрасываешь его всем сессиям, как и раньше с общим стеком на Маке).

Staging использует **демо-ключи** Supabase (ANON/SERVICE/JWT из `.env.example`) — ок, т.к. контур приватный (только tailnet, личное использование). Порты сдвинуты (kong `8020`, БД `5433`), чтобы не конфликтовать с n8n/template-postgres на MUSPELHEIM.

**Пароль staging-БД — НЕ в git.** Makefile читает его из `~/.swarm/staging_pgpw` (git-ignored, вне репо). Инициализация на своей машине: `mkdir -p ~/.swarm && printf 'your-super-secret-and-long-postgres-password' > ~/.swarm/staging_pgpw && chmod 600 ~/.swarm/staging_pgpw` (дефолт = демо-пароль Supabase; при желании поставь свой на staging-БД и обнови файл).

## Поток по поверхностям

| Поверхность | Пред-прод |
|---|---|
| Edge-функции | `supabase functions serve` локально → `make staging-sync-functions` + `make smoke-staging` → прод + `make smoke-prod` |
| БД / миграции | `supabase db reset` локально (ловит SQL-поломки) → `supabase db push --linked` на прод. Подробности — раздел «Миграции на прод» ниже |
| Бот / MCP | локалка + curl синтетического апдейта; strict/тулзы — `make smoke-staging` |
| Web (miniapp) | CF preview на ветку (авто) → мёрж в `main` |
| Рекордер | локал-сборка → тег `recorder-build-N` → **заливка zip в Storage `swarm_drive/recorder/`** → `LATEST_BUILD`-гейт (см. `recorder/README.md`) |

## Рабочий цикл (edge + миграция)

```bash
# edge-функция
supabase functions serve <fn>            # 1. локально против локальной БД
#    смоук локально (curl localhost)      # 2. вижу поведение
make staging-sync-functions              # 3. залить на staging + рестарт edge-runtime
make smoke-staging                       # 4. смоук на staging (по tailnet)
supabase functions deploy <fn> --no-verify-jwt   # 5. прод
make smoke-prod                          # 6. смоук на проде

# миграция БД
supabase db reset                        # 1. накат ВСЕХ миграций на чистую локальную БД (ловит SQL-поломки)
supabase db push --linked --dry-run      # 2. что уедет на прод (ничего не меняет)
supabase db push --linked                # 3. накат на прод — В ОКНО РАСКАТКИ и по «да» владельца
```

## Миграции на прод

**Штатный путь — кнопка «Накат миграций БД (руками)»** (`.github/workflows/deploy-migrations.yml`,
запуск через Actions или `gh workflow run deploy-migrations.yml -f dry_run=true`). Внутри тот же
`supabase db push --linked`, но токеном из секретов репозитория.

**Локально `supabase db push --linked` не проходит** (проверено 19.09.2026): CLI просит Platform API
завести временную login-роль, личный токен отвечает `403 does not have the necessary privileges`,
после чего CLI требует `SUPABASE_DB_PASSWORD`, которого в рабочем окружении нет. Тем же токеном
`supabase projects list` отвечает нормально, а `projects api-keys` — тоже 403.

**Флаг `include_all`** нужен, когда файл миграции старше последней применённой на проде (ветка
пролежала дольше соседних): без него CLI отказывается вставлять её «в середину» истории и выходит
с кодом 1. Сухой прогон (`dry_run=true`, по умолчанию) печатает список «Would push these migrations».

Правила вокруг наката:

- Файл миграции пишем **идемпотентным** (`IF NOT EXISTS` / `IF EXISTS`): накат мог частично
  доехать, и повтор не должен падать.
- Перед продом — `supabase db reset` на локальном контуре. Staging на MUSPELHEIM погашен
  06.08.2026, поэтому пред-прод сейчас = local → прод.
- Накат = раскатка: только по явному «да» владельца и в окно 23:00–06:59 (см. `CLAUDE.md` §5).
- Скриптам, которые ходят в Storage или базу напрямую (например `scripts/storage-migrate.ts`),
  нужен `SUPABASE_SERVICE_ROLE_KEY`. В секретах репозитория его нет по решению 2026-08-28 (не
  класть service-role в публичный репозиторий), поэтому такие шаги запускает владелец локально.
- Версия файла — **ровно 14 цифр** (`YYYYMMDDHHMMSS`). Восьмизначные версии вида `20260602`
  ломают CLI, если рядом есть версия с тем же префиксом: по именам файлов `20260602000001_…`
  сортируется раньше `20260602_…` (цифра `0` меньше `_`), а по версиям — позже, и push объявляет
  прод-версию потерянной. На этом стояли #16/#101/#158.
- Две миграции с одинаковым префиксом-версией — тоже мина: версия = префикс, пометка одной
  скроет другую. Проверка перед коммитом: ни одна версия не должна быть префиксом другой.

### История была разъехавшейся до 05.09.2026 (issues #16, #101, #158)

Полтора месяца `supabase_migrations.schema_migrations` и папка `supabase/migrations/` жили как две
записи одной и той же истории: изменение катили через дашборд (он ставил свою версию-таймстамп), а
в репозиторий клали файл со своей. К 05.09 расхождение было 44 файла, которых прод «не знал», и 21
прод-версия без файла — при том, что **схема у них одна и та же**.

Выровняли 05.09.2026 после сверки каждой миграции с реальной схемой прода (35 подтверждены наличием
объектов, 7 по эффекту, 2 объяснены; частично применённых — ноль): 44 файла помечены применёнными,
21 дублирующая запись дашборда удалена, версия `20260602` переименована в `20260602000000`.
Схему не трогали. Результат — `db push --dry-run` говорит «Remote database is up to date».

## Объявление и проверка «кто в системе» (с 27.08.2026)

Раскатка веба пересобирает Cloudflare Pages, после чего service worker сам перезагружает открытые
страницы. Чтобы никто не поймал reload посреди правки, порядок такой
(канон — [decisions/2026-08-27-deploy-notice.md](decisions/2026-08-27-deploy-notice.md)):

```bash
make who               # кто в проде прямо сейчас (можно и без раскатки)
make notice MIN=15     # объявить: в вебе появляется плашка с отсчётом (ПРАВКА ПРОД-ДАННЫХ)
#   … ждём 15 минут …
make deploy            # сам проверит активность, раскатает и снимет объявление
make notice-off        # снять объявление вручную, если раскатку отменили
```

**Без прав записи в базу — кнопка в Actions** «Плашка и заморозка (руками)» (`.github/workflows/notice.yml`). `make notice` пишет в базу личным токеном CLI, а у него права `database_write` нет, и расширять его не будем: токен нужен другим проектам (решение владельца 2026-09-25). Кнопка ходит в базу ключом из секретов репозитория, как накат миграций.

```bash
gh workflow run notice.yml -f action=notice -f minutes=30 \
  -f text_ru="Сегодня 16:00–17:00 МСК — обновление SWARM" -f text_en="Today 16:00–17:00 MSK — SWARM update"
gh workflow run notice.yml -f action=notice-off
gh workflow run notice.yml -f action=freeze -f minutes=40     # после вливания заморозки (#507)
gh workflow run notice.yml -f action=unfreeze
```

Свой текст плашки (`text_ru`, `text_en`) показывается вместо «Обновление через N мин». Кнопка тоже правит прод-данные, жать её — только по «да» владельца на раскатку.

## Код не уезжает вперёд схемы (с 25.09.2026)

`deploy-window.sh` перед раскаткой функций сверяет миграции релиза с применёнными на проде
(Management API, тем же `SUPABASE_ACCESS_TOKEN`, которым деплоятся функции) и **останавливает
раскатку**, если в релизе есть неприменённые: функция, которой нужна новая колонка, ответила бы
400 и положила раздел у всей команды до утра. `FORCE=1` этот гейт НЕ обходит — он про окно и про
людей в системе, а не про готовность базы.

Если проверить нечем (нет токена, API не ответил), раскатка тоже останавливается — это «проверка
не выполнилась», а не «всё хорошо». Осознанный обход, когда схему проверили руками:

```bash
MIGRATIONS_OK=1 ./scripts/deploy-window.sh go
```

Порядок для релиза с миграцией: сначала накатить миграции (Actions → «Миграции БД»), потом
раскатывать функции. Почему это понадобилось — [issue #509](https://github.com/GarroV/Swarm-brain/issues/509):
мину взрывала чужая раскатка, ближайший ночной прогон по любому другому PR.

## Заморозка на время работ (с 25.09.2026)

Плашка выше ПРЕДУПРЕЖДАЕТ, но ничего не запрещает. Для переезда, где правка во время работ
либо потеряется, либо ляжет поверх мигрирующей схемы, есть отдельный режим: веб показывает
полноэкранную заглушку «идут работы» на двух языках, API отвечает `503` + `Retry-After` на
любое ИЗМЕНЕНИЕ. Чтение остаётся: пустой экран пугает сильнее честной заглушки. Владелец
проходит сквозь заморозку — иначе он не проверит раскатку и не снимет режим через продукт.
Канон — [decisions/2026-09-25-maintenance-freeze.md](decisions/2026-09-25-maintenance-freeze.md).

```bash
make freeze MIN=30     # заморозить (ПРАВКА ПРОД-ДАННЫХ — только по «да» владельца)
make freeze-status     # заморожено ли сейчас и до какого времени
#   … раскатка, проверка на реальном окружении …
make unfreeze          # снять раньше срока; по сроку режим гаснет и сам
```

Срок обязателен, потолок — 180 минут: забытая заморозка это лежащий продукт, поэтому режим
гаснет сам, даже если скрипт упал, сессия оборвалась, а человек ушёл спать. Ночная автоматика
заморозку НЕ включает — ночью никто не работает, и останавливать некого.

`make deploy` отказывается катить, если:

- **идёт запись или обработка встречи** — жёсткий стоп, `FORCE=1` НЕ обходит (оборванный кусок
  аудио это потерянная встреча);
- **кто-то правил задачи/записи/комментарии за последние 10 минут** — предупреждение, обходится
  `FORCE=1` осознанно;
- **проверить активность нечем** (нет привязки к проду или запрос к базе не прошёл) — стоп с
  ОТДЕЛЬНЫМ текстом: про запись встречи в этом случае ничего не известно. Так всегда выглядит
  запуск из CI — прод-ключ там не держим (решение 2026-08-28), поэтому кнопку «Раскатка функций»
  жмут, проверив активность руками и поставив «Пропустить проверку кто в проде». До 21.09.2026
  этот случай выдавался за «идёт запись» и кнопка не работала вовсе (issue #429);
- **время вне окна** — как и раньше.

Плашка гаснет сама по `until` (заложено в данные), поэтому упавший скрипт не оставит её висеть.

## Команды (`make help`)
- `make smoke-staging` / `make smoke-prod` — смоук edge-функций (`scripts/smoke.sh`, один и тот же набор проверок для любого контура).
- `make staging-sync-functions` — tar `supabase/functions` → scp на MUSPELHEIM → распаковка в `volumes/functions/` → рестарт `supabase-edge-functions`.
- `make staging-migrate FILE=…` — накатить SQL-файл на staging-БД (`ON_ERROR_STOP`).
- `make staging-psql` — psql в staging-БД (стдин). `make staging-ps/-up/-down` — статус/подъём/останов стека.
