# Регулярные задачи и единый флоу быстрого создания

**Дата:** 2026-08-27 · **Статус:** принято, реализовано · **Решения владельца, не технические детали**

> ⛔ Формулировки ниже — выбор владельца из предложенных вариантов. Менять только новым его решением.

## Повод

Владелец, глядя на доску проектов:

> «1. плюсы в проектах добавляют задачу без привязки к пользователю. разве у нас не единый флоу
> создания задач во всех местах?
> 2. у задач нужно задать настройку цикличности. я думаю что чекбок, и после галочки можно
> настроить каждый день, каждый день недели (в зависимости от того дня что был выбран),
> каждую эту дату ежемесячно. под это все вывести отдельный раздел "регулярные задачи" куда
> эти задачи будут сами уходить»

## Что было не так с пунктом 1

Единого флоу не было — три точки создания задачи в вебе с разными дефолтами:

| Точка | Исполнитель до фикса |
|---|---|
| `TaskModal` (полная форма) | из селекта, дефолт «Общие (вся команда)» |
| `useReminderTasks.quickAdd` (список в духе Reminders) | **я** |
| `SprintBoard` (кнопка «+» в колонках и проектах) | **никакой** |

Автор (`created_by_telegram_id`) сервер ставил всегда, так что «без привязки» означало «без
исполнителя». Последствие ощутимое: задача, созданная плюсом, по правилу линз попадала в
«Команда» (общая = не приватная и без исполнителя) и **исчезала из «Моих»**.

## Решения владельца

| Вопрос | Ответ (27.08.2026) |
|---|---|
| Дефолт быстрого создания | **«Назначать на меня (как в Reminders)»** — единое правило для всех точек «+»; общую задачу делаешь осознанно, сняв исполнителя в полной форме |
| Модель регулярной задачи | **«Одна задача катится вперёд»** — как Todoist/Vikunja: отметил готовой → срок прыгает на следующее вхождение, статус снова «открыто». Шаблоны с экземплярами на каждое вхождение отклонены |
| Раздел «Регулярные» | **«Если есть хоть одна регулярная задача, то автоматом создаётся смарт-список таких задач, куда эти задачи привязываются. В других списках они могут быть если надо, но в списке регулярных это прям необходимо. Если задач таких нет, то список скрывается»** |
| Отсчёт следующего вхождения | **«От графика — ближайший будущий вторник»** — перебираем вхождения от прежнего срока, перескакивая прошедшие. «Отчёт по средам» остаётся по средам, сколько бы раз ни опоздали |

## Следствия, о которых стоит помнить

- **«+» в колонке проекта больше не создаёт общую задачу.** Она сразу твоя. Это осознанная смена
  поведения, а не регресс.
- **Истории выполнений у регулярной задачи нет** — это цена выбранной модели: строка одна, в
  «Готовых» она не появляется. След оставляем в уже существующей `task_history`
  (`note: «цикл закрыт, следующий срок …»`), отдельной таблицы журнала не заводим.
- **Цикличность требует срока.** День недели и число месяца не хранятся отдельно — они и есть
  `due_date`. Без срока считать не от чего: чекбокс задисейблен, API отбивает 400, снять срок у
  регулярной задачи нельзя без снятия цикличности.
- **Якорь числа месяца (`recur_anchor_dom`) пересчитывается только когда человек тронул срок или
  частоту.** `TaskModal` шлёт `recur_freq` и `due_date` при каждом автосейве, поэтому пересчёт «по
  любому запросу» у задачи «31-го числа», стоящей после зажатия на 28 февраля, молча увёл бы её с
  31-го на 28-е — навсегда.
- **Перекат живёт в `updateTask`** (`_shared/tasks/db.ts`) — единственной точке записи статуса
  задач. Веб, бот и MCP получают поведение автоматически, обойти его нельзя.

## Решения, принятые мной (не владельцем) — можно оспорить

| Решение | Причина |
|---|---|
| Новый цикл начинается со статуса «Открыто» | Задача, закрытая из «В работе», иначе навсегда осталась бы в работе |
| `start_date` и `remind_date` сдвигаются на ту же дельту, что срок | Иначе пинг остался бы в прошлом и молча не сработал, а начало оказалось бы позже срока |
| При включении галочки предвыбирается «раз в неделю» | Самая частая рабочая регулярность; переключается одним нажатием |
| Русская подпись — дательный падеж («по средам»), а не «каждый \<день\>» | «Каждый среда»/«каждый суббота» ломается на роде |
