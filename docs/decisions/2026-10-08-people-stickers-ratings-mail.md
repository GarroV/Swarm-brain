## 1. Люди без аккаунта и соисполнители

**Модель: справочник людей воркспейса.** Аккаунт — это человек, у которого есть вход; человек без
входа — та же сущность без `telegram_id`.

- **Вход — сама задача:** в поле «Соисполнители» (и «Ответственный») подсказка из справочника, а если
  человека нет — «+ Добавить „Имя“» (имя, по желанию почта) прямо там. Человек сразу попадает в
  справочник и дальше подставляется из списка. Отдельный экран заведения не обязателен.
- Таблица `people`: `id uuid`, `group_id`, `display_name`, `emails text[]` (нижний регистр),
  `telegram_id bigint NULL` (связь с аккаунтом), `source` (`account | calendar | manual | transcript`),
  `created_by`, `created_at`, `archived_at` (ничего не удаляем — [архивация](../../CLAUDE.md)).
  Уникальность e-mail внутри воркспейса.
- **Как люди появляются:** (а) у каждого `allowed_users` — своя запись (бэкфилл миграцией); (б) участник
  встречи при публикации — по e-mail, если такого ещё нет (переговорки отсекаются, как в
  `meeting-access.ts`); (в) вручную в «Команде» — «+ Человек без входа»; (г) имя из транскрипта
  вместо метки на строке (меняет решение 2026-08-28 — **нужно «да» владельца**).
- **Связывание:** человек вошёл через Google с e-mail, который уже есть в `people.emails`, → запись
  получает `telegram_id`, его задачи сразу видны в «Мои задачи». Дубли — «Объединить» у админа
  (+ `user_profiles.name_aliases` уже есть).
- **Роли на задаче** (терминология: **«Ответственный»** — один, отвечает за результат; **«Соисполнители»**
  — сколько угодно, делают часть): новые колонки `tasks.responsible_person_id uuid`,
  `tasks.coassignee_person_ids uuid[]`. Старые `assignee_telegram_ids`/`assignees` живут до конца
  перехода — два шага по правилу миграций (сперва код пишет в оба, потом читает новое, потом снос).
- **Видимость и права:** задачи человека без входа видят все в воркспейсе (как сейчас обычные).
  «Мои задачи» = я ответственный **или** соисполнитель. Отметить выполненной за человека без входа
  может автор задачи или админ.
- **Уведомлений таким людям нет** — канала нет; и любые новые сообщения людям — только по «да»
  владельца на текст, адресатов и условие.
- **Потребители, которые надо перевести на `person_id`:** аналитика спринта (сейчас по имени),
  `get_task_stats` (по имени), выбор исполнителя в `TaskModal` и боте, разбор задач из встреч.

**Карточка встречи** (вопрос коллеги «клик по 1:1»): боковая панель встречи из раздела «Встречи»,
с главной — переход туда. Блоки: итоги прошлой встречи с тем же составом (≥ половины участников
совпадает, берём тезисы); открытые задачи, где ответственный/соисполнитель ∈ участники; для страновой
встречи (метка рынка) — РС/РКО этой страны. Опирается на `people` — делается после п. 1.

## 2. Стикеры-задания

- Таблицы: `board_stickers` (`id`, `group_id`, `kind task|notice`, `title`, `body`, `due_at`,
  `tone` цвет, `link` куда ведёт кнопка, рекуррентность теми же RRULE-колонками, `created_by`,
  `archived_at`) и `board_sticker_people` (`sticker_id`, `person_id`, `task_id`).
- **Завести стикер-задание** (админ): заголовок, описание, срок, кому (люди/«все в воркспейсе»/страна),
  ссылка. На сохранение **каждому адресату создаётся задача**: ответственный — он, срок, описание,
  ссылка на стикер, метка «Доска». Выполнение стикера у человека = статус его задачи.
  Повторяющийся стикер («каждый месяц») — повторяются задачи, стикер показывает текущий круг.
- **Объявление** (`notice`) — без задач, кнопка «Понятно» пишет отметку прочтения.
- **Вид:** клик по стикеру → он разворачивается (общая анимация «стикер → карточка»: FLIP через
  transform, без смены вёрстки ленты; `prefers-reduced-motion` — без анимации). Внутри: описание, срок,
  прогресс «5 / 8», список людей с ✓ / ○ и сроком, кнопка действия. Свой стикер выполнил — на ленте
  он зачёркнут и уезжает в конец; все выполнили или срок прошёл — уходит в архив.
- **Живые стикеры** («Вычитай встречи», «Разбери просрочку») остаются вычисляемыми, без таблицы.
- Создание задач **ничего не рассылает** (уведомлений о назначении нет). Напоминание в боте — отдельно
  и только по «да» владельца.

## 3. Загрузка рейтингов РС и РКО

- **Без нейросети, скриптом по расписанию раз в 2 дня:** GitHub Actions по образцу `market-collect.yml`
  (cron `0 3 */2 * *`) → скрипт качает CSV листов → разбирает → шлёт в функцию приёма (по образцу
  `market-ingest`, секрет приёма). Ссылки листов — секреты Actions, не код.
- **Разбор терпимый, но громкий:** подписи волн нормализуются («Март-1» = «Март 1»), запятая → точка,
  пустые ячейки — нет данных. Если шапка не узнана, страна/пиццерия не нашлась в справочнике или
  значение вне 0–100 — прогон **падает** с понятной причиной (письмо Actions владельцу), а не пишет мусор.
  Отрицательный прогон на испорченной копии листа — в тестах.
- Таблица `quality_scores`: `kind rs|rko`, `country`, `pizzeria NULL`, `period_start date`,
  `period_label`, `score numeric`, `imported_at`; уникальность по (kind, country, pizzeria, period_start).
  Виджеты главной читают отсюда вместо образца; плашка «образец данных» снимается.
- **Открыто:** единые пороги (РС 90 против 92, РКО 94.6 против шкалы 96/90/80) — решить до снятия
  плашки. В листе РКО есть строки по ответственным людям — пригодится для аналитики по человеку.

## 4. OKR и таблицы Вики

- **OKR** (Objectives and Key Results — цели на период и измеримые ключевые результаты) — **внутренняя
  таблица нашей команды**: команда сама ставит цели, согласует и раз в месяц вносит факт. Отсюда стикер
  «Заполни OKR» с прошлым процентом. Таблица своя — привязываемся как хотим; что именно показывать —
  решить на созвоне команды.
- **Вика ведёт рейтинги РС и РКО** (таблицы из п. 3). Владелец спросил её, как долго и в каком виде
  таблицы будут вестись и можно ли к ним жёстко привязываться. От ответа зависит, насколько хрупким
  можно позволить себе разбор в п. 3.

## 5. Аналитика по человеку — критично и варианты

Базовые числа **уже есть** в «Статистике»; новая страница с теми же счётчиками ничего не даст. Риски,
которые надо решить до вёрстки: (а) **ощущение слежки** — рейтинги людей друг против друга убивают
честные сроки; (б) **кривые сроки** — половина задач без срока или со сроком «на глаз», «доля в срок» врёт;
(в) **исполнитель по имени** — пока не сделан п. 1, у людей без входа аналитики нет вообще.

Предложение — экран отвечает на вопрос **«что у меня горит и выполняю ли я обещанное»**:
1. **Обещания → факт:** задачи, взятые на встречах (источник — встреча), сколько закрыто и сколько висит
   дольше двух недель. Это то, о чём спрашивают на 1:1.
2. **Нагрузка по горизонту:** просрочено / неделя / месяц / без срока — без сравнения с коллегами.
3. **Застрявшее:** «в работе» без движения N дней (история задач пишется с #286).
4. **Здоровье моих проектов** («в срок / есть риск / отстаёт»): вычисляется по доле просроченного и
   ближайшим срокам открытых задач, с ручной правкой ответственным. ⚠️ Проекты — защищённый раздел:
   делать только по отдельной явной просьбе владельца про этот участок.
- **Видимость — общая** (решение владельца 08.10: «аналитика общая, нечего скрывать»): каждый видит
  всех. Ранжирования «кто лучше» всё равно не рисуем — показываем каждого против его собственных
  обещаний, а не против коллег.
- Обсудить на созвоне: нужны ли сроки обязательными, что считать «риском».

## 6. Плитка «Почта»

- **Отбор — правилами, смысл — дешёвой моделью.** Какие цепочки показывать, решают правила (без
  нейросети): участник, длина, давность, новое письмо, «не следить». Модель нужна только на то, чего
  правилами не сделать: одна строка «что нового» по последнему письму и «касается ли это меня» (ко мне
  обращаются / спрашивают / я в «Кому», а не в копии). Модель — самая дешёвая актуальная
  (на 08.10.2026 `gpt-6-luna`, $0.10 / $0.50 за 1M токенов): ~1,5k токенов на письмо ≈ $0.0002;
  50 писем в день × 10 человек ≈ **$0.1 в день**. Нужен доступ к телу письма — scope `gmail.readonly`
  (а не `gmail.metadata`).
- **Какие цепочки:** где человек участник, ≥ 4 писем и тянется ≥ 3 дней, и пришло новое с момента
  последнего просмотра. Порог — настройка. На плитке: тема, «новое от …», давность, ссылка «Открыть в
  Gmail» (`mail.google.com/…#all/<thread id>`), кнопка **«Не следить»** — цепочка в
  `mail_thread_mutes(person, thread_id)`, система её больше не показывает.
- Хранится только id цепочки, тема, дата последнего письма, отметки «видел/не следить» — у самого
  человека, никому больше не видно. Опрос — при открытии главной (с кэшем 15 мин), не фоном.
- **Цена:** новый scope = каждый коллега один раз заново даёт согласие Google. `gmail.metadata` —
  ограниченный (restricted) scope: для внешнего OAuth-приложения нужна проверка Google; для приложения
  с типом **Internal** внутри домена организации — нет. Владелец считает, что приложение внутреннее —
  **проверить в Google Cloud Console (OAuth consent screen → User type) до начала.**
- Тело письма уходит в OpenAI: только последнее письмо цепочки, только у тех, кто включил плитку, и
  не хранится — в базе остаётся одна строка «что нового».
- Задачи из почты в продукте не строим (решение владельца): путь «Claude разбирает почту → `add_task`
  через MCP» уже работает.

## 7. Модели OpenAI — пересмотр (08.10.2026)

Расход за 05–08.10 (журнал `model_usage`): **≈ $14.6 за 3,5 дня, из них 92% — расшифровка `whisper-1`**
(37 ч аудио), тезисы `gpt-5.6-terra` ≈ 7%, остальное (`gpt-4o-mini`, эмбеддинги) — копейки.
Цены на 08.10 (developers.openai.com/api/docs/pricing; 07.10 вышел GPT-6 со снижением цен):

| Где | Сейчас | Кандидат | Деньги | Риск |
|---|---|---|---|---|
| Расшифровка | `whisper-1` $0.006/мин | `gpt-4o-mini-transcribe` $0.003/мин | **−50% от 92% счёта** | качество русского на наших записях — сравнить на 5 встречах |
| Тишина в дорожке | платим за неё (#376) | обрезать тишину до отправки | ещё до −40% расшифровки | технический, без качества |
| Тезисы | `gpt-5.6-terra` $2/$12 | `gpt-6-sol` $2/$10 | чуть дешевле | качество — сухой прогон по правилам [проверки тезисов] |
| Мелкие (задачи, метки, бот) | `gpt-4o-mini` $0.15/$0.60 | `gpt-6-luna` $0.10/$0.50 | дешевле | умнее; сменить с проверкой извлечения задач |
| Эмбеддинги | `text-embedding-3-small` | без изменений | — | смена = переиндексация, решено не трогать |

Главный рычаг — расшифровка, а не «умная» модель: пара «mini-transcribe + обрезка тишины» снимает
больше половины всего счёта. Сторонние бенчмарки GPT-6 Luna против 5.6 Terra (gradually.ai и т. п.)
показывают близкое качество, но им не верим — решаем прогоном на своих встречах.
