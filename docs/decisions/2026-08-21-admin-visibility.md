# Что админ видит у сотрудников — решение владельца

**Дата:** 2026-08-21 · **Статус:** принято, действует · **Решение владельца, не техническая деталь**

**Подтверждено и уточнено владельцем 05.09.2026** — дословно:

> «личное пространство вообще должно быть неприкосновенно ни при каких действиях»

и, на прямой вопрос о противоречии с оверсайтом задач:

> «админ имеет доступ к задачам пользователя. это сделано специально для рабочего процесса. а вот транскрибации со встреч из личной базы — это неприкосновенность»

То есть граница проходит **по типу содержимого, а не по роли**: задачи — рабочий процесс, руководитель их видит; транскрипт разговора из личного хранилища — не видит никто, включая админа. Правило 2026-08-21 остаётся в силе без изменений; эта запись нужна, чтобы третья попытка «починить» оверсайт задач упиралась в свежую дату.

**Проверено по коду 05.09.2026** (сплошной обход всех обращений к личным сущностям):

| Поверхность | Оверсайт админа | Чем закрыто |
|---|---|---|
| Задачи | **есть, намеренно** | `canViewTask` / `canMutateTask` (`_shared/tasks/access.ts`) |
| Записи, включая опубликованные встречи | нет | `_shared/entries/access.ts` (тест на отсутствие `isAdmin` в коде), `swarm-api/entries-guard.ts` |
| Черновики встреч с транскриптом | нет | список — `recorders contains me`; деталь — `canAccessDraftMeeting`, куда `isAdmin` передаётся и **намеренно игнорируется** |
| Проекты и подпроекты | нет | `canViewProject` (`_shared/tasks/project-access.ts`) |

Тем же обходом найдено и закрыто нарушение: обработчик встреч в боте читал и правил запись по `id + group_id` без проверки приватности — чужую личную встречу можно было выгрузить файлом в Telegram, переписать ей рынки, название и дату (#60, раскатано 05.09.2026). Закреплено детектором `swarm-bot/handlers/meetings-access.test.ts`.

> ⛔ **Не менять без явного решения владельца.** Это правило уже пытались «починить» дважды, каждый раз приняв его за недосмотр. Если код кажется дырой — сначала читать этот файл, потом спрашивать, и только потом трогать.

## Контекст

В системе есть два разных вопроса, которые легко слить в один и сломать:

1. Должен ли админ видеть **личное содержимое** — записи, встречи, приватные проекты? — **Нет.**
2. Должен ли руководитель видеть **работу сотрудника** — его задачи? — **Да, это смысл продукта.**

Раньше в коде стояло только слово «намеренно» без причины и без пометки, что это решение владельца. Из-за этого 21.08.2026 оверсайт по задачам сняли целиком, приняв за забытый обход, и его пришлось возвращать.

## Модель задач (как её понимает владелец)

- **Задача с назначенным исполнителем — личная** задача этого сотрудника.
- **Задача без исполнителя — общая**, её видит вся команда.
- **Руководитель специально может смотреть задачи сотрудников** — чтобы понимать, что у человека происходит, и давать обратную связь. Это функция, а не утечка.

## Решение

| Что | Видит ли админ чужое | Как это в коде |
|---|---|---|
| **Задачи** (в т.ч. личные) | **Да** — осознанный оверсайт | `canViewTask`/`canMutateTask`/`taskAccessError` (`_shared/tasks/access.ts`) принимают `isAdmin`; `listTasks` (`_shared/tasks/db.ts`) снимает фильтр приватности для админа |
| **Записи** | Нет | `swarm-api/entries-guard.ts` про админа не знает вовсе (решение 2026-08-07, issue #15) |
| **Встречи** | Нет. Черновик на вычитке видит только записавший | `entries-guard.ts`, `_shared/meeting-access.ts` (`_isAdmin` не используется) |
| **Проекты и подпроекты** | Нет — чужая **закрытая** строка (тумблер-глаз на ней или на её группе) закрыта и для админа | `canViewProject` (`_shared/tasks/project-access.ts`) про админа не знает (решение 2026-08-21). ⚠️ С 2026-08-24 «закрыто» ≠ «подпроект»: доска стала общим пространством, прячет только тумблер — см. [2026-08-24-subproject-visibility.md](2026-08-24-subproject-visibility.md) |
| **Личные списки-метки** | Нет | `swarm-api/task-labels.ts` фильтрует по `owner_id` |

**Точка входа для оверсайта — тумблер «Все сотрудники»** на доске задач (виден только админу, `LensToggle.tsx`): переключает охват на линзу `staff` — задачи всех сотрудников, сгруппированные по исполнителю. По умолчанию тумблер выключен, то есть чужие личные задачи не мозолят глаза и показываются только по осознанному нажатию.

## Кто такой «админ»

Не только владелец продукта: признак — зашитый `ADMIN_USER_ID` **либо** флаг `allowed_users.is_admin`. Флаг в проде стоит больше чем у одного человека. **Расширяя оверсайт, помни, что расширяешь его на всех с этим флагом**, а сужая — проверь, не сломал ли работу руководителей.

## Последствия

- Приватность в продукте означает «личное содержимое скрыто», а не «руководитель не видит твою работу». Так и надо писать в пользовательских текстах.
- Любая новая поверхность, читающая `tasks`, обязана звать общий гард `_shared/tasks/access.ts`, а не писать своё условие — иначе оверсайт снова разъедется по копиям (это уже было, issue #45).
- Любая новая поверхность, читающая `projects`/`entries`/`meetings`, **не должна** получать админский обход.
