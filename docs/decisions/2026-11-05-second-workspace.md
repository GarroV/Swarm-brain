# 2026-11-05 — Второе пространство: разделение команды и общие встречи

**Статус:** решения владельца приняты, план на обсуждении. Задача — GitHub «Второе пространство и переезд людей: разбор и план».

## Контекст

Команда девелопмента делится на две: Европа остаётся в пространстве `cee` (Central East Europe), остальной кластер
(Турция, Кавказ, Центральная Азия и др.) уходит в новое пространство. Переезжают три человека; двое из них
сервисом пока не пользуются, поэтому их собственных командных встреч в базе нет.

## Решения владельца (дословно, 05.11.2026)

1. **Зачем разделять:** «Это наша же команда, но они занимаются другим кластером. Соответственно, их задача - работать
   там. И нам контекст мешать - нет смысла никакого, абсолютно. Только какие-то общие встречи.» — командные встречи
   каждой команды видны только в её пространстве.
2. **Общие встречи сохраняются в обоих пространствах автоматически:** «Участник давай ничего не будет отмечать, люди
   этим явно не будут заниматься. Поэтому либо сохраняем обоим копию, либо давай все-таки проработаем признак
   встречи.» — выбор между копией и признаком принадлежности — за проработкой.
3. **История переезжает:** «все, что относится к личному, мы все перевозим. Все, что общее, где эти люди
   присутствовали, значит, нужно открыть для их пространство в будущем тоже.»
4. **Переезд — из админки**, не ручным SQL на проде.
5. **Код `cee` остаётся:** «пространство, которое CE … оно остается CE». Название переименовывается; новое
   пространство продумать сразу.
6. **Страны нового пространства** владелец настраивает сам из админки.
7. **Администрирование отделено от рабочего контекста:** владелец — администратор всего проекта и одновременно
   сотрудник; хочет смотреть статистику другого пространства, «но все же, чтобы мой контекст вообще не перемешивался
   никаким образом».
8. **Находки по изоляции — приватные security advisory:** «если ты нашел проблему, оформляй, как security».

## Ответы владельца на вопросы плана (05.11.2026, второй заход)

9. **Токены переводятся при переезде:** «в этой ситуации нам надо будет перевести токены. т.е. сделать переход коллег
   максимально бесшовным». Триггеры отзыва MCP-токенов (аудит 27.10) остаются для всех прочих смен пространства и
   флага админа; исключение — только переезд, выполненный мастер-админом из админки.
10. **Видимость общей встречи:** «правила не меняются. общие встречи идут в общее пространство. для личных встреч есть
    шмель» — общая (не личная) встреча с участниками обеих команд видна обеим командам целиком по обычным правилам
    пространства; личные встречи — через bumblebee, как сейчас.
11. **Мастер-админ:** «как админ я хочу менеджерить пространства, видеть статистику, выдавать доступы. сейчас все
    настроено на единое пространство, надо сделать чтобы было раздельно.»
12. **Задачи переезжают вместе с человеком:** «задача переезжает вместе. в этом и смысл».
13. **Админов нового пространства задаёт владелец.** Права админа пространства — на обсуждении.
14. **Название нового пространства:** «Turkey and co».
15. **Общие для всех пространств разделы:** «аналитика рынков, статистика РКО РС и прочее - все общее». «Анализ рынка»,
    проверки DECIMUS (РС, РКО), «Качество» по пространствам не делятся; данные рынка (`mkt_*`) остаются без
    `group_id`. Пересечение стран у пространств допустимо.
16. **Старт стройки и живой прогон:** «начинай стройку. живой прогон будем на Индире делать, т.к. она работу ведет в
    проекте, остальные нет. важно: сделай бекап индиры, и делай на каждом шагу чтобы мы ничего не потеряли не дай бог»
    — перед каждым шагом на проде снимок данных переезжающего и сверка после шага; первый переезд — Индира.
17. **Страны «Turkey and co»** (владелец 05.11): Турция, Кыргызстан, Таджикистан, Монголия, Нигерия, Индонезия, Армения,
    Азербайджан, Грузия — `TR, KG, TJ, MN, NG, ID, AM, AZ, GE`. Сейчас все девять входят и в список `cee`
    (23 страны).

## Проект решения: общая встреча — признак принадлежности (этап 2)

- `entries.visible_group_ids text[] NOT NULL` — пространства, где запись видна; всегда содержит домашнее `group_id`
  (держит триггер: на INSERT/UPDATE `group_id` домашнее добавляется в массив). GIN-индекс. Лишние пространства
  допустимы только у встреч (`entry_type='meeting'`); у личной (`is_private`) массив не расширяет круг — личное
  видит только владелец, как раньше.
- **Чтение для просмотра** (список, поиск, карточка, дайджест, бот, MCP, статистика встреч) — по
  `visible_group_ids @> {g}` вместо `group_id = g`. Всё, что не переведено, продолжает работать по домашнему
  пространству: пропуск = «не видно у второй команды», а не «видно чужим» (fail-closed).
- **Запись и обработка** (claim, ingest, дедуп, публикация, тезисы, ключ OpenAI, задачи из встречи) — по домашнему
  `group_id`, без изменений. Задачи, извлечённые из встречи, принадлежат пространству того, кто их извлёк.
- После проверки доступа к записи последующие выборки по ней (версии, живые пометки) берут `entry.group_id`,
  а не пространство смотрящего.
- **Кто проставляет:** публикация встречи — пространства участников по e-mail (`allowed_users.email`) минус домашнее;
  Read.ai при смешанном составе — домашнее по владельцу/большинству, остальные в признак (вместо отказа 422);
  переезд человека — его прошлые встречи (участник/владелец) получают новое пространство в признак.
- Права правки и удаления встречи не меняются (владелец, участники по e-mail, админ домашнего пространства).
18. **Снимки данных — только на время стройки:** «бекап нужен на момент стройки, не больше». Хранятся вне git
    на машине разработки, не перезаписываются; после переезда и живой проверки удаляются.
19. **Страны второй команды убираются из `cee` — последним шагом:** «убрать, но потом. сначала создаем все что нужно
    для работы второй команды». Порядок: пространство, переезд и проверка — затем снимаем девять стран из списка `cee`.
20. **Название второго пространства — «World»** (владелец 05.11: «давай второе пространство назовем World»;
    заменяет «Turkey and co» из п. 14).

### Склейка общей встречи по календарному ключу (05.11, сверка с сессией рекордера)

Запись человека из B общей календарной встречи склеивается со строкой `meetings` пространства A (уникальность
`identity_key` без `group_id`) — **оставляем осознанно**: это одна встреча, раздельные строки дали бы обеим командам по
две копии. Следствия, принятые сознательно: домашнее пространство склеенной встречи — первое (A); расшифровку и тезисы
оплачивает ключ нейронки A; совладельцы по почте считаются по людям A. Записавший/claim/co_owner из B сохраняет доступ к
своему черновику; при публикации пространства записавших попадают в `visible_group_ids`. Уникальный индекс не меняем.
Мощности бота (слоты, память Contabo) и очередь записи бота — за сессией рекордера, после этапа «Пространства».
21. **Рассылка из админки:** «рассылку из админки давай просто дадим возможность выбирать пространства» — отправитель
    выбирает пространства-получатели (несколько), скрытого «всем» по умолчанию нет.
22. **Сторож «бот не пришёл» не меняем:** «нет, зачем?» — условие уведомления остаётся прежним; вопрос возникает только
    когда у второго пространства появится свой бот-записыватель, вернуться к нему тогда (задача про бота второго
    пространства).
23. **Раскатка — контролируемо:** «давай мы это проведем контролируемо, чтобы я с утра не обнаружил что весь сервис
    лег» — не автоматикой по метке; порядок и присутствие — по плану раскатки, согласованному отдельно.
