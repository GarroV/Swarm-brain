# Бот звонков `scriba` остаётся в монорепозитории Swarm

_Решение владельца, 17.09.2026._

## Контекст

Владелец спросил: «мы сейчас ведем работу по боту для звонков. нам нет смысла вывести его в
отдельный репозиторий?» Бот `scriba` (Node 22 + Playwright + Docker, живёт в `bot/`, работает
в WSL2 на MUSPELHEIM) собирается на ветке `feat/meeting-bot` и с остальным Swarm не делит
ни строки кода: там Deno (edge), Next (веб), Swift (рекордер).

Что проверено фактом, а не памятью (17.09.2026):

- **Вес репозитория доводом не является:** вся история — 9,2 МиБ (`git count-objects -vH`).
  692 МБ в `recorder/` и 978 МБ в `miniapp/` — артефакты сборки, в git их нет.
- **Пуш кода бота людей не будит:** отпечаток `sw.js` считается от содержимого
  `out/_next/static`, поэтому пересборка Pages без изменений веба до открытых вкладок
  не доезжает (канон [2026-08-27-deploy-notice.md](2026-08-27-deploy-notice.md)).
- **Прецедент уже работает рядом:** `bumblebee` — та же форма (свой язык, свой хост, свой цикл
  релизов, общий с сервером только HTTP-контракт) — живёт в монорепозитории с path-фильтром
  в `recorder.yml` и отдельным релизным workflow.
- **Общее у бота с сервером — контракт, а не код:** `meeting-claim` (включая `defer`),
  `meeting-ingest`, агентский токен `_shared/agent-auth.ts`. Один блок бота
  (`conference-link`) вообще серверный и остаётся в Swarm при любом решении.
- **CI для `bot/` никто не заводил:** `scripts/check` есть и его зовут приёмка блока и
  хук pre-push, а workflow в Actions нет (`docs/furca/plan.md` его предполагает, задачи на
  него в `tasks.md` не было).

## Решение

**Бот остаётся в монорепозитории.** Владелец: «давай сделаем как рекомендуешь».

Причины, по убыванию веса:

1. **Контракт меняется с двух сторон одним движением** (`defer`, таймлайн говорящих, формат
   ingest). В одном репозитории это один коммит, один прогон CI и пара тестов «сервер +
   клиент»; в двух — версионная синхронизация, то есть ровно тот дрейф, против которого
   написаны правила о доках.
2. **Прецедент `bumblebee`:** выносить бота значит дать двум одинаковым сущностям разные правила.
3. **Стройка идёт:** блок `conference-link` уже влит в серверный код, журнал и граф задач
   лежат в `docs/furca/` этого репозитория, от него отведены четыре worktree. Перенос — день
   работы и потеря связности ради нуля для продукта.
4. **Второй репозиторий — это второй дом** для доков, секретов, беклога и CI.

Единственный настоящий довод «за» (стеки уже столкнулись: `deno lint` краснел на
https-импортах, корневые конфиги накрывают всё дерево) закрывается фильтрами путей, а не
переездом.

## Следствия

- `.github/workflows/bot.yml` — свой прогон бота: `npm ci --prefix bot` → `scripts/check bot`.
- `ci.yml` получил `paths-ignore: ['bot/**']`.
- ⚠️ **Эти две правки — одно целое.** `main` не защищён (`required_status_checks` нет),
  поэтому PR, у которого не запустился ни один чек, для ночной автоматики выглядит как
  `mergeStateStatus=CLEAN` — «претензий нет» — и уезжает в прод непроверенным. Убираешь
  фильтр — убирай и `bot.yml`, и наоборот.
- Правка только в `bot/**` живёт по правилу `recorder/**`: веб не задевает. Раскатка самого
  `scriba` — пересборка контейнера на MUSPELHEIM, а не мёрж в `main`.
- `bot.yml` на `main` до слияния ветки бота не срабатывает (файлов `bot/**` там нет) и живым
  прогоном пока не проверен — первый настоящий прогон будет на PR ветки `feat/meeting-bot`.

## Когда пересмотреть

Три условия, любое из которых возвращает вопрос:

1. `scriba` становится **единственным** источником записей — тогда ему нужен свой хост
   (MUSPELHEIM как единственная точка уже помечен риском в `docs/furca/plan.md`) и свой цикл релизов.
2. Контракт **стабилизировался и версионируется** — перестал меняться с двух сторон сразу.
3. Бот понадобился **кому-то вне Swarm** (другой продукт, открытый код).
