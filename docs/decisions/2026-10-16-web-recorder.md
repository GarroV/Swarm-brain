# Запись встречи из браузера (офлайн-встречи)

Дата: 2026-10-16. Задача: «Запись встречи из браузера (мобильный веб)» в трекере.

## Решения владельца (дословно)

- «аккаунт явно покупать не буду … эту идею паркуем» — приложения на iPhone не будет, аккаунта Apple Developer нет.
- «давай идем значит вбраузерную запись. начни подгтовку» — вместо приложения запись из веб-версии Swarm.
- «если с телефона запускаем то участиников не определим конечно / по сути инструемент нужен для оффлайн встреч» — участники не определяются, сценарий — живая встреча в комнате.
- «кнопку да давай. продумаем чтоб красиво было» — кнопка и на компьютере, не только на телефоне.

## Что проверено на живом iPhone (iOS 26, Safari, вкладка)

Проверочная страница `miniapp/public/rec-probe.html`, два прогона владельца:

| Действие | Результат |
|---|---|
| Перезапуск MediaRecorder каждые 30 с на том же треке | каждый кусок — самостоятельный файл `audio/mp4`, звука ровно столько, сколько по часам |
| Отдельный фрагмент `timeslice` из середины куска | не читается — слать можно только кусок целиком |
| Уход в другое приложение на 67 с | запись не прервалась, куски полные |
| Блокировка экрана на 14 с | трек `mute`, эти секунды выпадают из куска (15,7 с звука из 30); после разблокировки `unmute` и запись продолжается сама, без нажатия |
| AudioContext для индикатора | создаётся спящим, если не создан синхронно в нажатии |

Не проверено: звонок посреди записи, содержимое звука в фоне (тишина или голос), приложение с домашнего экрана.

## Как устроено

**Клиент** пишет микрофон кусками по 5 минут: каждый кусок — новый `MediaRecorder` на том же треке, внутри `start(5000)`, фрагменты складываются в IndexedDB. Закрытый кусок уходит на сервер сразу; из IndexedDB удаляется только после ответа сервера. Смещение куска — секунды от начала записи по часам, поэтому выпавшие при блокировке секунды не сдвигают расшифровку. Экран держится включённым (Screen Wake Lock, перезапрос при возврате на страницу).

**Сервер** (модуль `swarm-api/web-recording.ts`, вход по обычной веб-сессии):

| Метод | Что делает |
|---|---|
| `POST /meetings/record` | заводит строку `meetings`: `source='web-recorder'`, `identity_kind='manual'`, `identity_key='web:<uuid>'`, `claim_owner` и `recorders=[{telegram_id}]` — автор, участников нет |
| `PUT /meetings/record/:id/segments/:n?offset=<сек>` | тело — аудио куска; кладётся в `meeting-audio/<id>/web/<n>-<offset_ms>.m4a`, повтор того же `n` перезаписывает (идемпотентно) |
| `POST /meetings/record/:id/finish` | собирает куски из Storage в `process_state` (дорожка `mic`), ставит `summary_status='processing'` — дальше обычная обработка встреч |
| `GET /meetings/record/active` | незавершённая запись автора — для «дозагрузить и завершить» после сбоя |

**Брошенная запись** (вкладку закрыли, телефон сел): сторож пустых встреч (`swarm-bot/lib/ghost-sweep.ts`) не помечает запись из браузера сбоем, пока по ней была активность последние 30 минут; после — завершает её тем же кодом, что `finish`, если хоть один кусок дошёл, иначе помечает `failed`.

**Видимость**: как у записи с Мака — `recorders` содержит только автора, вычитку видит только он, дальше обычные правила публикации.

**Сообщения людям**: уведомления «встреча обработана / не удалось / зависла» для записей из браузера **не отправляются**, пока владелец не скажет «да» на текст и адресата (глобальное правило о коммуникации).

**Метка в списке**: `source='web-recorder'` → «Офлайн-встреча» / «In-person». Миграции нет: `meetings.source` без ограничения, `recorded_by` для таких встреч пустой.
