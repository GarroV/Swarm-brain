# Произвольная повторяемость задач

**Дата:** 2026-10-07 · **Статус:** принято, реализовано (#823) · Развивает
[2026-08-27-recurring-tasks.md](2026-08-27-recurring-tasks.md): модель «одна задача катится вперёд»
и отсчёт «от графика» остаются как были.

## Запрос владельца (дословно)

> «в задачах надо дать возможность выбирать любую систему повторяемости. сделай прямо отдельным
> контекстными меню. нужно уметь настроить хоть каждый третий понедельник, хоть каждые 2 недели от
> текущей даты».

## Что выбрали

**Словарь RRULE (RFC 5545), но отдельными колонками задачи, а не строкой.**

| Колонка | RRULE | Значение |
|---|---|---|
| `recur_freq` | `FREQ` | `daily` \| `weekly` \| `monthly` \| **`yearly`** (новое) |
| `recur_interval` | `INTERVAL` | каждые N, 1–99, по умолчанию 1 |
| `recur_weekdays` | `BYDAY` | только weekly: дни ISO 1=пн..7=вс; NULL = день недели срока |
| `recur_setpos` | `BYSETPOS` | только monthly: n-й (1–5) или последний (−1) день недели срока; NULL = по числу |

Миграция `20261007160000_task_recurrence_rules.sql` — только ADD COLUMN и пересоздание CHECK.
NULL/1 в новых колонках = прежнее поведение, существующие задачи не меняются.

**Почему не строка RRULE.** Строку не проверит CHECK в базе: мусор («FREQ=HOURLY;BYDAY=XX»)
оседает молча и ломает перекат при первом же закрытии. Колонки проверяет и код
(`validateRecurFields`), и база (CHECK на каждую). Плюс колонки читаются в SQL без парсера.
Словарь RRULE взят, чтобы при выгрузке в календарь (iCal) правило переводилось один к одному.

## Правила счёта

- **Якорь — срок задачи**, интервал считается от него. Первое вхождение — строго позже
  max(срок, сегодня), фаза не сдвигается: «каждые 2 недели», опоздали на 3 недели → ближайшая дата
  той же чётности, а не «две недели от выполнения».
- **weekly с днями недели:** недели с шагом N отсчитываются от недели срока (неделя — с
  понедельника), внутри недели — дни из набора.
- **monthly с n-м днём:** день недели берётся из срока. «Каждый третий понедельник» = monthly,
  setpos = 3, срок — понедельник. Пятого такого дня в месяце нет — месяц пропускается (как BYSETPOS).
- **yearly:** месяц срока, число — `recur_anchor_dom`, зажатое по длине месяца: 29 фев → 28 фев в
  невисокосный год → снова 29 фев в високосный.
- **«Каждые 2 недели от текущей даты»** — веб: меню повтора без срока подставляет срок = сегодня.
- **Сброс** (`recur_freq: null`) обнуляет все поля правила — централизованно в
  `resolveRecurrence`/`recurrencePatchFor`, писатели (API, MCP) сами ничего не обнуляют.
  Не присланное поле правила сохраняется, пока частота та же (старая вкладка шлёт только
  `recur_freq` — интервал не теряется); сменили частоту — поле берёт умолчание.

## Решения, принятые мной (не владельцем) — можно оспорить

| Решение | Причина |
|---|---|
| Подпись «каждые N недель» показывает и день: «Каждые 2 недели: ср» | Иначе из подписи не понять, по какому дню идёт задача |
| Быстрые варианты месяца/года звучат «Каждый месяц, 26-го» / «Каждый год, 7 окт» вместо «26-го числа каждый месяц» | Один строй с подписями произвольного правила |
| Набор дней недели, равный одному дню срока, хранится как NULL | Тогда он идёт за сроком при переносе, как и раньше |
| Интервал ограничен 99 | Больше — почти наверняка опечатка; CHECK держит границу |
| Вариант «последний день недели» в меню месяца есть всегда, «n-й» — если n < 5 | 5-й такой день и есть последний, два одинаковых варианта ни к чему |
