# Веб-интерфейс «Рой» — Архитектура

> ⚠️ **Терминология (важно):** это **веб-интерфейс** — обычный сайт/PWA в браузере (`swarm-brain.pages.dev`), НЕ «Mini App». Вход как **Telegram Mini App внутри Telegram отключён** (~2026-07-15, коммит `53bd3ae` — бот ведёт на PWA). Слова «Mini App» ниже по тексту — это (а) историческое имя папки `miniapp/` и (б) спящий путь `initData`/`tma`, который ещё есть в коде, но точки входа не имеет (на удаление — см. `docs/BACKLOG.md`). **Живой вход — Telegram Login Widget → JWT-cookie в браузере.** Поверхностей у продукта три: веб-интерфейс, Telegram-бот, MCP.
>
> Статус: фронтенд реализован (2026-06-01), в проде на Cloudflare Pages (авто-деплой с `main`).

---

## Реализованный стек

```
Telegram Mini App (⚠️ СПЯЩИЙ — вход отключён; живой путь — Login Widget ниже)
        │
        │  Authorization: tma <initData>
        ▼
swarm-api  (Supabase Edge Function)
        │  - верифицирует initData (Telegram HMAC)
        │  - резолвит telegram_id → group_id
        │  - REST CRUD для задач
        ▼
_shared/tasks/db.ts  (общий движок)
        │
        ▼
Supabase DB (service_role_key, фильтр по group_id)
```

Режим: **поллинг** (фронтенд запрашивает данные сам). Realtime, RLS и Supabase Auth bridge не нужны.

## Аутентификация — два контекста

| Контекст | Способ | Поток |
|----------|--------|-------|
| Telegram Mini App **(⚠️ СПЯЩИЙ — вход отключён)** | `Authorization: tma <initData>` | код остался, но точки входа нет (Mini App выключен ~2026-07-15); живой путь — только строка ниже |
| Браузер / PWA (вариант B+) | httpOnly cookie `roj_session` (JWT) | `/login` → Telegram Login Widget → CF Function `auth/telegram` проверяет подпись → JWT в httpOnly cookie → прокси `/api/[[path]]` перекладывает cookie в `Authorization: Bearer` → swarm-api проверяет JWT |

**Почему прокси (B+):** miniapp — статика на Cloudflare Pages (нет Next API routes/middleware). httpOnly-cookie недоступна JS (защита от XSS) и не уходит cross-origin на `*.supabase.co`, поэтому CF Pages Function `functions/api/[[path]].ts` форвардит запросы на swarm-api server-side, перекладывая cookie → `Bearer`. JWT: HS256, секрет `WEB_JWT_SECRET` (общий у CF и Supabase). Login Widget подписывает данные секретом `SHA256(bot_token)` (иначе, чем Mini App).

Авторизация в обоих случаях одинакова: `telegram_id` → `allowed_users` → `group_id`. Виджет лишь подтверждает личность; доступ по-прежнему гейтится белым списком.

**`recorder_token` веб-интерфейс НЕ использует.** Персональный токен рекордера (`recorder_token_hash`, `/recordertoken`) — только для desktop-agent (`meeting-claim`/`meeting-ingest`, auth через `_shared/agent-auth.ts`). Веб-интерфейс ходит через браузерный JWT (`Bearer`) (спящий путь `tma`/`initData` — тоже не рекордерный токен) — никогда через токен рекордера.

## Безопасность

- `group_id` берётся **только** из проверенной личности (initData/JWT → telegram_id → allowed_users). Из тела запроса не принимается.
- Каждая операция с задачами скоупится по `group_id` — пользователь не может видеть или менять задачи другого воркспейса.
- Приватные задачи (`is_private`) видны только владельцу/админу; в командный бот не попадают.
- `service_role_key` только внутри swarm-api, фронтенду не передаётся.
- Веб-сессия: JWT в httpOnly Secure SameSite=Lax cookie (недоступен JS). SW не кэширует API.

### Модуль задач (Рой)
Дефолтный вид — **«Список»** в стиле macOS Reminders. Ось ВРЕМЕНИ (рельс/чипы): **Сегодня · Ближайшие · Все · Регулярные**, где **«Регулярные»** появляется только когда есть хоть одна циклическая задача и прячется, когда их не осталось (решение владельца 2026-08-27, канон [decisions/2026-08-27-recurring-tasks.md](decisions/2026-08-27-recurring-tasks.md)). **Ось СТАТУСА** (issue #216, добавлена 03.09.2026) — независимый мультивыбор тумблеров **Открыто · В работе · Готово** отдельным блоком под осью времени: накладывается на выбранный список, а не подменяет его (владелец: «фильтры не исключают друг друга, т.е. мы можем «все» задачи отсортировать по статусам»). Дефолт — «Открыто + В работе», поэтому для того, кто фильтр не трогал, экран выглядит как раньше. «Готовые» больше НЕ пункт оси времени; у закрытой задачи ось времени считается по дате закрытия, поэтому «Сегодня + Готово» = «что закрыл сегодня». `pending` и `backlog` замьючены целиком (решение владельца: «спринты не используются»), незнакомый статус попадает в «Открыто» — чтобы новое значение в базе не исчезло с экрана молча. Верхний переключатель-линза (ось «чьи задачи»): **Мои · Команда · Все**, где **«Команда» = ОБЩИЕ задачи: не приватные и без конкретного исполнителя** (решение владельца 2026-08-19: «командная задача = общая, у которой нет определённого юзера»), а **«Все» = мои + командные** (владелец 2026-08-20: «линза "все" показывает свои задачи и задачи команды, чужие задачи не показывает»). Личные задачи коллег не показываются НИ под одной из трёх позиций — только под админским тумблером «Все сотрудники» (внутренняя линза `staff`). Гард тумблера — и в UI (`showAllStaff`), и в `useReminderTasks` (`allStaff && me.is_admin`): состояние переживает потерю админства в `localStorage`, поэтому проверка не может жить только в разметке. «По рынкам» и «Все сотрудники» — **не линзы, а независимые тумблеры-модификаторы**: группируют результат ТЕКУЩЕЙ линзы, а не подменяют охват (`useReminderTasks`; раньше «По рынкам» была 4-й позицией линзы и всегда тянула чужие задачи — исправлено 2026-08-19). **Период** (`lib/dateRange.ts`, добавлен 2026-08-25) — третий независимый модификатор рядом с «По рынкам»/«Все сотрудники»: пресеты **Эта неделя · Этот месяц · Прошлая неделя · Прошлый месяц** либо произвольный диапазон из календаря. Он **пересекается** с активным списком, а не расширяет его: «Готово + эта неделя» = что закрыто за неделю (дата берётся из `updated_at` — отдельного `completed_at` в таблице нет), «Все + этот месяц» = нагрузка месяца (по `due_date`). Задача без нужной даты в период не попадает; из «Сегодня» под периодом выпадают просрочки за его границей — это ожидаемое следствие пересечения. Счётчики рельса считаются ПОД периодом (иначе цифры разошлись бы с показанным списком), активный период продублирован чипом в шапке (клик — снять), состояние живёт в том же ключе `localStorage` `roy_tasks_view` (`range`), причём пресет пересчитывается от сегодня при восстановлении. Десктоп и мобайл (`RoyTasksScreen`) делят логику через `useReminderTasks` + `TaskRow` + `SmartListNav`; на десктопе смарт-списки — левый рельс, на мобайле — чипы. Виды «Задачи» / «Проекты» / «Спринты» работают поверх того же `swarm-api` контракта (счётчики и линза считаются на клиенте из общего `fetchTasks`). Канбан живёт в ДВУХ видах — «Проекты» (доска) и «Спринты» — общим компонентом `TaskKanban` (вынесен из `SprintBoard` 09.09.2026, issue #267). Приватные задачи видны в miniapp только владельцу (фильтрация на бэкенде). PWA устанавливается на macOS: Safari → Поделиться → «Добавить в Dock».

### Навигация «Рой» — push-роуты (`RoyRoute`)

Корневые табы: `search` · `task` · `book` · `cal` (определены в `ui.tsx:ROY_TABS`).
Push-стек управляется `RoyApp.tsx`: `push(route)` → `PushScreen` рендерит нужный экран.

**Адресная строка синхронизирована с навигацией (issue #31, 05.09.2026).** До этого веб жил на одном роуте `/`: URL не менялся, ссылку на задачу дать было нельзя, «назад» браузера уводило с сайта. Причина историческая — приложение делалось как Telegram Mini App, где адрес не виден; вход из Telegram отключён ~15.07.2026.

Как устроено: чистый модуль [`lib/royUrl.ts`](../miniapp/src/lib/royUrl.ts) — `stateToQuery` / `queryToState` / `stateToPath`, ни `window`, ни `history` внутри (поэтому проверяется тестами, а не кликами: `lib/royUrl.test.ts`, 12 тестов). `RoyApp` кладёт `pushState` на каждый переход и слушает `popstate`.

- В адрес попадают **таб и верхний экран стека**: `?tab=task&view=taskDetail&id=<id>`. Не весь стек — намеренно: ссылка должна читаться человеком, а стек в продукте мелкий (0–1 экран). Глубина живёт в памяти сессии и `sessionStorage`, как и раньше.
- Дефолтный таб (`search`) в адрес не пишется; `queryToState` возвращает `tab: null` = «в адресе не задано», потребитель подставляет свой дефолт.
- Вычитка встречи сериализуется в **наследуемый `?meeting=<id>`**, а не в `view=meetingReview`: этот адрес уже рассылают уведомления «тезисы готовы» и лаунч установленного PWA (`lib/single-tab.ts`). Один формат вместо двух.
- При загрузке **адрес важнее сохранённой сессии**: по присланной ссылке открывается её экран, а не тот, на котором человек остановился вчера.
- Невалидный адрес игнорируется молча (роут без обязательного `id`, несуществующий `view`/`tab`) — его правит кто угодно, и чужая опечатка не повод показать белый экран.
- Типы маршрутов вынесены в [`lib/royRoute.ts`](../miniapp/src/lib/royRoute.ts), `nav.ts` их ре-экспортирует: Deno тайпчекает тесты в `lib/`, а модуль с `react` он собрать не может (та же причина, что у `lib/royIcons.ts`).

Проверено в браузере: `/` → `?tab=more` → `?tab=more&view=settings`, «назад»/«вперёд» меняют экран, прямая ссылка открывает нужный экран, легаси `?meeting=` жив.

**API-операции:**
| Действие | Entry (неподтв. встреча) | AgentMeeting (черновик) |
|----------|--------------------------|-------------------------|
| Согласовать (Общее/Личное) | `patchMeeting(id, {confirmed:true, is_private, countries})` | `publishAgentMeeting(id, "workspace"\|"personal", countries)` |
| Рынки записи | в очереди — вместе с согласованием; у согласованной — `patchMeeting(id, {countries})` сразу по клику | подсказка `fetchMarketSuggestion(id)`, выбор уходит в `publishAgentMeeting` |
| Править содержание | `patchMeeting(id, {content})` | название → `renameAgentMeeting(id,title)`; тезисы → `patchAgentMeetingDraft(id,md)` (инлайн на ревью) |
| Реклассифицировать | `patchMeeting(id, {entry_type:"note"})` → уходит из очереди | — |
| Сгенерировать задачи | `extractTasksPreview(content)` → `createTask({meeting_id, is_private})` | `extractTasksPreview(draft_notes_md)` → `createTask({is_private})` (автономно) |
| Отклонить | `deleteMeeting(id)` (с confirm) | `deleteAgentMeeting(id)` (с confirm) |

> Бэкенд: `PATCH /meetings/:id` принимает `content`/`is_private`(+`owner_id`)/`entry_type`/`countries` (swarm-api); `POST /tasks/extract { save:false }` возвращает предложения без создания. Пустой выбор рынков клиент шлёт как `["General"]` — это сентинел «конкретного рынка нет», а не отсутствие тега (в базе так лежат 65 встреч).
