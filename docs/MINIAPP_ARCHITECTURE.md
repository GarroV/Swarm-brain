# Веб-интерфейс «Рой» — Архитектура

> ⚠️ **Терминология (важно):** это **веб-интерфейс** — обычный сайт/PWA в браузере (`swarm-brain.pages.dev`), НЕ «Mini App». Вход как **Telegram Mini App внутри Telegram отключён** (~2026-07-15, коммит `53bd3ae` — бот ведёт на PWA). Слова «Mini App» ниже по тексту — это (а) историческое имя папки `miniapp/` и (б) спящий путь `initData`/`tma`, который ещё есть в коде, но точки входа не имеет (на удаление — см. `docs/BACKLOG.md`). **Живой вход — Telegram Login Widget → JWT-cookie в браузере.** Поверхностей у продукта три: веб-интерфейс, Telegram-бот, MCP.
>
> Статус: фронтенд реализован (2026-06-01), в проде на Cloudflare Pages (авто-деплой с `main`).

## Реализованный стек

```
Telegram Mini App (⚠️ СПЯЩИЙ — вход отключён; живой путь — Login Widget ниже)
        │
        │  Authorization: tma <initData>
        ▼
swarm-api  (Supabase Edge Function)
        │  - верифицирует initData (Telegram HMAC)
        │  - резолвит telegram_id → group_id
        │  - REST CRUD для задач
        ▼
_shared/tasks/db.ts  (общий движок)
        │
        ▼
Supabase DB (service_role_key, фильтр по group_id)
```

Режим: **поллинг** (фронтенд запрашивает данные сам). Realtime, RLS и Supabase Auth bridge не нужны.

## Аутентификация — два контекста

| Контекст | Способ | Поток |
|----------|--------|-------|
| Telegram Mini App **(⚠️ СПЯЩИЙ — вход отключён)** | `Authorization: tma <initData>` | код остался, но точки входа нет (Mini App выключен ~2026-07-15); живой путь — только строка ниже |
| Браузер / PWA (вариант B+) | httpOnly cookie `roj_session` (JWT) | `/login` → Telegram Login Widget → CF Function `auth/telegram` проверяет подпись → JWT в httpOnly cookie → прокси `/api/[[path]]` перекладывает cookie в `Authorization: Bearer` → swarm-api проверяет JWT |

**Почему прокси (B+):** miniapp — статика на Cloudflare Pages (нет Next API routes/middleware). httpOnly-cookie недоступна JS (защита от XSS) и не уходит cross-origin на `*.supabase.co`, поэтому CF Pages Function `functions/api/[[path]].ts` форвардит запросы на swarm-api server-side, перекладывая cookie → `Bearer`. JWT: HS256, секрет `WEB_JWT_SECRET` (общий у CF и Supabase). Login Widget подписывает данные секретом `SHA256(bot_token)` (иначе, чем Mini App).

Авторизация в обоих случаях одинакова: `telegram_id` → `allowed_users` → `group_id`. Виджет лишь подтверждает личность; доступ по-прежнему гейтится белым списком.

**`recorder_token` веб-интерфейс НЕ использует.** Персональный токен рекордера (`recorder_token_hash`, `/recordertoken`) — только для desktop-agent (`meeting-claim`/`meeting-ingest`, auth через `_shared/agent-auth.ts`). Веб-интерфейс ходит через браузерный JWT (`Bearer`) (спящий путь `tma`/`initData` — тоже не рекордерный токен) — никогда через токен рекордера.

## Безопасность

- `group_id` берётся **только** из проверенной личности (initData/JWT → telegram_id → allowed_users). Из тела запроса не принимается.
- Каждая операция с задачами скоупится по `group_id` — пользователь не может видеть или менять задачи другого воркспейса.
- Приватные задачи (`is_private`) видны только владельцу/админу; в командный бот не попадают.
- `service_role_key` только внутри swarm-api, фронтенду не передаётся.
- Веб-сессия: JWT в httpOnly Secure SameSite=Lax cookie (недоступен JS). SW не кэширует API.

## Переменные окружения

| Переменная | Обязательная | Описание |
|-----------|-------------|----------|
| `TELEGRAM_BOT_TOKEN` | да | уже есть (Supabase + CF Pages) |
| `MINIAPP_ORIGIN` | рекомендуется | CORS origin веб-интерфейса (напр. `https://swarm-brain.pages.dev`) |
| `INITDATA_MAX_AGE` | нет | свежесть initData в секундах (дефолт 86400) |
| `WEB_JWT_SECRET` | для веб-входа | подпись веб-сессий (одинаковый в Supabase secrets и CF Pages env) |
| `SWARM_API_URL` | CF Pages | цель прокси `functions/api/[[path]]` → swarm-api |
| `NEXT_PUBLIC_BOT_USERNAME` | CF Pages build | username бота для Login Widget (`swarm_brain_bot`) |
| `NEXT_PUBLIC_API_URL` | CF Pages build | `/api` (прокси same-origin) |

## Фронтенд веб-интерфейса — реализован (2026-06-01)

**Расположение:** `miniapp/`
**Деплой:** Cloudflare Pages — build command `npm run build`, output dir `out`
**Локальная разработка:** `cd miniapp && npm run dev` (с `NEXT_PUBLIC_DEV_MODE=true` в `.env.local`)

### Стек
- Next.js 16, `output: 'export'`, TypeScript
- Tailwind CSS v4 + shadcn/ui
- `@twa-dev/sdk` → `Telegram.WebApp.initData`
- Plain fetch + useEffect (поллинг 10 сек + visibilitychange)

### Модуль задач (Рой)
Дефолтный вид — **«Список»** в стиле macOS Reminders. Смарт-списки (рельс/чипы, ось время-статус): **Сегодня · Ближайшие · Все · Регулярные · Готовые**, где **«Регулярные»** появляется только когда есть хоть одна циклическая задача и прячется, когда их не осталось (решение владельца 2026-08-27, канон [decisions/2026-08-27-recurring-tasks.md](decisions/2026-08-27-recurring-tasks.md)). Верхний переключатель-линза (ось «чьи задачи»): **Мои · Команда · Все**, где **«Команда» = ОБЩИЕ задачи: не приватные и без конкретного исполнителя** (решение владельца 2026-08-19: «командная задача = общая, у которой нет определённого юзера»), а **«Все» = мои + командные** (владелец 2026-08-20: «линза "все" показывает свои задачи и задачи команды, чужие задачи не показывает»). Личные задачи коллег не показываются НИ под одной из трёх позиций — только под админским тумблером «Все сотрудники» (внутренняя линза `staff`). Гард тумблера — и в UI (`showAllStaff`), и в `useReminderTasks` (`allStaff && me.is_admin`): состояние переживает потерю админства в `localStorage`, поэтому проверка не может жить только в разметке. «По рынкам» и «Все сотрудники» — **не линзы, а независимые тумблеры-модификаторы**: группируют результат ТЕКУЩЕЙ линзы, а не подменяют охват (`useReminderTasks`; раньше «По рынкам» была 4-й позицией линзы и всегда тянула чужие задачи — исправлено 2026-08-19). **Период** (`lib/dateRange.ts`, добавлен 2026-08-25) — третий независимый модификатор рядом с «По рынкам»/«Все сотрудники»: пресеты **Эта неделя · Этот месяц · Прошлая неделя · Прошлый месяц** либо произвольный диапазон из календаря. Он **пересекается** с активным списком, а не расширяет его: «Готовые + эта неделя» = что закрыто за неделю (дата берётся из `updated_at` — отдельного `completed_at` в таблице нет), «Все + этот месяц» = нагрузка месяца (по `due_date`). Задача без нужной даты в период не попадает; из «Сегодня» под периодом выпадают просрочки за его границей — это ожидаемое следствие пересечения. Счётчики рельса считаются ПОД периодом (иначе цифры разошлись бы с показанным списком), активный период продублирован чипом в шапке (клик — снять), состояние живёт в том же ключе `localStorage` `roy_tasks_view` (`range`), причём пресет пересчитывается от сегодня при восстановлении. Десктоп и мобайл (`RoyTasksScreen`) делят логику через `useReminderTasks` + `TaskRow` + `SmartListNav`; на десктопе смарт-списки — левый рельс, на мобайле — чипы. Виды List / Timeline / Sprint / Projects работают поверх того же `swarm-api` контракта (счётчики и линза считаются на клиенте из общего `fetchTasks`). Канбан остался только в «Спринте». Приватные задачи видны в miniapp только владельцу (фильтрация на бэкенде). PWA устанавливается на macOS: Safari → Поделиться → «Добавить в Dock».

### Десктоп-главный экран (`RoyDashboard`) — 3 колонки

**Где:** `RoyApp.tsx` рендерит `RoyDashboard` только когда `isDashboard` = desktop (`lg+`) + активна вкладка `search` + push-стек пуст. На узких экранах (`< lg`) домашняя вкладка — `SearchScreen`. Контракт named-export `RoyDashboard` не менять (его импортит `RoyApp`).

**Список задач слушает `tasksVersion` (2026-08-25).** `useReminderTasks` обновлялся только опросом раз в 10 секунд, поэтому правка задачи из карточки (`TaskModal` бампает счётчик) до 10 секунд не была видна в списке — на телефоне это читается как «правка не применилась». Теперь хук перезапрашивает задачи по изменению счётчика. Проверка — `miniapp/e2e/deep-flows.mjs`. Там же закрыт пробел мока: DEV-`patchMeeting` игнорировал `title`, хотя бэкенд пишет его в `metadata.title` — локально и в демо переименование встречи молча не работало при тосте «Название обновлено».

**Тач-цели и плавающая кнопка (аудит экранов второго уровня, 2026-08-24).** Пройдены карточка задачи, форма создания, вычитка, встреча в базе, настройки, команда, экран ответа: горизонтального переполнения и ошибок в консоли нет, а зоны нажатия подняты к норме 44px там, где были 13–38px — «Назад» в `NavHeader` (стоит на каждом push-экране), выход и «Переименовать» на вычитке (были 20×20 и 17×17), «Редактировать тезисы»/«Транскрипт» (высота строки 16px), «Закрыть»/«Удалить» в карточке задачи, «Удалить комментарий» (13×13), поля и селекты карточки, чипы (`Chip`, `Segmented`, смарт-списки), колокольчик. Иконки прежнего размера — росла только зона нажатия (у чекбокса строки — через `::after`, чтобы не сдвигать вёрстку). **`FAB` переведён с `absolute` на `fixed`:** экраны-списки сами являются скролл-контейнерами, поэтому кнопка уезжала вместе с содержимым и на прокрученном списке оказывалась **поверх строк у верхнего края**, съедая по ним тап и свайп (найдено смоуком: горизонтальный свайп «не открывал шторку», хотя код исправен). **Правый угол шапки мобильных экранов** — `HeaderActions` (`roy/HeaderActions.tsx`): колокольчик уведомлений + поиск. Оба контрола жили в шапке «Поиска» — единственного экрана, который был домом; после редизайна «Поиск» стал push-экраном, и без переноса уведомления уехали бы вглубь. **Навигация мобайла — четыре корневых таба (2026-08-22).** Таб-бар: **Задачи · Проекты · Встречи · Ещё** (набор — решение владельца, [ADR](decisions/2026-08-22-mobile-nav.md)). Дом мобильного — **Задачи**, не «Поиск». **Поиск перестал быть табом**: иконка `SearchBtn` в шапке каждого корневого экрана → push-роут `ask` (тот же `SearchScreen` с «Назад» вместо лого) → `openAnswer`; формулировка входа одна во всех точках (владелец 2026-08-22: «у нас поиск в вебе один»). **База** — пункт «Ещё» → push-роут `base` (тот же `RoyBaseScreen` с «Назад»). **«Ещё»** — корневой таб: профиль, База, Команда, Настройки, Карта системы, Админ (админу); до этого вход в них был **только** из шапки «Поиска», т.е. с одного экрана из четырёх. `RoyTab` сохраняет `search`/`book` как ДЕСКТОПНЫЕ разделы; при восстановлении из `sessionStorage` на мобайле они мигрируют (`search` → `task`, `book` → `more`) — иначе живая сессия после деплоя попадала бы на экран, которого нет в баре.

На десктопе действия остались на виду — там мышь. Формат даты приведён к общему («12 июн.») и в очереди, и на экране вычитки `MeetingReview` — ISO-срез там был третьим форматом даты в одном разделе. Строка очереди на мобайле — тоже `SwipeRow`: «карандаш» дублировал тап (обе кнопки звали `onOpen`), «корзина» стояла мелкой целью в 8px от него; теперь тап открывает вычитку, свайп удаляет, на десктопе кнопки остались. Органы управления встречей на её экране не тронуты: правка названия/тезисов/стран, выбор «Общее/Личное» и «Сохранить в базу» — у несогласованной; у согласованной выбора хранилища нет (решение владельца 2026-08-21, коммит `0f1d55b`).

  - **Исполнитель** резолвится из имени, которое отдал GPT, в `telegram_id` (`resolveAssigneeId`, `lib/proposedTasks.ts`): полное имя → username → единственное совпадение по слову. Неоднозначно или не найдено → задача создаётся БЕЗ исполнителя, а в строке честно написано «не найден» (issue #126).
  - entry → привязка `meeting_id=entry.id`; agent → задачи автономные (записи ещё нет до публикации).
- **Справа (220px):** действия — блок **«Рынки»** (`MarketChips`, issue #73) → Segmented **«Общее/Личное»** (дефолт Общее) → «Согласовать/Опубликовать»; «Отклонить»; для entry — **«Не встреча → в заметки»** (`patchMeeting(id,{entry_type:"note"})`). Обновление списка/`selected` — через `onEntryUpdated`. Ошибки операций → тост.
  - **Рынки.** До этого рынок записи ставил ТОЛЬКО авто-классификатор, молча, в момент публикации — человек его не видел (владелец 23.08.2026: «до сих пор не вижу возможности настройки стран»), отсюда же перетег дайджеста чужими странами. Теперь: чипы всех `allowed_markets` (`/config`), мультивыбор, отдельный чип «Общее». У черновика предвыбрано предложение сервера (`fetchMarketSuggestion` → `GET /agent-meetings/:id/market-suggestion`) + подпись, откуда оно взялось («по названию встречи» / «по рынкам участников» / «по тезисам») — это мягкий нудж, публикация всегда уходит с тем, что человек оставил. У встречи-записи показываются её текущие `countries`. **Режим правки зависит от статуса:** в очереди выбор уезжает вместе с решением (`publishAgentMeeting(..., countries)` / `patchMeeting(id,{countries})`), у УЖЕ согласованной записи — сохраняется сразу по клику (оптимистично, откат + тост при ошибке), иначе перетеганную запись нечем починить.

**API-операции:**
| Действие | Entry (неподтв. встреча) | AgentMeeting (черновик) |
|----------|--------------------------|-------------------------|
| Согласовать (Общее/Личное) | `patchMeeting(id, {confirmed:true, is_private, countries})` | `publishAgentMeeting(id, "workspace"\|"personal", countries)` |
| Рынки записи | в очереди — вместе с согласованием; у согласованной — `patchMeeting(id, {countries})` сразу по клику | подсказка `fetchMarketSuggestion(id)`, выбор уходит в `publishAgentMeeting` |
| Править содержание | `patchMeeting(id, {content})` | название → `renameAgentMeeting(id,title)`; тезисы → `patchAgentMeetingDraft(id,md)` (инлайн на ревью) |
| Реклассифицировать | `patchMeeting(id, {entry_type:"note"})` → уходит из очереди | — |
| Сгенерировать задачи | `extractTasksPreview(content)` → `createTask({meeting_id, is_private})` | `extractTasksPreview(draft_notes_md)` → `createTask({is_private})` (автономно) |
| Отклонить | `deleteMeeting(id)` (с confirm) | `deleteAgentMeeting(id)` (с confirm) |

> Бэкенд: `PATCH /meetings/:id` принимает `content`/`is_private`(+`owner_id`)/`entry_type`/`countries` (swarm-api); `POST /tasks/extract { save:false }` возвращает предложения без создания. Пустой выбор рынков клиент шлёт как `["General"]` — это сентинел «конкретного рынка нет», а не отсутствие тега (в базе так лежат 65 встреч).
