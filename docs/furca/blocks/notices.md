# Блок: notices

## Назначение

Громкие отказы: всё, где бот мог бы промолчать, обязано дойти до человека. Отдельный блок, потому что
это прямое следствие первого принципа проекта, а не деталь адаптера.

Пользой наружу: владелец встречи узнаёт в Telegram, что запись **не** идёт и почему, — вместо того
чтобы после встречи обнаружить пустую очередь вычитки.

## API-контракт

### `POST /meeting-notice` (новая edge-функция)

Единственная поверхность блока. Бот не умеет слать в Telegram сам (токен Telegram живёт только на
сервере) — он просит сервер. Существующие эндпоинты не трогаются (принцип 2).

Вход: `Authorization: Bearer <токен>` + `X-On-Behalf-Of: <telegram id>` для токена бота.
Тело: `{ kind, title?, attempt?, lang?, detail? }`.

```jsonc
{ "kind": "door_waiting", "title": "Weekly sync", "attempt": 1, "lang": "en", "detail": null }
```

Ответ `200`: `{ ok: true, delivered: true, should_leave: boolean, next_reminder_in_s: number|null }`.

**Получатель не приходит из тела запроса** — это всегда человек из `resolveActingIdentity`
(`identity.telegramId`). Поле с чужим id в теле игнорируется: иначе токен бота стал бы рассылкой.

| `kind` | когда шлёт бот |
| --- | --- |
| `door_waiting` | стоит у двери (`attempt: 1` — через 90 с; `attempt: 2` — единственный повтор через 3 мин) |
| `door_denied` | хост отклонил вход |
| `captcha` | на входе капча — бот её не проходит |
| `no_conference_link` | `meeting-current` вернул `reason: "no_conference_link"` |
| `no_owner` | владелец встречи не определился — бот не заходит |
| `no_audio` | самопроверка звука не прошла: запись не начата |
| `recording_lost` | записал, но не смог отдать в Swarm (сеть, токен) |
| `container_died` | контейнер умер посреди встречи |
| `join_failed` | не смог зайти по другой причине (`detail` обязателен) |

### Дверь: повтор ровно один

Расписание задаёт сервер, бот его исполняет: `DOOR_WAIT_SECONDS = 90` (сколько стоять до первого
сигнала), `DOOR_REPEAT_SECONDS = 180` (пауза до повтора), `DOOR_MAX_ATTEMPTS = 2`.
`attempt: 1` → `should_leave: false`, `next_reminder_in_s: 180`. `attempt: 2` → `should_leave: true`,
`next_reminder_in_s: null`. `attempt: 3` → **409, ничего не отправлено**: потолок держит сервер, а не
добрая воля бота. У остальных видов отказа `should_leave: true` всегда — они терминальные, ждать
нечего; `attempt` у них не бывает больше единицы (иначе 400).

### Тексты (T081)

Каталог — `_shared/notice-texts.ts`, по одной паре `en`/`ru` на `kind` (для `door_waiting` — две пары:
`attempt 1` и `attempt 2`). EN приоритетный, `lang` по умолчанию `en`, неизвестный `lang` → `en`.
Подстановки: `{title}` (нет названия → «untitled meeting» / «встреча без названия»), `{detail}`.
Каждый текст обязан сказать **что не так** и **что из этого следует для человека** (запись не идёт).
Полнота каталога проверяется структурным тестом, а не глазами.

## Зависимости

`identity` (кому именно слать — владелец встречи определяется там же).

## Definition of Done блока

| этап | пункт |
| --- | --- |
| 1 | уведомление о двери приходит на живой встрече, куда бота не впустили (проверено вживую) |
| 1 | повтор ровно один, затем выход; бот не висит у двери вечно |
| 1 | тексты заведены на английском и русском (правило проекта: EN приоритетный) |
| 1 | ни один сценарий отказа не завершается молча — проверено по списку |

## Что должен звать потребитель (`meet-adapter` / `orchestrator`)

`waitAdmitted(90_000)` вернул `timeout` → `POST /meeting-notice {kind:"door_waiting", attempt:1}` →
ждать `next_reminder_in_s` секунд → если всё ещё не впустили, `attempt:2` → выйти по
`should_leave`. `denied` → `door_denied`, `captcha` → `captcha`, дальше по таблице видов.
Ответ 4xx/5xx — не повод замолчать: его текст пишется в лог контейнера целиком.
