# Блок: notices

## Назначение

Громкие отказы: всё, где бот мог бы промолчать, обязано дойти до человека. Отдельный блок, потому что
это прямое следствие первого принципа проекта, а не деталь адаптера.

Пользой наружу: владелец встречи узнаёт в Telegram, что запись **не** идёт и почему, — вместо того
чтобы после встречи обнаружить пустую очередь вычитки.

## API-контракт

### `POST /meeting-notice` (новая edge-функция)

Единственная поверхность блока. Бот не умеет слать в Telegram сам (токен Telegram живёт только на
сервере) — он просит сервер. Существующие эндпоинты не трогаются (принцип 2).

Вход: `Authorization: Bearer <токен>` + `X-On-Behalf-Of: <telegram id>` для токена бота.
Тело: `{ kind, meeting_id | meeting_key, title?, lang?, detail? }`.

```jsonc
{ "kind": "door_waiting", "meeting_id": "<uuid из meeting-claim>", "lang": "en" }
{ "kind": "no_conference_link", "meeting_key": "<identity_key из meeting-current>", "title": "Weekly sync" }
```

Ответ `200`: `{ ok: true, delivered: true, attempt, should_leave, next_reminder_in_s }`.
Отказы: `400` (не разобрано; `attempt` в теле; `title` при `meeting_id`), `403` (чужой воркспейс,
не владелец встречи), `404` (встречи нет — сперва claim), `409` (потолок или параллельный вызов уже
отправляет; `should_leave: true`), `502` (Telegram не принял; номер не сгорел), `503` (журнал
недоступен — вслепую не шлём).

**Получатель не приходит из тела запроса** — это всегда человек из `resolveActingIdentity`
(`identity.telegramId`). Поле с чужим id в теле игнорируется: иначе токен бота стал бы рассылкой.

**Привязка к встрече.** Встречные виды несут `meeting_id`: бот к этому моменту прошёл
`meeting-claim`. Сервер проверяет, что встреча из воркспейса агента и что уведомляемый — её
владелец (`claim_owner`); название берётся из встречи. До-встречные виды (`no_conference_link`,
`no_owner`) случаются раньше claim — несут ключ календаря и своё `title`.

| `kind` | привязка | когда шлёт бот |
| --- | --- | --- |
| `door_waiting` | `meeting_id` | стоит у двери 90 с; второй вызов через 3 мин — единственный повтор |
| `door_denied` | `meeting_id` | хост отклонил вход |
| `captcha` | `meeting_id` | на входе капча — бот её не проходит |
| `no_conference_link` | `meeting_key` | `meeting-current` вернул `reason: "no_conference_link"` |
| `no_owner` | `meeting_key` | владелец встречи не определился — бот не заходит |
| `no_audio` | `meeting_id` | самопроверка звука не прошла: запись не начата |
| `recording_lost` | `meeting_id` | записал, но не смог отдать в Swarm (сеть, токен) |
| `container_died` | `meeting_id` | контейнер умер посреди встречи |
| `join_failed` | `meeting_id` | не смог зайти по другой причине (`detail` обязателен) |

### Потолок держит сервер

Номер отправки считает сервер по журналу `meeting_notices` и занимает его **до** отправки
(уникальный индекс: из одновременных вызовов уходит одно сообщение). Присланный `attempt` → 400.
`DOOR_WAIT_SECONDS = 90`, `DOOR_REPEAT_SECONDS = 180`, `DOOR_MAX_ATTEMPTS = 2`: первый вызов
двери → `should_leave: false`, `next_reminder_in_s: 180`; второй → `should_leave: true`; третий и
дальше → 409. Прочие виды — по одному на встречу. Сверху: 6 на встречу, 30 на человека за сутки,
из них до-встречных 6 (их ключ сервер не проверит). Недоставленное помечается `failed` и номер
не занимает.

### Тексты (T081)

Каталог — `_shared/notice-texts.ts`, по одной паре `en`/`ru` на `kind` (для `door_waiting` — две пары:
`attempt 1` и `attempt 2`). EN приоритетный, `lang` по умолчанию `en`, неизвестный `lang` → `en`.
Подстановки: `{title}` (нет названия → «untitled meeting» / «встреча без названия»), `{detail}`.
Каждый текст обязан сказать **что не так** и **что из этого следует для человека** (запись не идёт).
Полнота каталога проверяется структурным тестом, а не глазами.

## Зависимости

`identity` (кому именно слать — владелец встречи определяется там же).

## Definition of Done блока

| этап | пункт |
| --- | --- |
| 1 | уведомление о двери приходит на живой встрече, куда бота не впустили (проверено вживую) |
| 1 | повтор ровно один, затем выход; бот не висит у двери вечно |
| 1 | тексты заведены на английском и русском (правило проекта: EN приоритетный) |
| 1 | ни один сценарий отказа не завершается молча — проверено по списку |

## Что должен звать потребитель (`meet-adapter` / `orchestrator`)

Сперва `meeting-claim` (он даёт `meeting_id`), потом заход. `waitAdmitted(90_000)` вернул `timeout`
→ `POST /meeting-notice {kind:"door_waiting", meeting_id}` → ждать `next_reminder_in_s` секунд →
если всё ещё не впустили, тот же вызов ещё раз → выйти по `should_leave`. `denied` → `door_denied`,
`captcha` → `captcha`, дальше по таблице видов. Ответ 4xx/5xx — не повод замолчать: его текст
пишется в лог контейнера целиком. Потребителя в `bot/` пока нет (оркестратор не построен).
