# Блок: orchestrator

## Назначение

Долгоживущая служба: поднимает контейнер на встречу, гасит после, шлёт heartbeat. Отдельно от
контейнера, потому что живёт дольше одной встречи и обязана переживать её падение.

Для MVP достаточно ручного запуска по приглашению из веба (D017); автозапуск по календарю — следующий этап.

## API-контракт

```ts
export async function startForMeeting(joinUrl: string, platform: Platform, onBehalfOf: number, invite?: { id: string; joinUrl: string }): Promise<ContainerId>;
export async function stop(id: ContainerId): Promise<void>;
```

Вход — служба `orchestrator-main.ts`: опрашивает `POST /meeting-invite` (токен агента, без
`X-On-Behalf-Of`) и по каждому приглашению зовёт `startForMeeting(..., invited_by, invite)`;
площадка без адаптера — `join_failed` позвавшему (EN+RU), контейнер не поднимается.

Живёт **внутри WSL2** рядом с Docker, управляет контейнерами через dockerode. Границу Windows/WSL2 не
пересекает.

## Зависимости

`container` (что поднимать), `swarm-client` (чем ходить на сервер), `conference-link` (откуда берётся
ссылка и площадка).

## Definition of Done блока

| этап | пункт |
| --- | --- |
| 1 | контейнер поднимается по ссылке и гасится после встречи |
| 1 | контейнер умер посреди встречи → heartbeat прекратился, существующий watchdog это видит |
| 1 | два контейнера одновременно не мешают друг другу |
| 1 | брошенных контейнеров не остаётся: проверено после падения оркестратора |
| 2 | автозапуск по календарю: бот приходит на встречу сам |

## T159

**2026-09-28 · сделан, ветка `fix/claim-seconds-ceiling`, ждёт приёмки.**

Что сделано. Заявка claim на уже существующую встречу проверяется по серверному времени встречи
(`meeting-claim/claim-clock.ts`): секунды не больше прошедшего от более раннего из `started_at`
(прислал первый заявитель) и `created_at` строки, ×1.1 и +300 с на раннее начало записи; сверх —
урезаются, и урезанные идут в арбитраж, в строку встречи (занятие, перехват, запасная) и в `recorders`.
Более раннее из двух — потому что рекордер заявляется на стопе (строка после встречи), а бот — до
захода (строка раньше начала). Запас 300 с, а не 10 минут склейки: при запасе S заявка сразу после
конца встречи длиной D перебивает держателя при D ≤ (S−300)/0.4, то есть при 300 — никогда.

Проверено. Юнит `claim-clock.test.ts` (ядро, 6) — до кода красный, порчи «якорь — позднее время»
и «без потолка» — по 2 красных. Живой контур (Supabase 4410–4413, функции 4414–4419):
`scriba-watchdog-smoke.ts` — 45 ожиданий зелёные, порча «без потолка» — 2 красных;
`scriba-same-owner-smoke.ts` — 25 зелёные. `scripts/check` — зелёный.

Открыто, решать не мне:
- Потолок — ограничение сверху, не мера длины: заявка много позже встречи (досылка из карантина)

  перебить держателя. Закрыть до конца может только серверно измеренная длина записи (длина аудио в

- Истёкший лиз без стенограммы — встреча брошенная, её занимает любая заявка независимо от секунд
