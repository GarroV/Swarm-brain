# Блок: identity

## Назначение

Даёт `scriba` законную личность на сервере: он приходит со своим токеном, но действует **от имени
человека**. Отдельный блок, потому что это единственное место, где расширяется авторизация, — вся
новая власть собрана здесь и здесь же накрыта блокирующими тестами. Корень графа: без него ни один
серверный вызов бота не проходит.

## API-контракт

```ts
// _shared/agent-auth.ts
export type TokenKind = "recorder" | "recorder_prev" | "mcp" | "bot";
export interface AgentIdentity { telegramId: number; groupId: string | null; kind: TokenKind }

export async function resolveActingIdentity(
  supabase: SupabaseClient, req: Request, onBehalfOf?: number,
): Promise<AgentIdentity>;
```

Подмена личности происходит **один раз, на входе**. После неё `identity.telegramId` — человек, и весь
существующий код (десять мест в `meeting-claim`, проверка владельца в `meeting-ingest`, запись статуса
в `meeting-heartbeat`) продолжает работать без правок.

Хранение: **отдельная таблица служебных агентов** (не `allowed_users` — это таблица людей, служебная
строка в ней молча сделала бы бота сотрудником в выборках команды).

## Зависимости

Продуктовых блоков нет — корень графа. Внешнее: существующая `_shared/agent-auth.ts`, таблица
`allowed_users`, Supabase.

### T015: что сделано и откуда продолжать

Живого прогона рекордера (`bumblebee`) не было и в этой копии быть не может: это macOS-приложение,
пишущее реальный звук в ПРОД-эндпоинты, а прод трогать запрещено. Что вместо этого **уже доказано**:

- `resolveActingIdentity` отдаёт токену рекордера ту же личность, что и раньше (тест «личный токен
  рекордера работает как раньше»), и `verifyAgentToken` без подмены — тоже;
- ни один существующий запрос рекордера не несёт заголовка `X-On-Behalf-Of`, поэтому ветка отказа
  на него для рекордера недостижима;
- heartbeat человека пишет ровно те же пять полей в `allowed_users` (тест на состав патча);
- `deno check` по ВСЕМ функциям зелёный, 670 тестов зелёные.

**Чего не хватает и как доделать.** Стенд для настоящего прогона поднят и почти доведён:
`docker compose -p scriba-identity` в scratch-каталоге блока держит `supabase/postgres` на порту
54100 (миграции накатываются циклом по `mig-list.txt`) и `postgrest` на 54101. Осталось:
1. дождаться готовности БД (контейнер пересоздавался, база `swarm` не накатилась — повторить цикл миграций);
2. засеять воркспейс, человека с `recorder_token_hash` и агента в `service_agents`;
3. поднять обработчик подменой `Deno.serve` на порт из диапазона 54100–54119 и прогнать:
   запрос рекордера (как есть) → строка `allowed_users.recorder_last_*`; запрос агента с
   `X-On-Behalf-Of` → строка `service_agents`, `allowed_users` НЕ тронута; `meeting-claim` агентом →
   `claim_owner` = человек.
Ключ service_role лежит в `service_key.txt` в scratch-каталоге блока (локальный, к проду отношения не имеет).
