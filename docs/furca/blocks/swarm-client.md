# Блок: swarm-client

## Назначение

Клиент пяти эндпоинтов Swarm и очередь выгрузки: то, ради чего бот вообще существует — отдать запись в
конвейер. Отдельный блок, потому что контракт с сервером и логика ретраев не должны зависеть от того,
какая площадка была на той стороне.

Эталон поведения — `bumblebee`: его `SwarmClient.swift` и `UploadQueue.swift` (818 строк чистого
протокола) переписываются на TypeScript. Переносится **контракт, а не код**.

## API-контракт

Потребляет: `GET /meeting-current`, `POST /meeting-claim`, `POST /meeting-ingest`,
`POST /meeting-heartbeat`, `GET /meeting-status`.

Предоставляет оркестратору:

```ts
export interface RecordingSession {
  claim(): Promise<"transcribe" | "defer">;
  pushAudioPart(part: Blob, offset: number): Promise<void>;
  finish(timeline: SpeakerSpan[]): Promise<void>;
  heartbeat(): Promise<void>;
}
```

Собирает таймлайн говорящих из периодических опросов `activeSpeaker()` и отдаёт его в `meeting-ingest`
полем `speakers`.

## Зависимости

`identity` (токен и подмена личности), `ingest-speakers` (формат таймлайна), `meet-adapter`
(источник активного говорящего).

## Внутреннее устройство

| файл | что держит |
| --- | --- |
| `contract.ts` | форма запросов и ответов пяти эндпоинтов; имена полей — как на проводе |
| `errors.ts` | `SwarmHttpError` / `SwarmTransportError`, `isTransient` (5xx и 429 — да, прочие 4xx — нет) |
| `retry.ts` | `withRetry`: full-jitter бэкофф, `Retry-After` уважается; сон и случайность внедряются |
| `client.ts` | `SwarmClient` — пять вызовов, `Authorization: Bearer` + `X-On-Behalf-Of` |
| `speakers.ts` | `spansFromSamples` (чистая) + `SpeakerTimelineCollector` — опросы `activeSpeaker` |
| `queue.ts` | `UploadQueue` — папка на встречу, `meta.json`, ретраи между запусками, dead-letter |
| `session.ts` | `RecordingSession` — сборка claim → части → finish; ворота `defer` |
| `testing/fake-swarm.ts` | фальшивый сервер пяти эндпоинтов для тестов (правила списаны с серверного кода) |

Личность: токен бота (`kind: "bot"`) сам по себе прав не даёт — каждый запрос несёт
`X-On-Behalf-Of: <telegram_id>` человека, от имени которого действует бот.

**Ворота `defer`.** Решение арбитража живёт в сессии: `pushAudioPart` и `finish` на отклонённой
сессии **бросают** `SwarmDeferredError` и в очередь ничего не кладут. Молча вернуть `void` нельзя —
принцип №1 (громкий отказ важнее тихой работы), а вызов `finish` после `defer` — это ошибка
оркестратора, которую надо увидеть, а не замести.

**Очередь.** `pushAudioPart` сразу пишет часть на диск (`<root>/pending/<meetingId>/sys_N.m4a`) —
это и есть локальный бэкап. `meta.json` пишется атомарно (временный файл → `rename`). Грузятся
только запечатанные (`sealed`) записи: незапечатанная — это встреча, которая ещё идёт. Постоянный
сбой (4xx кроме 429) и исчерпанные попытки → `<root>/failed/` (dead-letter), а не тихое удаление.
Успешная выгрузка бэкап не стирает: `202 ≠ обработано`. Стирает его только `meeting-status`,
когда встреча опубликована в базу (`status = "in_base"`), либо потолок в трое суток.

## Definition of Done блока

| этап | пункт |
| --- | --- |
| 1 | все пять эндпоинтов вызываются и их ответы разбираются; контрактный тест со стороны потребителя |
| 1 | `claim` вернул `defer` → аудио не отправляется вообще (проверено тестом) |
| 1 | очередь выгрузки переживает обрыв сети: ретраи с задержкой, локальный бэкап неотправленного |
| 1 | части ≤25 МБ, манифест `[{name, offset}]` совпадает с тем, что принимает сервер |
| 1 | таймлайн говорящих собирается и отправляется; при пустом таймлайне запись всё равно уходит |
| 1 | `bumblebee` не задет: проверено, что формат запроса совместим |

Живым прогоном против двойника сервера (настоящий HTTP на localhost, настоящие файлы на диске):
пять эндпоинтов и разбор ответов, `defer` → ни одного запроса к `meeting-ingest`, обрыв сети с
перезапуском процесса → запись доезжает, манифест `[{name, offset}]`, `speakers` уходит и без него
запись уходит тоже.

Проверки прогнаны на сломанном входе — все четыре порчи покраснели по делу и файлы возвращены
копиями, снятыми до порчи: подмена `sys_parts` на сервере, снятые ворота `defer` (краснеет именно
«запросов к `meeting-ingest` — ноль», а не соседнее утверждение), стирание бэкапа при неудачной
отправке (три проверки сразу), снятая проверка дубля имени части в двойнике.

`bumblebee` не задет: ветка меняет только `bot/src/swarm-client/` и этот файл — в `supabase/` и
`recorder/` ноль изменений. Формат запроса сверяется с их исходниками контрактным тестом.

Открыто, решать не мне:

1. **Способ передачи `speakers` в форме** план не фиксирует. Взято: текстовое поле `speakers` с
   JSON-массивом, как `sys_parts`; ноль времён — начало записи (`offset` 0 первой части `sys`).
