# Направление: готовые решения (FURCA discovery — бот-участник видеовстреч)

Контекст: бот входит в видеозвонок как участник (Google Meet первый этап, далее
Контур.Толк, Zoom), пишет звук целиком, отдаёт в Whisper → тезисы. Стек:
TypeScript/Node + Playwright + Chromium в Docker, Xvfb + PulseAudio null-sink +
ffmpeg. Ищем, что можно переиспользовать/портировать из открытого кода.

Формат записи: находка → ссылка → лицензия → что берём → чем рискуем.
Каждая находка помечена: прочитано целиком / просмотрено по заголовкам.

---

## 1. Vexa (Vexa-ai/vexa) — вход в Google Meet: селекторы, waiting room, отказ хоста

**Прочитано целиком** (три файла TypeScript, не пересказ README):
- https://github.com/Vexa-ai/vexa/blob/main/core/meetings/modules/join/src/googlemeet/selectors.ts
- https://github.com/Vexa-ai/vexa/blob/main/core/meetings/modules/join/src/googlemeet/join.ts
- https://github.com/Vexa-ai/vexa/blob/main/core/meetings/modules/join/src/googlemeet/admission.ts

**Лицензия:** Apache License 2.0 (репозиторий помечен `apache-2.0` через GitHub API; файл `LICENSE` в корне репо). Разрешает копирование/модификацию с сохранением уведомления об авторстве — можно портировать код напрямую.

**Что нашёл (конкретно, с указанием строк/логики):**

- **Стек и структура ровно наш**: TypeScript + Playwright, отдельный модуль `core/meetings/modules/join/src/googlemeet/` на площадку, есть `join.ts` (флоу входа), `selectors.ts` (только константы-селекторы, без логики — явно вынесено, чтобы не путать раздельные контексты выполнения), `admission.ts` (отдельно классификация «впустили/отказали/ждём»). Это готовая референсная декомпозиция для нашего адаптера `join/waitAdmitted/isAlone/leave`.

- **Селекторы кнопки входа** (`googleJoinButtonSelectors` в selectors.ts): порядок — сначала XPath `//button[.//span[text()="Ask to join"]]`, затем `button:has-text("Ask to join")` → `"Join now"` → `"Join"`, и в конце широкий структурный бэкстоп `button[jsname]:not([aria-label]):has(span)` (ловит кнопку без текстовых селекторов, но ТОЛЬКО последним по счёту — комментарий в коде прямо предупреждает не менять порядок, иначе структурный селектор перехватит клик раньше точного текстового). Отдельно есть `googleAuthJoinCtaSelectors` для случая, когда бот залогинен в Google-аккаунт (там кнопка — «Join now» / «Switch here» / «Ask to join»).

- **Локализация — решённая ими проблема, которую мы бы наступили сами**: текстовые селекторы `has-text("Ask to join")` работают только на английском UI. Раньше у них было падение на венгерской локали (issue #856/#917, комментарии в коде дают номера prod-инцидентов 13951/13952/14018/14153). Решение — принудительно пиннят локаль браузера к `en-US` (`--lang=en-US`, Playwright `context.locale`) И добавляют `?hl=en` в URL встречи (`withPinnedMeetLocale()` в join.ts), чтобы Meet рендерил английский интерфейс детерминированно, а не полагались на угадывание виджета. Отдельный «структурный CTA-скан» (`findLobbyPrimaryCta`, ищет единственную видимую кнопку без иконки-глифа и с текстом ≤48 символов) сейчас работает ТОЛЬКО как диагностика (никогда не кликает) — по их же решению (issue #856/#917), потому что уникальность кнопки не гарантирует, что это правильная кнопка.

- **Ввод имени** (`googleNameInputSelectors`): порядок тоже locale-agnostic-first — структурные `input[jsname][type="text"]` / `input[type="text"]:not([aria-hidden="true"])` идут раньше английского `input[aria-label="Your name"]`.

- **Waiting room vs отказ — главное, что нам нужно для `waitAdmitted()`**:
  - `googleWaitingRoomIndicators` — тексты вида `"Asking to be let in..."`, `"You'll join the call when someone lets you in"`, `[aria-label*="waiting room"]`. Отдельно занятный баг-фикс (issue #471): кнопка «Return to home screen», которая показывается на экране ожидания, раньше была ошибочно в списке индикаторов ОТКАЗА — из-за этого бот ложно считал себя отклонённым через ~4 секунды вместо того чтобы ждать хоста. Исправлено переносом в waiting-индикаторы.
  - `googleRejectionIndicators` — явные тексты отказа (`"denied your request"`, `"weren't allowed to join"`, `"not admitted"`) ОТДЕЛЕНЫ от двусмысленных («Meeting not found», кнопки Try again/Retry), потому что вторые могут означать капчу/бот-детект, а не решение хоста.
  - `classifyGoogleRejection()` в admission.ts — двухпроходная классификация: 1) явный текст отказа хоста побеждает всегда, даже если на экране есть reCAPTCHA-виджет; 2) двусмысленный индикатор + ЖИВАЯ reCAPTCHA (видимый iframe размером с виджет, не invisible-скоринг-фрейм) → трактуется как бот-детект, а не отказ хоста, и бот остаётся на странице до `CAPTCHA_SOLVE_GRACE_MS = 120_000` мс, чтобы человек/агент решил капчу вручную (через VNC/CDP); после истечения окна — терминальный отказ `captcha_unsolved`. Это прямой ответ на наш пункт про бот-детект: Google действительно показывает reCAPTCHA Enterprise ботам, и у них есть explicit fallback на решение капчи человеком, а не автоматика.
  - Позитивный сигнал «впустили» — НЕ просто «нет индикатора отказа», а `countRealParticipantTiles()`: считает `[data-participant-id]` тайлы, ИСКЛЮЧАЯ tile с лейблом "visual effects/backgrounds and effects" (это тайл собственного превью-эффекта, который есть даже в лобби и раньше давал ложный «уже впущен» — зафиксировано как живой баг, проверено 2026-06-12 против списка участников хоста).

- **Хрупкость адаптера — история issues подтверждает, вёрстка Meet меняется, надо закладывать частые правки**: в самом коде — множество комментариев со ссылками на конкретные issue-фиксы (#471, #454/#429 про Gemini "take notes for me" consent-gate, #840, #844/#846, #856/#917 про локаль). Т.е. Vexa сама фиксирует, что список селекторов регулярно ломается и чинится точечными PR — заложить у себя тот же процесс (централизованный файл селекторов + тест на валидность каждого селектора, у них это `src/shared/selector-validity.test.ts`, гоняет CSS-парсинг каждого массива).

- **"Humanized" ввод против детекта синтетического инпута**: в join.ts прямо написано — «Google Meet now blocks browser-synthetic input (Playwright/CDP clicks have isTrusted=false and no real pointer movement)», поэтому для `platform === "google_meet"` по умолчанию включён режим `"humanized"`: клики идут не через Playwright `.click()`, а через реальный OS-level XTEST-инпут (`xdotool`) с траекториями мыши, записанными заранее (`HumanizedInteractor`, `MOCAP_LIBRARY` — библиотека "motion capture" траекторий). Требует `xdotool` + X-дисплей в образе бота; при отсутствии — тихий fallback на синтетический клик с логом-предупреждением. **Это прямой, конкретный ответ на пункт "детект ботов площадками" из задания: Meet отличает isTrusted=false клики и это уже приводило к проблемам у них.**

**Что берём:** структуру модуля (selectors.ts / join.ts / admission.ts как отдельные файлы), сам список селекторов и порядок их проверки (портировать, не копировать один в один — у нас нет их лицензионных проверок и телеметрии), идею locale-pinning (`--lang=en-US` + `?hl=en`), идею `countRealParticipantTiles` с исключением self-tile, двухпроходную классификацию рекапчи vs отказ хоста, и саму идею "humanized" клика через xdotool как задел на случай, если синтетические клики Playwright начнут отклоняться Meet.

**Чем рискуем:** это моментальный снимок верстки Meet на 2026 год — комментарии в коде сами предупреждают, что классы вроде `Oaajhc`/`HX2H7`/`wEsLMd` (см. следующую находку про active speaker) обфусцированы и будут меняться. Портировать код — не значит один раз скопировать и забыть, нужен тот же процесс регулярного починки + тест на валидность селекторов.

## 2. Vexa — конкретный гоча: Meet прячет тулбар без реальных движений мыши, и это ломает детект admission

**Прочитано целиком** (продолжение того же файла): https://github.com/Vexa-ai/vexa/blob/main/core/meetings/modules/join/src/googlemeet/admission.ts (функция `checkForGoogleAdmissionIndicators` и `waitForGoogleMeetingAdmission`).

**Лицензия:** Apache-2.0 (см. находку 1).

**Что нашёл:** Google Meet автоматически прячет тулбар звонка (mic/camera/present/leave) после нескольких секунд отсутствия активности указателя — а бот никогда не двигает "настоящую" мышь. Из-за этого, особенно когда кто-то демонстрирует экран (это дополнительно перестраивает chrome интерфейса), все селекторы тулбара возвращают `isVisible:false`, и бот ошибочно решает "не впущен", хотя реально сидит в звонке (баг воспроизведён вживую: митинг идёт, виден "X (Presenting)", 0 транскриптов). Фикс — синтетическое движение мыши перед каждой проверкой (`page.mouse.move(640,360)` → `page.mouse.move(960,540)`) чтобы "разбудить" UI и сделать `isVisible()` снова информативным. Отдельно: за структурные селекторы (`[data-participant-id]`, `[data-self-name]`) они используют факт присутствия в DOM (count>0), а не видимость — потому что эти узлы не участвуют в авто-скрытии тулбара, в отличие от кнопок.

Также в этом же файле — Gemini "take notes for me" consent-gate (issue #429): если участник включил в звонке Gemini-заметки, Meet показывает диалог согласия, который перекрывает управление звонком, но кнопки тулбара уже видны позади него — бот должен НЕ засчитывать это как "admitted" (иначе получаем "status active, 0 transcriptions"), и НЕ кликать на диалог автоматически (согласие — решение человека), а эскалировать на `needs_human_help`.

**Что берём:** обязательно заложить периодическое синтетическое движение мыши в цикл проверки `waitAdmitted()`/`isAlone()` — иначе тот же класс ложноотрицательных срабатываний неизбежен и у нас. Идею "presence, не visibility" для структурных индикаторов.

**Чем рискуем:** это точечный фикс под конкретное поведение Meet 2026 года; нет гарантии, что подход перенесётся на Контур.Толк или Zoom без переработки — там своя вёрстка и, возможно, другая логика авто-скрытия панели.

## 3. Vexa — захват звука: НЕ PulseAudio+ffmpeg для транскрипции, а Web Audio API прямо в странице

**Прочитано целиком:**
- https://github.com/Vexa-ai/vexa/blob/main/core/meetings/modules/gmeet-capture/src/gmeet-capture.ts
- https://github.com/Vexa-ai/vexa/blob/main/core/meetings/modules/gmeet-capture/src/pcm-capture.ts
- https://github.com/Vexa-ai/vexa/blob/main/core/meetings/services/bot/entrypoint.sh
- Частично (первые ~400 строк) https://github.com/Vexa-ai/vexa/blob/main/core/meetings/services/bot/src/capture-bridge.ts

**Лицензия:** Apache-2.0.

**Важное расхождение с нашим предполагаемым стеком** (PulseAudio null-sink + ffmpeg): у Vexa звук для транскрипции НЕ пишется через PulseAudio/ffmpeg вообще. Вместо этого:

- Google Meet рендерит звук КАЖДОГО участника как отдельный `<audio>`/`<video>` элемент со своим `srcObject = MediaStream` (это факт устройства Meet DOM, не решение Vexa). `gmeet-capture.ts` находит все такие элементы (`document.querySelectorAll('audio, video')`, отфильтрованные по `!paused && srcObject instanceof MediaStream && getAudioTracks().length>0`) и на каждый навешивает свой `AudioContext({sampleRate:16000}) → createMediaStreamSource → AudioWorkletNode`. Это работает ПРЯМО В СТРАНИЦЕ (browser-context код, инжектится через `page.addInitScript`/`browser-utils.global.js`), а не в ОС.
- PCM-фреймы (Float32Array, блоками по 4096 сэмплов) идут из AudioWorklet (см. `pcm-capture.ts`) через `page.exposeFunction` на Node-сторону бота (`__vexaPerSpeakerAudioData` в capture-bridge.ts) — то есть звук пересекает границу Playwright как обычные данные, а не как файл/поток от звуковой карты.
- **Конкретный пойманный баг, который стоит учесть заранее**: комментарий в коде — "Chrome's autoplay policy can create the [Audio]context SUSPENDED (no user gesture) → the worklet never runs → zero PCM even while people talk", лечится явным `ctx.resume()`. Это ровно тот класс "пишется тишина", который в задании указан как известный риск.
- **Ещё один пойманный баг**: раньше использовали `ScriptProcessorNode`, который в устаревшем виде выполняется в главном потоке — при загруженной странице (рендеринг Meet + несколько параллельных захватов + STT round-trip) буферы дублировались/терялись, что давало слышимое заикание в записи. Замена на `AudioWorkletNode` (выделенный аудио-поток) устранила это (комментарий в `pcm-capture.ts`: "That doubled/overlapping PCM is exactly the 'stutter' heard in the captured audio").
- Каждый элемент захватывается ОТДЕЛЬНО (`index` = стабильный номер потока по `stream.id`) — то есть у них с самого начала звук КАЖДОГО участника раздельный (а не общий микс комнаты), что и даёт им возможность делать point-in-time диаризацию через `gmeet-speakers.ts` (см. следующую находку) — стемпинг имени говорящего прямо на аудио-чанк в момент захвата.
- **PulseAudio у них всё же есть, но для ДРУГОЙ задачи** — озвучки бота обратно в звонок (TTS playback / "speak" путь): `entrypoint.sh` поднимает `pulseaudio --start`, создаёт `module-null-sink sink_name=tts_sink` и `module-remap-source ... source_name=virtual_mic`, что подключается как "виртуальный микрофон" бота для проигрывания TTS в комнату. Комментарий явно говорит: "Voice/capture audio graph (best-effort; only the speak path strictly needs it)" — то есть PulseAudio null-sink нужен ИМ только если бот сам говорит в звонок, не для того чтобы записать чужой звук.
- Отдельно есть модуль `record-chunker` и `recording` (audio-pipeline.ts, recording-codec.ts) — они принимают уже полученный по мосту PCM и складывают/кодируют его для хранения; не читал целиком (см. риски).

**Что берём:** саму идею — если наш бот пишет только через Chromium (без реального аудио-устройства ОС), можно тэпать `<audio>`/`<video>` элементы участников через Web Audio API ПРЯМО в странице и передавать PCM через `page.exposeFunction`, вообще не поднимая PulseAudio null-sink для записи чужого звука. Это устраняет целый класс проблем "тишина/рассинхрон на уровне ОС-аудио", которые обычно бывают у связки PulseAudio+ffmpeg. AudioWorklet вместо ScriptProcessorNode — обязательно, если пойдём этим путём. Если понадобится, чтобы бот сам говорил (TTS) — тогда PulseAudio null-sink пригодится именно для этого, как у них.

**Чем рискуем:** этот способ специфичен для площадок, которые рендерят звук как отдельные HTML media-элементы с доступным `srcObject` (подтверждено для Google Meet). Не проверено, работает ли то же самое в Контур.Толк или Zoom Web — там DOM может не давать прямого доступа к MediaStream участников (например, если рендерится через `<canvas>`/WebRTC внутри Web Component с закрытым shadow DOM, или звук идёт через один смешанный WebRTC-трек). Для Zoom у Vexa есть отдельный `zoom-capture` модуль (не читал целиком, я его не открывал в этом заходе) — сам факт отдельного модуля намекает, что подход для Zoom иной. Это стоит проверить отдельным этапом ресёрча именно под Контур.Толк, а не считать доказанным для всех площадок.

## 4. Vexa — активный говорящий: обфусцированные CSS-классы + структурный self-marker, БЕЗ авто-обучения

**Прочитано целиком:** https://github.com/Vexa-ai/vexa/blob/main/core/meetings/modules/gmeet-capture/src/gmeet-speakers.ts

**Лицензия:** Apache-2.0.

**Что нашёл:**
- Детект «говорит ли участник сейчас» — это поллинг DOM каждые 250 мс (`pollMs ?? 250`), который на каждом тайле `[data-participant-id]` проверяет наличие одного из ЖЁСТКО ЗАШИТЫХ, обфусцированных CSS-классов Google Meet: `Oaajhc`, `HX2H7`, `wEsLMd`, `OgVli` (плюс несколько человекочитаемых алиасов типа `speaking`/`active-speaker` "на всякий случай", которые реально в Meet скорее всего не встречаются). Эти классы — сгенерированные имена (obfuscated build), то есть **гарантированно переименуются при следующей крупной пересборке фронтенда Meet**, и в коде это прямо признано.
- **Важный урок из их истории (прямо в комментарии к коду)**: раньше у них было самообучение — "если известные классы 10 секунд молчат, выучить новый класс как признак речи". Это было УДАЛЕНО, потому что эвристика один раз по ошибке выучила класс, который просто означает "плотная активность у не говорящего", и после этого ВСЕ каналы схлопнулись в одного "говорящего" (комментарий называет это "the all-one-speaker collapse"). Итог: они сознательно вернулись к тому, что при промахе классов участник просто НЕ считается говорящим (безопасный отказ), вместо попытки угадать новый селектор на лету.
- Есть готовый диагностический метод `probeDom()` — снимает структуру live DOM (сколько `<audio>/<video>` с активным audio-треком, привязка каждого медиа-элемента к тайлу участника через `data-participant-id`, кто сейчас "светится" как говорящий) — специально для того, чтобы **разрабатывать более надёжный небутафорский сигнал** (например, состыковать audio-элемент с speaking-тайлом структурно, а не по обфусцированному классу). У них это пока НЕ сделано ("worst case a tile reads as not-speaking… For now detection uses the known classes ONLY").
- Идентификация "это я, бот" — чисто структурная, НЕ по имени: `data-self-name` атрибут на тайле или его потомке, никогда сравнение текста имени. Это устраняет ложные срабатывания из-за смены отображаемого имени бота.
- Имя участника достаётся из `span.notranslate` внутри тайла (текстовый узел), с фильтром на "мусорные" авто-имена вида `Google Participant (spaces/...)` и служебные фразы подсказок ("let participants…", "turn on captions…").
- Итоговый сигнал — не сырой булев "говорит/не говорит" на каждый кадр, а debounced события `onSpeaking(name, isEnd)`: переход в "говорит" и переход в "замолчал" эмитятся один раз на границе состояния, что и используется как "hint" для последующей привязки имени к аудио-чанку (в паре с `gmeet-capture.ts` из находки 3 выше).

**Что берём:** саму архитектуру — раздельный "сырой сигнал" (что видно в DOM) и "решение" (кому приписать голос) как два разных слоя, никогда не мешать их в одну функцию. Идею structural self-detection через `data-self-name`, а не по имени бота. Список классов как отправную точку для проверки на живом Meet (но не как готовый вечный список).

**Чем рискуем:** это САМОЕ хрупкое место во всей находке. Список обфусцированных классов (`Oaajhc` и т.д.) специфичен для конкретной сборки Meet и **точно сломается** без предупреждения при обновлении фронтенда Google — у них у самих в коде прямо написано, что предыдущая попытка "подстраховаться" авто-обучением привела к худшей поломке (весь звонок читался как один говорящий), чем просто честный промах. Разумный вывод для нас: не пытаться городить самообучение поверх CSS-классов, закладывать в план регулярную проверку живым Meet + запасной путь (например, аудио-уровень RMS каждого захваченного per-participant PCM-потока — это уже даёт грубый, но не завязанный на вёрстку сигнал "кто сейчас громче", и Vexa сам считает RMS для другой цели — `rmsOf()` в capture-bridge.ts — так что это дешёвая надстройка).

## 5. Vexa — флаги запуска Chromium: экономия CPU (`--in-process-gpu`) и что НЕ включать против бот-детекта

**Прочитано целиком:** https://github.com/Vexa-ai/vexa/blob/main/core/meetings/modules/join/src/browser-args.ts

**Лицензия:** Apache-2.0.

**Что нашёл (это прямой ответ сразу на два пункта задания — экономия ресурсов и бот-детект):**

- **Экономия CPU, измеренная ими самими**: комментарий в коде — "2026-04-27 measurement (Zoom Web): the gpu-process ran SwiftShader software-WebGL + the software video decoder at ~357% CPU; `--in-process-gpu` folds that into the renderer and drops per-bot demand from ~4.4 cores to ~115%". То есть один флаг `--in-process-gpu` (схлопывает GPU-процесс Chromium в рендерер, убирая отдельный процесс) снизил потребление CPU на бота почти в 4 раза. Также прямо отмечено, что `--disable-webgl`/`--disable-3d-apis` **не помогали вообще** ("were all inert") — процесс GPU хостит ещё и видео-декодер, не только компоузер, так что убирать нужно было именно процесс, а не отдельные фичи.
- Полный список флагов запуска (`JOIN_BROWSER_ARGS`): `--incognito`, `--no-sandbox`, `--disable-setuid-sandbox`, `--disable-features=IsolateOrigins,site-per-process`, `--disable-infobars`, `--disable-gpu`, `--in-process-gpu`, `--use-fake-ui-for-media-stream` (автоматически разрешает запрос доступа к камере/микрофону без диалога), `--autoplay-policy=no-user-gesture-required` (нужно, чтобы AudioContext стартовал не в состоянии `suspended` — иначе, как в находке 3, захват аудио участников не запустится), `--use-file-for-fake-video-capture=/dev/null` (у бота нет реальной камеры — фейковый видеовход из `/dev/null`), `--disable-blink-features=AutomationControlled`, `--disable-features=VizDisplayCompositor`, `--disable-site-isolation-trials`.
- **Явное предупреждение, чего НЕ делать против бот-детекта** (комментарий "Pack F", дата 2026-06-06): раньше добавляли `--ignore-certificate-errors`, `--ignore-ssl-errors`, `--disable-web-security`, `--allow-running-insecure-content` — все они убраны намеренно, потому что "detectable by Google's bot-detection layer and directly cause the 'You can't join this meeting' interstitial on datacenter egress IPs". То есть у них есть подтверждённый факт: Google Meet банит именно по этим флагам (или связанным с ними сигналам) ботов, идущих с дата-центровых IP, и убирание флагов — часть фикса. Вместо `--disable-web-security` для инъекции скриптов используется CDP (`init-scripts` через Chrome DevTools Protocol), которые не зависят от CSP страницы.
- Локаль браузера (`--lang`, `--accept-lang`) пиннится тем же набором аргументов, что описано в находке 1 (issue #856) — вынесено сюда как единственный источник истины, используется и продовым ботом, и debug-харнессом, чтобы они были "byte-identical".

**Что берём:** список флагов как отправную точку для своего Dockerfile/launch-конфига — особенно `--in-process-gpu` (реальная, измеренная экономия ресурсов на инстанс, что прямо отвечает на требование "гасят видео/GPU ради экономии памяти", только тут это скорее экономия CPU, но механизм тот же — не рендерить видео тяжёлым способом), `--use-file-for-fake-video-capture=/dev/null`, и намеренный список того, чего НЕ включать (`--ignore-certificate-errors` и компанию) — это прямая, проверенная информация о бот-детекте Google Meet по датацентровым IP.

**Чем рискуем:** вывод про датацентровые IP означает, что **IP адрес хостинга бота сам по себе является сигналом детекта** — это относится не к коду, а к инфраструктуре (откуда физически будет запускаться контейнер бота). Для нашего продукта это стоит проверить отдельно: если контейнер будет крутиться на обычном облачном/датацентровом хостинге, тот же "interstitial-бан" может сработать независимо от того, насколько аккуратно написан клиентский код.

## 7. Attendee — отключение входящего видео через РОДНУЮ функцию Meet "Audio only" (экономия ресурсов)

**Прочитано целиком:** https://github.com/attendee-labs/attendee/blob/main/bots/google_meet_bot_adapter/google_meet_ui_methods.py (функции `disable_incoming_video_in_ui`, `get_layout_to_select`, `attempt_to_set_layout`, строки 589–780).

**Что нашёл — прямой ответ на пункт "как гасят видео ради экономии памяти":**
- Attendee не глушит видео своими хаками поверх WebRTC, а включает **штатную функцию самого Google Meet** — "Incoming video is set to audio only" (в настройках звонка: кнопка "More options" → "Settings" → вкладка "Video" → опция "Audio only"). **Что берём:** саму идею "просить у площадки честный audio-only режим, если он есть, вместо самодельного заглушения видео" — это и экономичнее, и безопаснее с точки зрения детекта, чем блокировать видео на уровне сети/DOM. Для нашего адаптера Meet стоит проверить: можно ли выставить тот же localStorage-флаг ДО навигации на страницу встречи (через `page.addInitScript`/`context.addCookies`-аналог в Playwright) — тогда отпадает необходимость в хрупких UI-кликах по меню настроек вообще.

**Чем рискуем:** конкретный localStorage-ключ/значение, который включает этот режим, в этом файле не назван (видно только, что он есть и что есть UI-фолбэк) — его нужно найти отдельно (например, поискать по остальной кодовой базе Attendee `bot_controller`/`streaming` или прочитать issue-трекер). Сами селекторы UI-фолбэка (текст "More options", "Settings", кнопка "Video", `li[aria-label="Audio only"]`) — обычная для этого жанра хрупкость к вёрстке Meet, тот же риск, что и в находках 1-2.

## 9. Attendee — ГОТОВЫЙ рецепт PulseAudio null-sink + ffmpeg (ровно наш предполагаемый стек, но у Attendee — через x11grab, не puppeteer/getUserMedia)

**Прочитано целиком:**
- https://github.com/attendee-labs/attendee/blob/main/Dockerfile (базовый образ и системные пакеты)
- https://github.com/attendee-labs/attendee/blob/main/entrypoint.sh (поднятие PulseAudio)
- https://github.com/attendee-labs/attendee/blob/main/bots/bot_controller/screen_and_audio_recorder.py (сам ffmpeg-рецепт)

**Лицензия:** Elastic License 2.0 (см. находку 6) — портируем подход, при заимствовании кода — с уведомлением.

**Что нашёл — это единственная из трёх находок, что реально показывает связку "PulseAudio null-sink + ffmpeg", как в нашем плане:**

- **Базовый образ**: НЕ официальный playwright-образ, а `ubuntu:22.04` (`linux/amd64`), с ручной установкой конкретной версии Google Chrome (`google-chrome-stable_134.0.6998.88`, скачивается по прямой ссылке с их собственного зеркала `build-assets.attendee.dev`, с проверкой sha256 — то есть они сами пиннят и раздают конкретный билд Chrome, а не полагаются на `apt` последнюю версию) + отдельно `chromedriver` той же версии (134.0.6998.88) с sha256-проверкой. Аудио-стек пакетов: `pulseaudio pulseaudio-utils ffmpeg`, плюс ALSA (`libasound2 alsa alsa-utils alsa-oss`), плюс `libavdevice-dev` с пересборкой Python `av==12.0.0` из исходников ("Needed so that webpage streaming using pyav will work"), плюс полный набор `gstreamer1.0-*`. Это заметно более тяжёлый образ, чем у Vexa (которая тэпает звук через Web Audio API в браузере и почти не трогает системный аудио-стек для входящего звука).
- **PulseAudio bring-up** (`entrypoint.sh`) — аккуратно решает конкретные проблемы окружения контейнера: сам выбирает рабочий `XDG_RUNTIME_DIR` (проверяет что текущий кандидат существует, доступен на запись и принадлежит текущему UID; иначе пробует `/run/user/$UID`, иначе создаёт `/tmp/xdg-$UID`), пишет `~/.asoundrc` с `pcm.!default { type pulse }` / `ctl.!default { type pulse }` (это то, что делает ALSA-приложения типа ffmpeg `-f alsa -i default` прозрачно писать через Pulse), стартует свой PulseAudio демон только если `PULSE_SERVER` не задан снаружи (поддержка "общего" Pulse-сервера на несколько контейнеров), ждёт до 5 секунд, пока `pactl info` не отзовётся, и в конце явно выставляет `auto_null`/`auto_null.monitor` дефолтным sink/source, если он есть.
- **Сам захват — один процесс ffmpeg, а не пара "запись экрана" + "запись звука" по отдельности**:
  - audio-only: `ffmpeg -f alsa -i default -c:a libmp3lame -b:a 192k -ar 44100 -ac 1 <file>.mp3`
  - видео+звук: `ffmpeg -f x11grab -framerate 30 -video_size <WxH+10> -draw_mouse 0 -i $DISPLAY -f alsa -i default -vf crop=... -c:v libx264 -preset ultrafast -pix_fmt yuv420p -g 30 -c:a aac -b:a 128k <file>`. Обратите внимание: у нас в задании — m4a/AAC, у Attendee для видео тоже AAC, но для audio-only — MP3, не AAC/m4a; если нам нужен именно m4a, кодек `libmp3lame` тут не образец, зато остальная обвязка (устройство ALSA `default`, `-thread_queue_size` против дропа буфера при высокой нагрузке) — то, что стоит перенять.
  - **Пауза записи** — НЕ останавливает ffmpeg-процесс, а (1) мьютит sink через `pactl set-sink-mute @DEFAULT_SINK@ 1` и (2) закрывает экран сплошным чёрным `xterm`-окном на весь экран (`-bg black -fg black`, без рамки/скроллбара, поверх всего дисплея) — то есть "пауза" физически продолжает писать чёрный кадр + тишину, просто не показывает реальный контент. Это самый дешёвый способ поставить на паузу без пересоздания процесса захвата.
  - **Деградация видео при превышении размера файла** (`degrade_recording_if_file_size_exceeded`) — отдельный, интересный защитный механизм: раз в 60 секунд проверяется размер уже записанного файла, и если он превысил лимит, экран НАВСЕГДА закрывается тем же чёрным xterm (тем самым видео-поток становится по сути пустым/легко сжимаемым, останавливая рост файла от видео, но продолжая писать звук) — обозначено в коде как необратимое решение на всю оставшуюся запись.
  - Постобработка: если файл видео < 3 ГБ, гоняется `ffmpeg -c copy -movflags +faststart` — перемещает `moov atom` в начало файла для потокового воспроизведения без докачки целиком (типичная проблема "видео нельзя перемотать, пока не докачано").

**Что берём:** это самый близкий к нашему изначальному плану референс. Берём: (1) `.asoundrc` + PulseAudio auto_null трюк, чтобы `ffmpeg -f alsa -i default` писал именно то, что играет система, а не микрофон; (2) `-thread_queue_size` на входы ffmpeg (мы упустили бы это и рисковали получить дропы буфера под нагрузкой); (3) идею паузы через мьют sink + чёрный xterm, если нам вообще нужна пауза записи; (4) faststart-постобработку, если формат контейнера это поддерживает (для m4a/AAC аналогичный приём тоже применим); (5) защиту от разрастания файла — полезно, даже если у нас только звук (аудио тоже может течь часами).

**Чем рискуем:** этот рецепт пишет ЦЕЛИКОМ то, что играет в PulseAudio-выходе (весь микс комнаты одним потоком), в отличие от подхода Vexa (находка 3), который различает участников по отдельности ещё на этапе захвата. Если нашему конвейеру Whisper→тезисы важна диаризация по отдельным трекам (а не только общий микс), рецепт Attendee сам по себе такое не даёт — придётся либо доверять диаризации Whisper/pyannote по общему миксу, либо сочетать оба подхода (PulseAudio для целостной записи как фолбэк/архив + Web Audio API для попытки развести по участникам, как у Vexa).

## 10. Patchright (Kaliiiiiiiiii-Vinyzu/patchright) — "необнаруживаемый" форк Playwright: что именно патчит и почему

**Прочитано целиком:** README репозитория https://github.com/Kaliiiiiiiiii-Vinyzu/patchright (секции "Patches" и "Stealth").

**Лицензия:** Apache 2.0 (значок в README; отдельно есть NodeJS-пакет https://github.com/Kaliiiiiiiiii-Vinyzu/patchright-nodejs — то, что нужно для нашего TS-стека, не проверял его LICENSE отдельно в этом заходе).

**Что нашёл:** легитимный, давно живущий проект (создан 2023-11-07, органический рост до 4611 звёзд к 2026-09, не похоже на накрутку — в отличие от находки 11 ниже). Патчит Playwright именно в тех местах, которые площадки используют для детекта автоматизации:
- **`Runtime.enable` CDP-leak** — "the biggest patch". Обычный Playwright для выполнения JS в странице включает CDP-метод `Runtime.enable`, что палится детекторами (см. https://vanilla.aslushnikov.com/?Runtime.enable, на который ссылается README). Patchright вместо этого выполняет JS через изолированные ExecutionContexts, не включая этот домен.
- **`Console.enable` CDP-leak** — патчится полным отключением Console API (то есть `console.log` внутри страницы через Patchright не работает — явный компромисс, о котором README прямо предупреждает).
- **Command-line флаги** — конкретный список, что убрать/добавить относительно дефолтов Playwright: добавить `--disable-blink-features=AutomationControlled` (ровно то же самое, что мы уже видели у Vexa в находке 5 — независимое подтверждение того же приёма), убрать `--enable-automation` (иначе `navigator.webdriver` палится), убрать `--disable-popup-blocking`, `--disable-component-update`, `--disable-default-apps`, `--disable-extensions` (эти дефолтные Playwright-флаги сами по себе являются сигналом "это автоматизация", т.к. обычный пользовательский Chrome их не выставляет).
- Умеет кликать по элементам внутри **закрытых Shadow DOM** (closed shadow roots) — это может быть релевантно, если Контур.Толк или другая площадка рендерит виджеты звонка через Web Components с закрытым shadow root (Vexa/Attendee-код такого не упоминает, но это неизвестность именно для Контур.Толк).
- **Список площадок, которые он проходит** (со слов авторов, включая специализированные антибот-сервисы: Cloudflare, Kasada, Akamai, Shape/F5, Datadome, Fingerprint.com, CreepJS, Sannysoft, Incolumitas и т.д.) — ни Google Meet, ни Zoom, ни тем более Контур.Толк в этом списке НЕ упомянуты явно; это универсальные антибот-тесты, а не подтверждение конкретно для наших целевых площадок.

**Что берём:** сам список "какие CDP-домены и флаги детектируются" — это прямой, конкретный список того, что стоит проверить/пропатчить в нашем Playwright-запуске, независимо от того, будем ли использовать сам Patchright как зависимость или просто повторим эти конкретные флаги (мы уже частично это делаем через находку 5 — `--disable-blink-features=AutomationControlled` у Vexa). Как минимум стоит проверить `Runtime.enable`/`Console.enable` эффект именно на Google Meet бот-детекте, раз Vexa этого не упоминает явно (Vexa решает бот-детект флагами и IP, но не CDP-доменами).

**Чем рискуем:** README на верхнем уровне сильно замусорен спонсорской рекламой прокси-сервисов (NodeMaven, Swiftproxy, RapidProxy, Scrappey) — это нормально для инструментов из scraping-тусовки, но означает, что сам проект монетизируется через такую рекламу, и к качеству/мотивам поддержки стоит относиться спокойно-настороженно, а не как к вендору. Отключение Console API — реальная потеря отладочной информации, если решим использовать Patchright целиком, а не точечно повторить его флаги/приёмы в собственном Playwright-запуске (что, вероятно, безопаснее).

## 11. Внимание: два репозитория "антидетект-браузер" с явно накрученными звёздами — не доверять с ходу

**Просмотрено по заголовку/метаданным, НЕ читал код.** Ссылки: https://github.com/CloakHQ/CloakBrowser (31 501 звёзд, создан 2026-02-22) и https://github.com/jo-inc/camofox-browser (11 062 звёзд, создан 2026-01-26) — оба всплыли в поиске `gh search repos playwright stealth`.

**Почему это тревожный сигнал, а не находка для использования:** оба репозитория набрали десятки тысяч звёзд за 7–8 месяцев существования на нишевую тему "необнаруживаемый браузер" — это статистически аномальный темп роста даже для popular open-source проектов (для сравнения, тот же по духу, реально органический Patchright — находка 10 — набирал звёзды почти 3 года и остановился на 4611). Такой паттерн типичен для звёздной накрутки (fake-star farming), которую иногда используют, чтобы продать вредоносный форк/зависимость или направить трафик на платный SaaS. Я это НЕ проверял глубже (не читал их код, не проверял README целиком) — привожу как предупреждение, а не как вывод "это malware".

**Что берём:** ничего напрямую. Если понадобится "антидетект" библиотека — ориентироваться на проекты с органической историей роста (как Patchright) и репутацией в известных scraping-сообществах, а не на звёзды в поиске GitHub. Проверять `created_at`/`stargazers_count`/скорость роста звёзд как быстрый фильтр перед тем, как тянуть чей-то код в контейнер, который получает доступ к живым видеозвонкам компании.

**Чем рискуем:** это предостережение, а не результат аудита — если эти репозитории всё же легитимны (например, звёзды куплены для маркетинга, а сам код чист), моя пометка излишне осторожна; но при выборе между "проверить глубже" и "предупредить и пропустить" в контексте инструмента, который будет иметь доступ к корпоративным видеовстречам, выбрал предупредить.

## 12. puppeteer-stream (samuelscheit/puppeteer-stream) — готовая библиотека-обёртка "получи webm-поток со страницы", третий способ захвата звука

**Прочитано целиком:** README https://github.com/samuelscheit/puppeteer-stream (секции Installation/Usage/Launch/getStream). Код самой Chrome-расширения реализации не читал (см. риски).

**Лицензия:** нужно проверить отдельно — на странице репозитория GitHub API отдаёт лицензию неопределённой (не Apache/MIT в моём первом запросе `gh search repos`), а README её не указывает явно; перед использованием сверить файл `LICENSE` репозитория (я его не открывал в этом заходе).

**Что нашёл:** это готовая npm-библиотека (`npm i puppeteer-stream`, 460 звёзд, живая — последний пуш 2026-07-06, создана в 2020) ровно под задачу "зайди на страницу и получи её звук/видео как поток", НО специфична для Puppeteer, а не Playwright (у нас в плане Playwright — потребует либо смены библиотеки автоматизации, либо порта техники под Playwright). Механизм — третий, отличный и от Vexa (Web Audio API в странице), и от Attendee (PulseAudio+ffmpeg на уровне ОС): пакет ставит СВОЁ Chrome-расширение (`extensionPath`) в браузер, которое использует `chrome.tabCapture`/аналогичный API, чтобы получить MediaStream всей вкладки целиком (то, что реально играет из динамиков этой вкладки — то есть уже готовый общий микс комнаты, без разделения по участникам), прогоняет через `MediaRecorder` и стримит наружу как `Readable` (Node-поток, `webm`), с настраиваемым `mimeType`, битрейтом, `audioConstraints`/`videoConstraints`. Явно заявлена поддержка headless-режима (`headless: "new"`). Важная деталь из README — **сами авторы прямым текстом в разделе "Recording video/audio from video conferencing calls" рекомендуют для записи созвонов (Zoom/Meet/Teams) готовый сервис Recall.ai**, а не собственную библиотеку "as is" — то есть даже создатель этого инструмента не считает его законченным решением для нашей конкретной задачи, а скорее строительным блоком.

**Что берём:** саму идею "захват через `chrome.tabCapture` + `MediaRecorder` внутри расширения" как ЕЩЁ ОДИН альтернативный путь получения звука, который вообще не требует ни PulseAudio, ни ручного тэппинга каждого `<audio>`-элемента через Web Audio API — это может быть проще в реализации, чем оба других подхода, ценой того, что звук уже смешанный (без разбивки по говорящим на этапе захвата, в отличие от Vexa). Полезно держать в голове как запасной вариант, если связка PulseAudio+ffmpeg или Web-Audio-per-participant у нас забуксует на конкретной площадке.

**Чем рискуем:** библиотека рассчитана на Puppeteer, не Playwright — сам факт использования потребовал бы либо смены автоматизационного фреймворка (что расходится с уже принятым решением по стеку), либо переписывания механики расширения под Playwright (Playwright тоже поддерживает загрузку расширений в persistent context, так что теоретически переносимо, но это доп. работа, которую я не оценивал). Также инжект стороннего Chrome-расширения — это дополнительная поверхность для детекта площадкой ("почему у обычного пользователя стоит незнакомое расширение с правами `tabCapture`") и для нас лицензионный/секьюрити-риск, который не изучен (не читал исходный код расширения).
