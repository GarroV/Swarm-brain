# T110 — покрывает ли официальный Talk API (Контур.Толк) сценарий «встреча → стенограмма в Swarm» без браузерного бота

Issue: GarroV/Swarm-brain#362. Направление: официальный Talk API vs браузерный адаптер (T111), развилка из `docs/furca/spec.md:110`.

## Метод и оговорка по источникам

Официальный developer-портал `developers.kontur.ru` и справочные страницы `support.kontur.ru/talk/*`
недоступны для автоматического чтения: `support.kontur.ru/talk/82708-api` (страница «API — Толк») отдаёт
инструменту WebFetch `403 Forbidden`, а через `curl` — антибот-страницу с обфусцированным JS, внутри
которого обнаружен явный текст, похожий на prompt-injection ловушку для агентов (функции с именами вида
"расчёт летальной дозировки"). Это **не легитимный контент Контура** — я не выполнял и не пересказывал
эту часть, отнёсся к странице как к недоступной и не заходил на неё повторно. Через Wayback Machine
снапшотов страницы тоже нет.

Поэтому основной источник ниже — **официальный OpenAPI-документ самого Talk API** (`title: "Talk API"`,
преамбула: *«Эта документация предназначена для интеграторов. Она описывает работу с платформой
Контур.Толк от имени внешнего приложения с использованием HTTP API»*), найденный не на самом
developers.kontur.ru (туда попасть не удалось), а как файл `talk.public.api-api-2.json`, который
сторонний разработчик приложил к своему открытому репозиторию:
[mdemyanov/ktalk-cli](https://github.com/mdemyanov/ktalk-cli), файл прочитан целиком (523 КБ, скачан и
распарсен как JSON, не только просмотрены заголовки). Это **копия официальной спецификации**, а не
чей-то пересказ — она описывает себя как документацию для интеграторов Контур.Толк с полным текстом
разделов «Начало работы», «Области действия и разрешения», кодами ошибок и т.д. Риск: копия может
отставать от актуальной версии на портале, и сам README репозитория, где я её нашёл, прямо предупреждает
про расхождения между этим файлом и реальным поведением API (см. раздел «Открытые вопросы» ниже) —
поэтому все выводы из неё стоит перепроверить, зайдя на `developers.kontur.ru` под логином владельца
пространства.

Дополнительно как secondary source использованы: README неофициального PHP SDK

## 1. Есть ли API получения записи/стенограммы встречи

Да, официально, и заметно полнее, чем можно было предположить. Из OpenAPI-документа (`paths`):

| Эндпоинт | Что даёт |
|---|---|
| `GET /api/Recordings/{recordingKey}/file/{qualityName}` | скачать сам видеофайл записи, по качеству (рекомендуемое значение `900p`) |
| `GET /api/recordings/{recordingKey}/transcript` | полная транскрипция |
| `GET /api/recordings/{recordingKey}/summary` / `/summary/{summarizationType}` | краткий пересказ (`shortSummary`) или протокол встречи (`protocol`), с временными метками, в JSON |
| `GET /api/recordings/v2/{recordingKey}/summary` | протокол + краткий пересказ + транскрипция одним вызовом |
| `GET /api/Domain/recordings`, `/v2` | список **всех** записей пространства (не одного пользователя), с фильтрами по дате/комнате/названию |
| `GET /api/Domain/recordings/{recordingKey}` | метаданные одной записи |
| `GET /api/Domain/recordings/{recordingKey}/participants` | список участников записи |
| `GET /api/Recordings/{recordingKey}/access` | права доступа к записи |
| `GET /api/domain/conferencesHistory`, `/api/ConferencesHistory/{v2}/{conferenceKey}` | история прошедших конференций и их «артефакты» (нужно для сценария опроса без вебхука) |

**Разметка говорящих есть, и она сильнее, чем у типичного браузерного бота.** Схема транскрипта
(`TalkTranscript` → `tracks[]: TalkTranscriptTrack` → `chunks[]: TalkTranscriptChunk` →
`words[]: TalkTranscriptWord`) содержит:
- `speaker` и `diarizedSpeaker` как `TalkUserRef` — то есть говорящий привязан к **профилю пользователя
  Контур.Толк**, а не просто пронумерован ("Спикер 1/2"), как обычно бывает у браузерных ботов, которые
  вынуждены угадывать спикера по активной видео-плитке;
- пословные тайм-коды (`startTimeOffsetInMillis`/`endTimeOffsetInMillis`) и `confidence` на уровне
  слова и всего трека.

Это подтверждено чтением самой JSON Schema внутри официального OpenAPI-документа, не пересказом.

Дополнительно, по сниппетам support.kontur.ru (не прочитано напрямую, см. оговорку выше): «Толк
автоматически создаёт транскрипцию облачной записи встречи... обычно готова в течение нескольких минут
после окончания записи» и «Толк распознаёт спикеров и отображает разговор в виде диалога» — согласуется
с данными схемы.

## 2. Чья запись доступна и нужна ли ручная запись

**Доступ — на уровне всего пространства (домена), не только организатора.** Ключевой факт:
`GET /api/Domain/recordings` — «Получить список записей **пространства**» (не «моих записей»), права —
`application.recording.read`. То есть один API-ключ, выпущенный администратором пространства, даёт
доступ ко всем записям всех встреч в организации, независимо от того, кто их организовал. Это разительно
отличается от сценария Google Meet, где для scriba пришлось городить браузерного бота именно потому, что
официальный API даёт доступ per-organizer/per-OAuth-grant.

**Но запись при этом должна быть включена вручную.** По сниппетам поддержки (не прочитано напрямую —
см. оговорку): «Запись встречи доступна только модератору. Во время записи любой модератор может
поставить её на паузу или полностью остановить»; администратор пространства может полностью отключить
запись в настройках («Управление» → «Пространство» → «Настройки конференций» → «Запись встречи»), но
явных признаков **автозаписи по умолчанию для каждой встречи** не найдено ни в этих сниппетах, ни в
OpenAPI-документе. Модель похожа на «нажми Record», как в Zoom/обычном Meet без спецнастройки — то есть
API решает проблему «как забрать данные», но не проблему «как гарантировать, что запись вообще
включена». Это единственное существенное расхождение с тем, что даёт браузерный бот (browser-бот сам
управляет входом и может форсировать запись независимо от воли участников).

## 3. Аутентификация

Из `components.securitySchemes` официального документа — четыре схемы:

| Схема | Заголовок/механизм | Комментарий из документации |
|---|---|---|
| `xAuthToken` | `X-Auth-Token` | «Авторизация с помощью апи-ключа, **выданного администратором домена**» — это и есть ключ пространства для интеграторов |
| `apiKey` | `X-API-Key` | «Ключ, используемый **внутренними** приложениями» — похоже, не для внешних интеграторов |
| `userSession` | `Authorization: Session {key}` | авторизация через пользовательскую сессию |
| `oauth2` | implicit-флоу через `https://passport.skbkontur.ru/connect/authorize`, scope `profiles` | похоже на SSO для пользовательских приложений, не для серверной интеграции |

Путь получения ключа (описан текстом самого API-документа, раздел «Начало работы»): **любой
администратор пространства** заходит в панель администрирования → вкладка «API-ключи» → «Добавить» →
указывает разрешения (scope) и срок действия. Значение ключа показывается **только в течение часа**
после создания — не будет доступно повторно, только смена настроек. Ключ передаётся в каждом запросе
заголовком `X-Auth-Token` (это же подтверждено отдельно и напрямую прочитанной страницей
[talk.kontur-f.ru/instructions/kljuch-api/](https://talk.kontur-f.ru/instructions/kljuch-api/)).

Области действия (scope) ключа — по названиям из документа: «Профили», «Роли», «Комнаты», «Отчётность»,
«Встречи», «Управление календарями», **«Записи»** (получение информации о записях, изменение, скачивание
и удаление), «Статистика», «Киоски», «Маршрутизация» — на каждую можно выдать «только чтение» или «чтение
и изменение». Для нашего сценария нужны как минимум «Записи» (read) и «Отчётность» (read, для
`conferencesHistory` и вебхуков — точное соответствие scope → `application.webhooks.*` в тексте не
расписано явно, это стоит уточнить на практике).

**Значит от владельца/команды нужно:** чтобы кто-то с ролью администратора пространства Контур.Толк
зашёл в «Управление» → «API-ключи» и выпустил ключ с правами «Записи» + «Отчётность» (+ права на
управление вебхуками, если это отдельный переключатель) — это административное действие внутри
пространства, не разработка.

## 4. Вебхук «запись готова» или только опрос

**Вебхуки официально есть**, с явно описанным в OpenAPI набором событий
(`SkbKontur.Talk.Webhooks.Common.Events.WebhookEventType`, enum ровно шесть значений):

```
recordingCompleted, transcriptionReady,
userConnectedToRoom, userDisconnectedFromRoom,
conferencesStarted, conferencesFinished
```

`recordingCompleted` и `transcriptionReady` — это ровно два события, которые нужны Swarm для триггера
«тянуть стенограмму». Активация двухшаговая (подтверждено телом OpenAPI-описания эндпоинта
`POST /api/Webhooks`): при создании вебхука Толк присылает на указанный URL `{"activationKey": "..."}`,
и события не пойдут, пока не вызван `POST /api/Webhooks/{webhookKey}/activate` с этим ключом — это нужно
учесть в реализации (аналог верификации webhook, как у многих провайдеров). `POST /api/Webhooks`
ограничен **10 запросами в день** (создание новых вебхуков, не приём событий).

Если вебхук не поднимать сразу — есть honest fallback на опрос: `GET /api/domain/conferencesHistory`
(диапазон дат, фильтр по комнате, курсорная пагинация) и `GET /api/Domain/recordings` (тоже с фильтром
по дате). То есть polling как временное или запасное решение тоже реализуем без бота.

Задержка готовности — по сниппетам поддержки (не прочитано напрямую, см. оговорку): запись «обрабатывается
пару минут»; саммари/транскрипт «обычно готовы в течение нескольких минут после окончания записи, при
высокой нагрузке — 1–2 часа». Точных SLA-цифр в самом OpenAPI-документе нет.

## 5. Тарифные ограничения и лимиты

- Общий rate-limit подтверждён и в OpenAPI-документе (раздел кодов ошибок): `429 TooManyRequests` —
  «Превышено ограничение по количеству запросов к API. Ограничение может быть указано в описании
  запроса» — то есть точное число лимита не глобальное, а прописано у части конкретных методов (пример —
  10 запросов/день на создание вебхуков).
- Доступность самих ролей/прав зависит от тарифа: явно в документе — «Если вы не нашли указанных ролей
  или прав доступа в вашем пространстве, возможно они недоступны для вашего тарифа» (со ссылкой на
  `kontur.ru/talk/price/vks`). Не проверено, входит ли scope «Записи»/«Отчётность» в базовый тариф или
  требует более дорогого плана — **нужно свериться с тарифом команды** (открытый вопрос ниже).
  Аналогично есть отдельная (не прочитанная напрямую) страница поддержки про «Превышен лимит
  одновременных записей» — то есть лимит на число **одновременно идущих** записей тоже завязан на
  тариф, но не на объём API-выгрузки как таковой.
- Точных числовых лимитов (запросов/минуту, размер выгрузки и т.п.) в открытом доступе найти не удалось.

## 6. Вывод

**Официальный Talk API покрывает сценарий «человек провёл встречу в Толке → в Swarm появилась
стенограмма» без браузерного бота — при одном обязательном условии: запись встречи должна быть включена
вручную кем-то из модераторов.** Если это условие выполняется (команда взяла за привычку жать «Запись»,
или админ пространства может настоящим образом заставить это делать), то дальше всё решается API:

- один ключ пространства (`X-Auth-Token`, выпущен админом один раз) даёт доступ ко всем записям всей
  организации — не нужен per-organizer OAuth и не нужно, чтобы каждый организатор что-то отдельно
  подключал;
- вебхуки `recordingCompleted`/`transcriptionReady` дают событийный триггер без опроса;
- `GET /api/recordings/v2/{recordingKey}/summary` одним вызовом отдаёт транскрипт + саммари + протокол,
  с диаризацией, привязанной к профилю пользователя Контур.Толк — это даже точнее, чем спикер-разметка,
  которую обычно даёт browser-бот (там спикер обычно угадывается по активной видео-плитке).

**Чего API не даёт по сравнению с браузерным ботом:** он не может сам решить, что встречу нужно
записывать. Scriba в Google Meet заходит в комнату как самостоятельный участник и не зависит от того,
нажал ли кто-то «Record» — Talk API работает только постфактум, после того как запись УЖЕ включена
человеком. Значит вопрос «нужен ли ещё и браузерный адаптер (T111)» сводится не к доступу к данным (тут
API закрывает вопрос полностью), а к вопросу **принуждения к записи**: если в команде запись
пропускают/забывают, T111 всё равно может понадобиться — но не ради стенограммы, а ради гарантии, что
запись вообще произошла. Рекомендация: T110 (интеграция по API) реализуема и достаточна для получения
данных; T111 не обязателен для доступа к контенту, но стоит держать в беклоге как решение проблемы
«никто не нажал запись», если она окажется частой на практике.

## Открытые вопросы владельцу

1. **Нужен административный доступ в пространство Контур.Толк команды.** Кто-то с ролью администратора
   пространства должен зайти в «Управление» → «API-ключи» и выпустить ключ с правами «Записи» (чтение) +
   «Отчётность» (чтение) + управление вебхуками — это займёт минуту, но требует, чтобы такой человек был
   определён и согласился. Без этого ключа ничего из выше описанного не проверить на реальных данных.
2. **Какой тариф у пространства** и включает ли он API-доступ к записям/отчётности (документ явно
   предупреждает, что часть scope недоступна на некоторых тарифах) — нужно свериться с
   `kontur.ru/talk/price/vks` или напрямую в панели администрирования пространства.
3. **Включена ли (и насколько дисциплинированно соблюдается) ручная запись каждой встречи** — если
   команда не жмёт «Записать» стабильно, вопрос «нужен ли T111» переоткрывается, но уже не ради доступа к
   данным, а ради принуждения к записи.
4. **Официальный портал `developers.kontur.ru` и `support.kontur.ru` не читались напрямую** — сработала
   антибот-защита (403 у справки, подозрительный обфусцированный JS с внедрённым текстом на странице
   `/talk/82708-api`, который я не выполнял и не пересказывал). Все выводы про эндпоинты и схемы взяты из
   официального OpenAPI-файла, найденного в стороннем открытом репозитории — стоит когда-нибудь свериться
   вручную, зайдя на портал под логином владельца пространства, особенно на предмет: (а) актуальности
   версии спецификации, (б) точных числовых квот 429, (в) политики автозаписи, которую я не нашёл
   зафиксированной нигде.
5. Неофициальный проект `mdemyanov/ktalk-mcp` в своём README прямо пишет, что включённая туда копия
   OpenAPI-спецификации (`talk.public.api-api-2.json`, тот же файл, что использован в этом
   исследовании) **расходится с реальным поведением API** (пути, формат авторизации, структура ответов) —
   и что с версии 3.0.0 сам проект отказался от ключа `X-Auth-Token` в пользу токена пользовательской
   сессии для части операций. Это сигнал, что при реализации T110 нужен ранний smoke-тест реального ключа
   против реальных эндпоинтов, а не разработка вслепую по документу.
