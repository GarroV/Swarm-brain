# Рекордер: надёжность записи собеседника — Фаза 1 (хирургия корня + оборона)

> Дизайн от 2026-07-15. Повод — инцидент: на реальной встрече рекордер (build 4) перестал писать собеседника и завис на стопе («крестик не вырубает»). Разбор: диагностика по живому процессу (`sample`), git-форензик, research известных багов Core Audio process-tap.

## Проблема (root cause)

Запись собеседника — системный звук через Core Audio **process-tap** (`ProcessTapSystemRecorder` в `SystemAudioCapturer.swift`, macOS 14.4+). Два симптома, одна связка причин:

1. **`AudioDeviceStop()` виснет намертво** в CoreAudio HAL (`__psynch_mutexwait`) → весь стоп зависает: mic не финализируется, `claim`/`flush`/скрытие панели не наступают, UI держит «Отправку», встреча теряется.
2. **Тап тихо перестаёт писать собеседника** во время встречи (IOProc вызывается, но буферы — строго нули), без сигнала пользователю.

**Корневой дефект (в коде, латентный с build 2):** управляющий вызов `AudioDeviceStop`/teardown выполняется на **той же** serial-очереди `swarm.systemtap`, на которую Core Audio доставляет IOProc-буферы. `Stop` ждёт завершения in-flight IOProc, а IOProc не может выполниться, т.к. очередь занята `Stop` → самодедлок. Это классический анти-паттерн Core Audio (тот же класс, что чинили в JUCE `ScopedUnlock` и Chromium `catap`).

**Почему проявилось на build 4 (спусковые крючки):**
- build 3/4 добавили постоянную нагрузку во время записи: панель `LiveNotesPanel` (полупрозрачное окно + бесконечная CoreAnimation + два таймера на `RunLoop.main .common`: 1 Гц и 10 Гц), дефект порядка старта (`AppDelegate` запускает таймеры **и** виджета, **и** панели одновременно), heartbeat-`Task` на переходах `.recording`/`.sending`. Возросшая конкуренция за планировщик → латентный дедлок стал срабатывать.
- Внешние факторы: Bluetooth-выход (смена профиля A2DP→HFP на звонке меняет формат устройства → нули + дедлок; UID при этом не меняется, штатный детект слеп), MacBook Air + аптайм 14 дней (по research — худший профиль для all-zero-бага).

Источники: Apple Dev Forums thread 825780 (all-zero буферы); Chromium `media/audio/mac/catap_*` (fence IOProc до Stop, intentional-leak); JUCE forum 51882 (deadlock на stop/restart); insidegui/AudioCap (LIFO teardown).

## Цель Фазы 1

Рекордер **никогда не зависает** на стопе, **никогда не теряет записанное молча**, и **честно сигналит**, когда собеседник не пишется. Остаёмся на process-tap (миграция на ScreenCaptureKit — Фаза 2, только если Фаза 1 недостаточна). Graceful degradation: в худшем случае теряем часть дорожки собеседника, но не всю встречу и не тишину без предупреждения.

## Изменения

### A. Убрать самодедлок (`SystemAudioCapturer.swift`)
- Разделить очереди: **ioQueue** (`swarm.systemtap.io`) обслуживает только IOProc-доставку (запись в файл, peak, якоря); **controlQueue** (`swarm.systemtap.control`) — все HAL-вызовы (build/start/stop/teardown/rebuild), device-listener, silence-watchdog и мутацию управляющего состояния.
- `AudioDeviceStop` теперь на controlQueue ≠ ioQueue → `Stop` дожидается in-flight IOProc (на ioQueue) без взаимной блокировки. Порядок teardown строго LIFO, продолжаем при ошибке каждого шага (уже так).
- Синхронизация разделяемого состояния: `levelTracker` уже потокобезопасен; `file`/`_firstSampleUptime`/`lastNonSilentUptime` защитить (после `Stop` IOProc гарантированно не вызывается → обнуление `file` безопасно; якоря — под lock или чтение только после `Stop`).
- **Страховка** (уже реализована в `AudioRecorder.stop`): остановку capturer ограничить потолком по времени; зависший teardown-поток при таймауте намеренно «утечь» (паттерн Chromium), стоп продолжается. Свести с разделением очередей.

### B. Не терять собеседника молча (`SystemAudioCapturer.swift`, `AppDelegate.swift`)
- Watchdog нулей: если тап отдаёт нули ≥ N сек при активной записи → (1) **честный сигнал пользователю** «собеседник не пишется» (уведомление + метка в панели), (2) полная пересборка tap+aggregate на controlQueue с потолком по времени.
- Добавить слушатель **смены формата/частоты** текущего output-сабдевайса (`kAudioDevicePropertyNominalSampleRate` / `kAudioTapPropertyFormat`), а не только `kAudioHardwarePropertyDefaultSystemOutputDevice` — на Bluetooth UID не меняется, а формат меняется. На изменение — превентивная пересборка.
- Порог N подобрать так, чтобы не рвать на легитимной тишине (десятки секунд); пересборку не гейтить жёстко только на `realCallActive()`.

### C. Снять триггеры build 4 (`AppDelegate.swift`, `RecorderWidget.swift`/`LiveNotesPanel.swift`)
- Исправить порядок старта записи: не запускать одновременно level-таймеры **и** виджета, **и** панели (сейчас `setState(.recording)` дергает `syncWidget` до `notesExpanded=true`).
- Heartbeat не слать синхронно на переходах `.recording`/`.sending` (моменты старта/стопа тапа — самые хрупкие); оставить периодический + по другим переходам.
- Снизить частоту live-индикатора уровней (10 Гц → ~5 Гц достаточно для полосы).

### D. UX + защита данных (`AppDelegate.swift`, `LiveNotesPanel.swift`)
- Панель заметок скрывать **мгновенно** в `stopTapped()` (не ждать всю цепочку claim→flush). Буфер пометок сохраняется, `flush` уходит когда появится `meetingId`; убрать ранний `return` без `hide()` в `flush()`.
- Live-заметки писать на диск по ходу (append-файл), а не только в память → краш/зависание не съедает пометки; на успешном `flush` — очистка.

### Вне Фазы 1
- Миграция системного звука на ScreenCaptureKit (Фаза 2, если понадобится).
- Фрагментированная запись аудио (moov по ходу), чтобы даже недописанный файл проигрывался.
- Требование macOS ≥ 26.1 (на 26.0 часть багов — сама ОС; у пользователя 26.5.1, неактуально).

## Тестирование

- Смоук на этой машине (Bluetooth-выход, длинная запись): убедиться, что (1) стоп не виснет, (2) watchdog ловит нули и сигналит, (3) пересборка не вешает очередь.
