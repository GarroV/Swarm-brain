**Дата:** 2026-09-18 · **Статус:** согласовано владельцем («вроде окей, на словах, но надо смотреть и щупать… начинай стройку»)
**Решения владельца:** [docs/decisions/2026-09-18-doska-iniciativ.md](../../decisions/2026-09-18-doska-iniciativ.md)
**Эталон поведения:** `~/Documents/workbench/private/swarm/initiatives-board-artifact.html` (вне git: внутренние задачи и имена коллег, репозиторий публичный) — артефакт из Claude под проект «Качество в Европе»
**Опирается на:** [спринты #267](2026-09-08-sprints-design.md) (в проде с 09.09.2026) · issue [#378](https://github.com/GarroV/Swarm-brain/issues/378)

## 1. Что делаем

Вкладка «Спринты» становится местом для больших проектов, которые ведут несколько команд сразу. Сверху в ней переключатель
**пространств**. Пространство — это вкладка доски проектов («Гарро», «Аня», …, «Качество в Европе»).
Внутри пространства всё, что умеет артефакт: спринты со сверкой в середине и переносом по
причине, общий вид «Все инициативы», аналитика, журнал, выгрузка итогов.

Механику спринта не пишем заново. Даты, старт, приёмка кнопкой, снимок `frozen_*`, «в плане /
сверх плана» и отчёт уже в проде (#267). Добавляется: **пространства**, **вид инициатив**,
**ритуал сверки и переноса**, **автоматический следующий спринт**.

Задачи те же самые строки `tasks`. Задача, взятая в спринт «Качества», видна у исполнителя в
«Задачах» и на доске проектов. Закрыл её в одном месте — закрыта везде.

## 2. Термины

| Термин | Что это | Где в коде |
|---|---|---|
| **Пространство** | вкладка доски проектов со своей серией спринтов | таблица `sprints` (имя историческое, это вкладки) |
| **Направление** | проект верхнего уровня во вкладке | `projects`, `parent_id = null` |
| **Инициатива** | подпроект | `projects`, `parent_id ≠ null` |
| **Спринт** | период с датами, статусом и снимком | `sprint_cycles` |
| **Живой спринт** | черновик или идущий; в пространстве не больше одного | `sprint_cycles.status in ('draft','active')` |
| **Состав спринта** | связь задача ↔ спринт; носитель снимка, сверки, переноса, упоминания удалённой | `sprint_items` |
| **Сверка** | отметка в середине спринта: по плану / риск / проблема + комментарий | `sprint_items.check_*` |
| **К переносу** | ручная пометка «не успеваю» с причиной | `sprint_items.to_carry`, `carry_reason` |
| **Ответственный задачи** | **существующий исполнитель**, нового поля нет (решение владельца) | `tasks.assignees`, `assignee_telegram_ids` |
| **Ответственный инициативы** | человек из того же списка + срок | `projects.owner_telegram_id`, `start_date`, `end_date` |

Структура «направление → инициатива» ложится на существующие два уровня доски. Ограничение
глубины (`validateParent`, DB-гард `20260812140000`) не трогаем.

## 3. Жизненный цикл спринта (согласован владельцем 18.09.2026)

**Правило:** в пространстве в каждый момент **один живой спринт**. Держит его БД —
частичный уникальный индекс. Следующий спринт появляется сам при приёмке; выбирать «куда
переносить» не нужно.

1. **Черновик — набор состава.** Три входа, результат один — строка `sprint_items`:
   - **из списка слева** (пул): задачи проектов пространства, ещё не в спринте; по одной или
     галочками пачкой — основной способ;
   - **из «Все инициативы»** кнопкой «в спринт N»;
   - **новой задачей**: «+ задача» внутри инициативы создаёт задачу в этой инициативе и сразу в составе.

   Убрать — крестик: из спринта уходит, в проекте остаётся. Первый спринт пространства —
   кнопкой «+ Спринт» (видна, только когда живого нет).
2. **«Начать спринт»:** всё в составе становится планом (`in_plan = true`).
3. **Идёт:** статусы двигаются; добавленное — «сверх плана»; в день сверки каждый отмечает
   «по плану / риск / проблема»; что не успевает — «к переносу» с причиной.
4. **«Принять спринт»** (только из идущего), одной транзакцией:
   снимок → итоги → **новый черновик** (даты встык: старт = конец + 1, конец = старт + 13,
   сверка = старт + 6, имя «Спринт N · дд.мм — дд.мм») → в него уезжают все незакрытые:
   помеченные — «перенесена вручную» с причиной, остальные — «не выполнена в прошлом спринте».
5. **Разбор и набор нового:** в черновике уже хвосты; добираем по пункту 1 и снова «Начать спринт».

**Удалённая задача** остаётся в составе строкой-упоминанием: название и пометка «удалена»
(решение владельца «просто как упоминание»). В подсчёты «взято / сделано / перенесено» она не
входит и никуда не переносится.

## 5. Модель данных

Одна миграция: `ADD COLUMN`, индексы, триггер, функция приёмки. Бэкфилла нет — единственный
спринт на проде владелец разрешил удалить («Мой текущий спринт можно удалить»); удаление —
отдельной операцией при раскатке этапа 1, задачи при этом не трогаются.

```sql
-- Пространство и день сверки у спринта
alter table sprint_cycles add column if not exists tab_id uuid references sprints(id) on delete set null;
alter table sprint_cycles add column if not exists check_date date;
create index if not exists idx_sprint_cycles_tab on sprint_cycles(tab_id, start_date desc);
-- Один живой спринт на пространство
create unique index if not exists uniq_sprint_cycles_live_per_tab
  on sprint_cycles(tab_id) where status in ('draft', 'active') and tab_id is not null;

-- Сверка, перенос, происхождение, упоминание удалённой, расширение снимка
alter table sprint_items add column if not exists check_status text
  check (check_status in ('ok', 'risk', 'problem'));
alter table sprint_items add column if not exists check_note     text;
alter table sprint_items add column if not exists check_at       timestamptz;
alter table sprint_items add column if not exists check_by       text;
alter table sprint_items add column if not exists to_carry       boolean not null default false;
alter table sprint_items add column if not exists carry_reason   text;
alter table sprint_items add column if not exists carry_at       timestamptz;
alter table sprint_items add column if not exists carry_by       text;
alter table sprint_items add column if not exists carried_from   uuid references sprint_items(id) on delete set null;
alter table sprint_items add column if not exists carried_manual boolean;
alter table sprint_items add column if not exists carry_count    integer not null default 0;
alter table sprint_items add column if not exists frozen_due_date date;
alter table sprint_items add column if not exists removed_title      text;
alter table sprint_items add column if not exists removed_project_id uuid;
alter table sprint_items add column if not exists removed_at         timestamptz;

-- Ссылки у задачи
alter table tasks add column if not exists links jsonb not null default '[]'::jsonb;
alter table tasks add constraint tasks_links_is_array check (jsonb_typeof(links) = 'array') not valid;
-- VALIDATE отдельной командой: NOT VALID берёт тяжёлую блокировку на мгновение,
-- VALIDATE сканирует под лёгкой и не мешает чтениям и записям.
alter table tasks validate constraint tasks_links_is_array;

-- Ответственный и сроки направления/инициативы
alter table projects add column if not exists owner_telegram_id bigint;
alter table projects add column if not exists start_date date;
alter table projects add column if not exists end_date   date;
```

**Триггер упоминания.** `before delete on tasks`: у строк состава этой задачи, ещё не
замороженных приёмкой, записать `removed_title`, `removed_project_id`, `removed_at`. Именно
триггер, а не код: задачи удаляются не только через `deleteTask`, но и напрямую — бот при
работе со встречей (`swarm-bot/handlers/meetings.ts:221`). Код такой путь пропустил бы.

**Функция приёмки** `accept_sprint_cycle(...)` — plpgsql, одна транзакция (§6.4). Приёмка
необратима, и половинчатый результат (спринт принят, хвосты не перенесены) недопустим — у
нынешнего `acceptCycle` из #267 шаги идут отдельными запросами. `SECURITY INVOKER`,
`EXECUTE` отозван у `PUBLIC`/`anon`/`authenticated`, выдан только `service_role` (урок
GHSA-vxrp-599j-46hv: грант на `PUBLIC` наследуется в `anon`).

Почему так:

- **`tab_id on delete set null`**, как `projects.sprint_id`: при удалении вкладки спринты не
  пропадают, а попадают в служебное пространство «Без вкладки» (видно, только если такие есть).
- **`tab_id` допускает NULL** ради старого веба в ночь раскатки (между функциями и вебом). Новый
  веб передаёт его всегда. Уникальность живого спринта на NULL не распространяется.
- **Сверка, перенос и упоминание — в строке состава**: у каждого спринта свои, после приёмки
  строка неизменна, снимок получается сам.
- **`links jsonb`** — массив `{title, url}`. Старое поле `url` не трогаем (его пишут встречи и бот),
  на строке 🔗 считает оба.
- **`carry_count`** — сколько раз задача уже переезжала (решение владельца 18.09.2026, развилка 3).
  Считается при переносе как `предыдущая + 1`, а не рекурсивным обходом `carried_from`: обход стоит
  дороже и нужен на каждой отрисовке строки.
- RLS: новых таблиц нет, на существующих RLS включён без политик (issue #41) — без изменений.
- **Гранты прописываются явно** (`grant select, insert, update, delete on <объект> to service_role`),
  без опоры на автогранты Supabase: с 30.10.2026 они снимаются во всех существующих проектах
  ([changelog](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)).
  `anon` и `authenticated` доступа не получают.

## 6. Правила поведения

### 6.1 Пространство
- Пул, «Все инициативы», аналитика, журнал — задачи проектов вкладки и их подпроектов
  (`projects.sprint_id = tab_id`). Приватные задачи не попадают ни в каком виде.
- `POST /sprint-cycles` проверяет, что `tab_id` из воркспейса (иначе 400) и что живого спринта
  в пространстве нет (иначе 409).

### 6.2 Права
Создать, переименовать, сдвинуть даты, начать, принять — **любой участник** (решение
владельца). Проверку «только админ» с этих роутов #267 снимаем. **Удаление спринта — админ**
(«давай пока оставим, потом ещё поменяем»).

### 6.3 Сверка и перенос — пока спринт не принят
- Отметку сверки ставит и снимает любой участник; повторное нажатие снимает. Пишутся `check_at/by`.
- «К переносу» так же; снятие очищает причину. Причина необязательна; пустая в отчётах — «не указана».
- Причину можно вписать и тем задачам, которые уезжают автоматически, — прямо в окне приёмки
  (решение владельца 18.09.2026, развилка 2). Поле необязательное: не заполнил — задача уезжает как
  раньше. Заполненная причина сохраняется в `carry_reason`, `carried_manual` остаётся `false` —
  «сам отметил» и «вписали при приёмке» в отчётах не смешиваются.
- У закрытой задачи (`done`/`cancelled`) пометка не показывается и при приёмке не учитывается.
- На принятом спринте оба действия → 409.

### 6.4 Приёмка
`POST /sprint-cycles/:id/accept`: TypeScript читает состав, считает итоги (`computeSprintStats`,
под тестами) и параметры следующего спринта (`nextCycleDates`, под тестами) и вызывает
`accept_sprint_cycle`. Функция под блокировкой строки спринта:
1. проверяет `status = 'active'`;
2. замораживает состав (`frozen_*` + `frozen_due_date`) из живых задач; упоминания удалённых остаются как есть;
3. ставит `accepted`, `accepted_at/by`, `stats`;
4. создаёт следующий черновик в том же пространстве;
5. переносит незакрытые (кроме удалённых): `carried_from` = строка этого спринта,
   `carried_manual = to_carry`.

Итоги (`stats`) дополняются ключами, которые показывают баннеры артефакта: `carried_manual`,
`carried_auto`, `check_ok`, `check_risk`, `check_problem`, `removed`, `cancelled`. Классификация «остаётся /
вручную / автоматически / упоминание» — чистая функция `planCarry` (`_shared/tasks/sprint-carry.ts`),
её же логику повторяет SQL; тест сверяет результат функции приёмки на локальной базе с `planCarry`.

### 6.5 Формулы (как в артефакте)
- **Ответственный задачи** для фильтра, сверки, цвета и «по людям» — имена исполнителей;
  нет исполнителя — «Без исполнителя».
- **Отменённая задача — отдельная цифра, вне процента** (решение владельца 18.09.2026, развилка 1):
  `cancelled` не входит ни в «сделано», ни в знаменатель — ни в итогах спринта, ни в прогрессе
  инициативы, ни в KPI. Показывается своим числом «отменено N». Сейчас в #267 она считается
  сделанной, то есть отмена задачи улучшает процент; это меняем (см. §9).
- **Не отмечено** (решение владельца 18.09.2026, развилка 4): задача не закрыта, отметки сверки нет,
  и сегодня уже не раньше дня сверки. До дня сверки молчание нормально и не выделяется.
- **Сколько раз переносилась** — `carry_count` строки состава; показывается начиная с двух.
- **Просрочено:** задача не закрыта и `due_date < сегодня`. KPI «просрочено» — по всем задачам
  пространства; остальные KPI — по текущему спринту.
- **Прогресс инициативы:** готово / всего по её задачам; в виде спринта — по задачам спринта.
- **Текущий спринт** пространства — живой (он один).
- Сортировки аналитики: инициативы — по просрочкам ↓, затем по проценту ↑; люди — по числу
  задач ↓; «где рискуем не успеть» — по сроку.

| `DELETE /sprint-cycles/:id` | админ, как сейчас |
| `PATCH /sprint-cycles/:id/items/:taskId` | **новый**: `check_status`, `check_note`, `to_carry`, `carry_reason`; 409 на принятом |
| `GET /sprint-cycles/:id` | новые поля строк; упоминания удалённых с `removed: true` |

### 7.2 Задачи и проекты
- `POST`/`PATCH /tasks`: `links` — массив ≤ 20, `url` только `http(s)://`, `title` ≤ 200.
  Проверка — чистая `parseLinks` под тестом: ссылка рисуется как `<a href>`, `javascript:` недопустим.
- `POST`/`PATCH /projects`: `owner_telegram_id` (участник воркспейса), `start_date`, `end_date`
  (`start ≤ end`, иначе 400).
- Журнал задач запишет `links` сам (`history.ts` ведёт все поля, кроме исключённых); в подписи
  полей MCP (`analytics-format.ts`) добавляется «ссылки».

### 7.3 Журнал пространства — `swarm-api/space-journal.ts`
`GET /spaces/:tabId/journal?days=1|3|7|all` — одна лента, новые сверху, не больше 800 строк:
`task_history` и `task_comments` задач пространства; события состава (взята в спринт, сверка,
«к переносу», удалена — по `removed_at`); события спринтов (начат, принят с итогом).
**Приватность:** задачи отбираются фильтром видимости списков (`is_private = false OR owner_id = я`) —
журнал не должен стать обходом к чужим приватным задачам. Отдельный тест гварда.

## 8. Интерфейс

Тексты — сразу на двух языках через `dt(ru, en)`. `SprintsScreen.tsx` уже 499 строк: новые виды —
компонентами в `components/tasks/sprints/`, расчёты — чистыми функциями в `lib/`.

### 8.1 Переключатель пространств
Чипы вкладок доски. Выбранное запоминается у человека (`localStorage`). «Без вкладки» — только
если есть спринты без вкладки.

### 8.2 Шапка
Название, «N инициатив · спринт: даты», пять KPI (§6.5).

### 8.3 Навигация
Чипы спринтов пространства, затем «Сверка · спринт N», «Все инициативы», «Аналитика», «Журнал».
Инструменты: фильтр по исполнителю, поиск, «Выгрузить итоги».

### 8.4 Строка задачи (спринт, сверка, «Все инициативы»)
Статус, заголовок, плашка исполнителя с цветом, срок, «спринт N», метки переноса, сверки,
«просрочено», «удалена», «не отмечено», «×N» (переносилась N раз, с двух), 💬 N, 🔗 N,
«к переносу» с полем причины. Клик — `TaskModal`.
В `TaskModal` одно новое поле — **«Ссылки»**, над описанием. Пустое по умолчанию.

### 8.5 Спринт
- **Список** (по умолчанию): направление → инициатива (ответственный, полоска, сделано/всего) →
  задачи спринта; только инициативы с задачами под фильтр. «+ задача в спринт N» внутри
  инициативы. Баннер «идёт · даты» с кнопкой «Принять спринт и открыть следующий» и
  подтверждением «всё невыполненное уйдёт в следующий спринт». В окне приёмки — список уезжающих
  автоматически, у каждого поле причины одной строкой, необязательное.
- **Канбан** — экран #267, переключатель запоминается у человека.
- **Пул слева** — набор состава, только из проектов пространства.
- **Черновик** — «Начать спринт».
- **Принятый** — баннеры итогов («взято, выполнено %, перенесено вручную, ушло автоматически») и
  сверки, строки из снимка только для чтения, с причинами переноса и комментариями сверки.

### 8.6 Сверка
Шкала «старт → сверка → финальные статусы → приёмка → разбор и набор нового» (прошедшее
приглушено, сегодня выделено), баннер со счётом, задачи текущего спринта по исполнителям, три
кнопки, при «риске» / «проблеме» — поле комментария. На принятом — только чтение.
Начиная с дня сверки неотмеченные задачи получают серую пометку «не отмечено», их число стоит в
баннере и у каждого человека рядом с именем: молчание должно быть видно так же, как риск.

### 8.7 Все инициативы
Направление → сворачиваемая инициатива («ответственный · до даты», полоска, «сделано/всего ·
N просроч.») → все задачи с «в спринт N» у тех, что не в текущем. Ответственный и сроки
инициативы правятся по клику на заголовок. «+ задача» внизу инициативы.

### 8.8 Аналитика и журнал
Семь таблиц артефакта в том же порядке (`lib/spaceAnalytics.ts`). Журнал — лента §7.3 с фильтром
периода и группировкой по дням.

### 8.9 Выгрузка итогов
Markdown состава артефакта: принятые спринты с итогами и строками, текущий спринт с метками
переноса, рисков и проблем, прогресс по инициативам. Файл + копия в буфер. Сборка — чистая
`buildSpaceReport` под тестом.

### 8.10 Демо
Решение владельца «сделай его так, как оно есть в артефакте»: демо-пространство по содержанию
артефакта — те же 5 направлений, инициативы, спринт со сверкой, на английском. **Имена людей
выдуманные, формулировки без внутренних деталей Dodo:** демо открывается без входа по ссылке с
публичной витрины. Сид — `supabase/demo-seed.sql`, идемпотентный порядок удаления:
`sprint_cycles` → `projects` → `sprints` воркспейса `demo`.

## 10. Проверка

**Ядро — тесты до кода** (ошибка тихая: неверная цифра или потерянный хвост):
- `planCarry`: закрытые остаются; помеченные — «вручную» с причиной; незакрытые — «автоматически»;
  пометка у закрытой игнорируется; упоминание удалённой не переносится и не считается.
- `nextCycleDates`: встык, 14 дней, сверка + 6, номер N.
- `computeSprintStats`: новые ключи, сверка с ручным пересчётом.
- SQL-функция приёмки на локальной базе: результат совпадает с `planCarry`; повторный вызов → отказ;
  живой спринт в пространстве после приёмки ровно один.
- Триггер: удаление задачи (через `deleteTask` и прямым `delete`) → упоминание в составе.
- `lib/initiatives.ts`, `lib/spaceAnalytics.ts`, `buildSpaceReport`, `parseLinks`.
- Гварды: `tab_id` чужого воркспейса → 400; второй живой спринт → 409; журнал не отдаёт чужую
  приватную задачу; сверка и перенос на принятом → 409; удаление спринта не-админом → 403.

Каждую новую проверку прогоняю на заведомо сломанной копии и убеждаюсь, что она падает с
понятной причиной.

**Остальное — прогоном:** `supabase db reset`; `deno check`, `deno task test`; `npm run build`;
экраны в `next dev` в обеих темах; после раскатки — демо-пространство на проде по демо-ссылке.
