# Единый контракт транскрибаторов — дизайн

> Статус: дизайн (brainstorming). Дата: 2026-07-02. Автор: Claude + владелец.
> Реализация — по этапам через writing-plans. Каждый этап деплоится и проверяется отдельно.

## Overview

**Проблема.** Встречи попадают в систему тремя агентами одного процесса «Захват встреч» — рекордер (`desktop-agent`), Granola, Read.ai — но идут **вразнобой**: у каждого своё хранилище черновика, своё ревью, своя публикация. Это плодит дубль-код (хардкод списка источников в 5-6 местах), путает (две очереди «на согласовании»/«на вычитке»), усложняет добавление новых источников.

**Цель.** Единый флоу для всех источников: **захват → приёмная → вычитка → публикация**. Источник влияет только на метку (`sourceLabel`), не на механику.

**Явные требования владельца (2026-07-02):**
1. **Не потерять текущие встречи** — данные сохранны, опубликованное не трогаем.
2. **Не сломать флоу подключённых сервисов** — рекордер и Granola продолжают работать во время и после рефактора.
3. **Всё через вычитку** — единообразно, без «сразу в базу» (bypass убираем).

**Контекст на 2026-07-02:** Read.ai **отключается** (`READ_AI_ENABLED` off по умолчанию) — его write-путь НЕ переводим на новый контракт, оставляем законсервированным. Приватность pending и провенанс (sourceLabel) уже сделаны ранее.

## Целевая архитектура (вариант A)

- **`meetings`** — единая приёмная (pending) для ВСЕХ источников. Черновик живёт здесь до публикации (`status='awaiting_review'`), тезисы — в `draft_notes_md`.
- **`entries`** — только **опубликованное** (финальный артефакт: поиск, страны, задачи). В pending-состоянии `entries` больше не участвует.
- **Публикация** — единый `POST /agent-meetings/:id/publish`: создаёт `entries` (`entry_type='meeting'`, `confirmed:true`), линкует `meetings.entry_id`, ставит `status='in_base'`.
- **Ревью** — единый `GET /agent-meetings?status=awaiting_review` для всех источников.
- **Реестр источников** `_shared/sources.ts` (`SOURCES` + `sourceLabel()`) вместо хардкода `.in([...])`.

Почему A, а не «всё в entries» (B): рекордеру всё равно нужна `meetings` для durable-транскрибации (transcript, process_state, lease); складывать сырой pending в `entries` до вычитки — смешивать базу с недовычитанным (ровно то, от чего уходим). A даёт чистый `entries` = «то, что в базе».

## Что НЕ трогаем (гарантии сохранности)

- **Опубликованные `entries`** (все прошлые встречи в базе) — структура и данные без изменений. Downstream (поиск, страны, задачи, дайджест) не ломается.
- **Рекордер** (`meeting-claim`/`ingest`/`process`, durable-обработка) — путь почти не меняется; он уже пишет в `meetings`. Продолжает работать как есть.
- **Промпт тезисов** (`TEZISY_CORE`) и **дедуп** (`findDuplicateMeeting`) — уже единые, переиспользуем.

## Миграция данных Granola pending (23 записи в `entries`)

Существующие непроверенные Granola-встречи (`entries` `metadata.confirmed=false`, ~23) **не бросаем**. Два безопасных варианта (решаем на этапе 2, по факту):
- **Предпочтительно — бэкфилл в `meetings`**: разовый скрипт создаёт `meetings`-строки (`status=awaiting_review`, `draft_notes_md`=summary, `source=granola`, `external_id=granola_note_id`, `owner`, `group_id`) для этих 23 и удаляет/архивирует старые pending-`entries`. Идемпотентно, с дедупом.
- **Или обратная совместимость**: оставить старый `PATCH /meetings/:id {confirmed:true}` живым переходный период — 23 pending доработаются старым путём, новые идут новым. Через N дней старый путь ретайрится.

В любом случае: **ни одна встреча не теряется**, публикация обеих очередей работает во время перехода.

## Этапы (инкрементально, каждый — деплой + смоук, откат = прошлая версия функции)

**Этап 0 — реестр источников (чистый рефактор, поведение не меняется).**
`_shared/sources.ts`: `SOURCES` (id → label, kind) + `sourceLabel()`. Заменить хардкод `.in("source",[...])` в swarm-mcp, swarm-bot, swarm-api на реестр. Юнит-тест на реестр. Риск ~0 (поведение то же).

**Этап 1 — единая приёмная для Granola (параллельно старому, ничего не ломая).**
Granola-поллер (`ingestNewGranolaNotesForUser`) пишет НОВЫЕ встречи в `meetings` (`status=awaiting_review`, `draft_notes_md`=тезисы, `transcript`=готовый из Granola, `source=granola`, `external_id=note_id`, `owner`, `group_id`; без durable-транскрибации — тезисы уже есть). Дедуп по `meetings`+опубликованным `entries`. Старый путь (`entries` pending) остаётся живым для уже накопленных 23 — не ломаем.

**Этап 2 — единое ревью и публикация в UI/боте.**
Веб (`useDashboardData`, очередь «на вычитке») и бот-кнопки ревью Granola переключаются на `agent-meetings` (meetings). Публикация Granola — через `POST /agent-meetings/:id/publish` (создаёт entry). Дашборд: две очереди («на согласовании» + «на вычитке») схлопываются в одну.

**Этап 3 — миграция 23 + чистка.**
Бэкфилл 23 старых pending в `meetings` (или дожать старым путём), ретайр `PATCH /meetings/:id {confirmed}`-пути и entries-pending фильтров, убрать двойные хардкоды. Read.ai — заморозить путь (kill-switch уже есть) или удалить.

## Обратная совместимость и откат

- Каждый этап — отдельный деплой; откат = вернуть предыдущую версию edge-функции.
- Этапы 0-1 не меняют пользовательское поведение (0 — рефактор, 1 — новый путь параллельно старому).
- Старый путь публикации Granola живёт до этапа 3 → нет «дыры», где встреча недоступна.

## Тестирование

- Юнит: реестр `sourceLabel`/`SOURCES`.
- Смоук на проде после каждого этапа: рекордер (e2e один звонок), Granola-импорт (новая встреча → вычитка → публикация), дедуп (одна встреча из двух источников не двоится), ревью-очередь (одна, все источники).
- Данные: до/после — счётчики встреч по источникам (не потеряли), 0 pending-утечек.

## Решённые вопросы

- **Manual-save Granola** — убираем bypass, всё через вычитку (владелец, 2026-07-02).
- **Read.ai** — не переводим, отключается.
- **Различимость программы записи** — per-source `sourceLabel` (уже есть); отдельная «3rd-party recorder» метка не нужна.
- **`entries` = финал** — да, унифицируем только вход+ревью, не схлопываем всё в `meetings`.
