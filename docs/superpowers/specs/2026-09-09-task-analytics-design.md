# Статистика по задачам — направление

> Запрос руководства через владельца (09.09.2026): «выгружать статистику по задачам — где, когда,
> куда передвинуть». Плюс уже реализованный запрос коллеги: дайджест изменений по задачам поверх
> MCP (#275 id задачи, #276 свежие комментарии). Владелец: «мы всё равно проводим большую работу
> по введению статистики. На данный момент это всё по спринтам, но по сути нам нужно в целом
> отслеживать задачи: сколько задач, когда начали, когда закончили, сколько у пользователя,
> сколько времени он их вычитывал».
>
> Хенд-мейд документ. Спринтовая часть — [2026-09-08-sprints-design.md](2026-09-08-sprints-design.md),
> её метрики (`computeSprintStats`) не дублируются, а переиспользуются.

## Главное, что нужно знать до планирования: истории почти нет

На проде **`task_history` содержит 2 строки на 2 задачи** (проверено 09.09.2026), при том что
задач десятки и их двигают каждый день. Причина не в чистке данных, а в писателях:

| Поверхность | Писала ли историю |
|---|---|
| Веб (SprintBoard, TaskModal) — основной интерфейс, где карточки тащат мышью | **нет, никогда** |
| Telegram-бот | только в одном сценарии (`swarm-bot/tasks/handlers.ts`) |
| MCP | нет |

Запись «при любой смене статуса» появляется только в ветке `feat/sprints` (этап 1, `_shared/tasks/db.ts`)
и **на прод не раскатана**. Следствия, которые надо сказать руководству прямо:

1. **«Где, когда, куда передвинули» за прошлое восстановить нечем.** Никакого архива перемещений
   не существует; всё, что есть про прошлое — `created_at`, `updated_at` (только последнее
   изменение), `due_date`, `status` на сейчас.
2. **Данные копятся только вперёд**, с момента раскатки записи истории. Поэтому включать журнал
   надо как можно раньше — каждый день без него это безвозвратно потерянная статистика.
3. Часть метрик доступна и без журнала — их можно отдать сразу (см. ниже).

## Что считается уже сегодня (без журнала)

Из `tasks`: `created_at`, `completed_at` (ветка спринтов + бэкфилл), `due_date`, `start_date`,
`status`, `assignees`/`assignee_telegram_ids`, `owner_id`, `project_id`, `sprint_id`, `country`,
`priority`, `confirmed`.

- **Поток:** создано / закрыто за период; в разрезе исполнителя, проекта, рынка, приоритета.
- **Lead time:** `completed_at − created_at` — сколько задача жила от постановки до закрытия.
- **Дисциплина сроков:** доля закрытых до `due_date`; просроченные открытые (`due_date < now`).
- **Текущая картина:** сколько у человека открыто, сколько в работе, сколько в бэклоге.
- **Возраст незакрытых:** `now − created_at` для открытых — «что висит дольше всего».

## Что требует журнала изменений (и потому не считается сейчас)

- время в каждом статусе; **cycle time** (`in_progress → done`) отдельно от lead time;
- «сколько времени до взятия в работу» (`created_at → первый in_progress`) — вероятно это и есть
  «сколько тратил на открытие задачи»; **допущение, требует подтверждения владельцем**;
- сколько раз задачу возвращали (`done → open`), сколько раз переносили срок и на сколько дней;
- смены исполнителя и переходы между проектами/спринтами — «куда передвинули».

## Модель: расширить `task_history` до журнала изменений полей

Сейчас: `task_id, changed_by (text), old_status, new_status, note, created_at`. Узко (только
статус) и `changed_by` — текст, по нему не сгруппировать человека.

Предлагается **ADD-only** расширение той же таблицы, без новой сущности:

| Колонка | Зачем |
|---|---|
| `field` (text) | что изменилось. **Отмечаем ЛЮБОЕ поле задачи** (решение владельца 09.09.2026: «надо уметь всё что угодно отмечать у задач, чтобы потом вытащить можно было») — blacklist, а не whitelist, поэтому новое поле журналируется само. Исключения: служебное (`id`, `group_id`, `created_at`/`updated_at`, `completed_at`) и шум перетаскивания (`tree_x`, `tree_y`, `timeline_position`, `reminded_at`, `assignee_telegram_ids`). Значения обрезаются до 200 символов |
| `old_value`, `new_value` (text) | значения до и после; для статуса дублируют `old_status`/`new_status` |
| `changed_by_telegram_id` (bigint) | человек как ключ, а не как текст (`changed_by` остаётся legacy) |
| `group_id` (text) | воркспейс — чтобы выгрузка не ходила в `tasks` за изоляцией на каждую строку |

Плюс индексы `(task_id, created_at)` и `(created_at desc)`. Старые строки читаются как
`field='status'` — совместимость не рвётся.

**Единственная точка записи — `_shared/tasks/db.ts` (`updateTask`).** Это главное архитектурное
преимущество: веб, бот и MCP уже ходят через неё, поэтому журнал наполнится со всех поверхностей
сразу, без правок в трёх местах и без риска, что одна поверхность «забудет» записать.

## Приватность — часть требований, а не оговорка

Статистика агрегирует в том числе личные задачи. Правило: **в любой выдаче и выгрузке учитываются
только задачи, видимые запрашивающему** — тот же `canViewTask` + воркспейс, что в остальном коде
(`_shared/tasks/access.ts`). Админский оверсайт по задачам (решение 2026-08-21) сохраняется, но
это значит, что сводка «по человеку» для админа включает его личные задачи — **владельцу стоит
подтвердить это отдельно для статистики**, потому что агрегат раскрывает объём личной работы
иначе, чем чтение одной задачи.

## Поверхности выдачи

1. **MCP** (нужно руководству и коллеге для дайджеста):
   - `get_task_stats(period, assignee?, project?, country?)` — агрегаты из раздела «считается сегодня»;
   - `get_task_history(task_id)` — журнал одной задачи;
   - `get_recent_task_changes(since)` — все изменения за период одним запросом, брат `get_recent_comments` (#276).
2. **Веб:** экран «Статистика» + **кнопка выгрузки CSV** — руководство просило именно «выгружать».
3. **Спринты:** `computeSprintStats` остаётся снимком на приёмке; определения метрик берутся из
   общего словаря (ниже), чтобы спринт и общая статистика не считали одно и то же по-разному.

## Словарь метрик (одно определение на метрику)

| Метрика | Определение |
|---|---|
| Lead time | `completed_at − created_at` |
| Cycle time | первый переход в `in_progress` → `completed_at` (по журналу; ✅ `computeFlowTimes`) |
| Time to start | `created_at` → первый `in_progress` (по журналу; ✅ `computeFlowTimes`) |
| Throughput | закрыто задач за период |
| WIP | задач в `in_progress` на момент времени |
| On-time rate | доля закрытых с `completed_at ≤ due_date` (задачи без срока не учитываются) |
| Reopen rate | доля задач с переходом `done → open` (нужен журнал) |
| Due-date slip | сумма сдвигов `due_date` в днях (нужен журнал) |

## Этапы

- ✅ **Э0 — отдать что есть.** MCP `get_task_stats` + `get_task_history` (сделано 09.09.2026,
  ветка `feat/sprints`). Каждая выдача несёт оговорку про дату старта журнала.
- ✅ **Э1 — включить журнал (приоритет).** Миграция `20260909220000_task_history_field_journal`
  (ADD-only) + запись всех отслеживаемых полей в `updateTask`; прежняя вставка из бота убрана,
  иначе события из бота удваивались. Автор изменения прокинут из веба, бота и MCP.
- ✅ **Э2 — `get_recent_task_changes(since)`** для дайджеста руководства (сделано там же).
- **Э3 — экран статистики + CSV** в вебе.
- **Э4 — сводка по человеку/команде за период** (регулярный отчёт руководству).

## Что НЕ делаем

Story points, оценки в часах, графики сгорания — уже отклонены по спринтам. Отдельного
хранилища/DWH не заводим: объёмы (десятки задач, сотни событий) считаются запросом на месте.

## Открытые вопросы владельцу

1. «Сколько времени он их вычитывал / тратил на открытие этих задач» — заложено как
   `created_at → первый in_progress` (сколько задача ждала начала работы) плюс
   `in_progress → закрытие` (сколько пробыла в работе); обе метрики уже считаются
   (`computeFlowTimes`, видны в `get_task_stats`). **Если имелось в виду другое** — например,
   время между открытием карточки в интерфейсе и действием, — это трекинг UI-событий, которого
   нет и который дорог; нужно сказать отдельно.
2. Формат для руководства: достаточно MCP-выдачи (её читает Claude и приносит текстом) или нужна
   именно выгрузка файлом (CSV) / регулярное письмо?
