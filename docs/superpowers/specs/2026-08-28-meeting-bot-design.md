# Бот-участник видеовстреч — дизайн

> Статус: спека написана по итогам брейншторма с владельцем 2026-08-28. Ветка: `feat/meeting-bot-spec`.
> **Стройка отложена** — решение владельца: «сначала давай спеку построй, а сама стройка пойдет позже,
> когда токены будут».
> Хенд-мейд документ (дизайн-спека), не генерируется.

## 1. Проблема и цель

Сегодня звук встречи берётся **с машины участника** — рекордером `bumblebee` (macOS). У этого способа
три врождённых ограничения, и все три сейчас стоят проекту денег:

1. **Нужен мак и установка.** Коллега на Windows записать встречу не может вообще.
2. **Пишется смешанная дорожка.** Системный звук — один общий тап всех удалённых собеседников, поэтому
   «кто именно говорит» физически отсутствует в записанных данных
   ([meeting-processor.ts:395](../../../supabase/functions/_shared/meeting-processor.ts#L395)).
3. **Несколько рекордеров на одной встрече расходятся.** Один созвон даёт несколько строк `meetings`
   и несколько несовпадающих версий тезисов (issues #164, #168; решения
   [2026-08-28-meeting-dedup-scope](../../decisions/2026-08-28-meeting-dedup-scope.md) и
   [2026-08-28-one-meeting-one-record](../../decisions/2026-08-28-one-meeting-one-record.md)).

**Цель:** отдельный бот, который сам заходит в звонок как участник, пишет его целиком и отдаёт аудио
в уже существующий конвейер Swarm — по тем же правилам, что и рекордер.

Бот снимает все три ограничения разом: он пишет всегда и у всех, слышит обе стороны, и — главное —
**он один на встречу**, поэтому расхождения версий не возникают по построению.

> Это прямой ответ на решение владельца №4 от 28.08: «надо продумать какой-то механизм коннекта
> рекордеров во время работы, чтобы они работали синхронно». Один бот вместо N рекордеров — самый
> простой из возможных механизмов синхронизации: синхронизировать нечего.

## 2. Решения владельца (брейншторм 2026-08-28)

| Вопрос | Решение | Дословно |
|---|---|---|
| Что строим | Отдельный бот, сидящий на встрече | «отделный бот который сидит на встрече, да» |
| Площадки встреч | Google Meet, Контур.Толк, Zoom | — |
| Роль относительно `bumblebee` | В перспективе заменяет, на старте работают параллельно | «в перспективе заменяет, но на старте будут параллельно» |
| Переиспользование рекордера | Сделать его ботом, работающим по тем же правилам | «мы можем его сделать ботом? чтобы работал по всем тем же правилам» |
| Площадка размещения | MUSPELHEIM сейчас, Dodo AI Platform потом | «Сервер можео пока сделать на муспельхейм. в будущем может быть переедет на аи хаб» |
| Когда строим | Спека сейчас, стройка позже | «сама стройка пойдет позже, когда токены будут» |

## 3. Что бот наследует даром

Главный вывод анализа: **рекордер не содержит бизнес-логики.** Он тупой клиент, а все правила живут
на сервере. Значит бот, стучащийся в те же пять эндпоинтов, получает их бесплатно:

| Эндпоинт | Что даёт |
|---|---|
| `GET /meeting-current` | какая встреча идёт сейчас (календарь) |
| `POST /meeting-claim` | право транскрибации + арбитраж по полноте |
| `POST /meeting-ingest` | приём аудио → Storage → durable-обработка |
| `POST /meeting-heartbeat` | watchdog: оборванная запись, истёкший токен |
| `GET /meeting-status` | статус обработки, сигнал чистить локальный бэкап |

Вместе с ними приходят: изоляция по `group_id`, приватность (`entries-guard`), дедуп
(`_shared/meeting-dedup.ts`), тезисы (`_shared/tezisy-prompt.ts`), теги рынков, очередь вычитки.

**Формат аудио совпадает один в один.** `meeting-ingest` принимает m4a/AAC, части ≤ 25 МБ
(`OPENAI_AUDIO_MAX_BYTES`), манифест `[{name, offset}]`. Рекордер режет **без перекодирования**
(`AVAssetExportPresetPassthrough`), `ffmpeg -c copy` делает ровно то же. Переписывать нечего.

**Арбитраж работает на бота.** Право транскрибации достаётся более полной записи по `recorded_seconds`,
а на публикации — версии с бо́льшим объёмом распознанного текста
([2026-08-28-one-meeting-one-record](../../decisions/2026-08-28-one-meeting-one-record.md)). Бот сидит
всю встречу и слышит всех, поэтому выигрывает по обеим метрикам без специальной логики.

### Что из кода рекордера переносимо

| Модуль | Строк | Зависимости | Переносим |
|---|---|---|---|
| `SwarmClient.swift` | 300 | только `Foundation` | ✅ протокол целиком |
| `UploadQueue.swift` | 429 | только `Foundation` | ✅ очередь, ретраи, бэкап |
| `SwarmTypes.swift` | 89 | только `Foundation` | ✅ контракт |
| `SystemAudioCapturer.swift` | 710 | `ScreenCaptureKit`, `CoreAudio` | ❌ macOS-only |
| `Segmenter` / `SilenceTrimmer` / `AudioRecorder` | 497 | `AVFoundation` | ❌ |
| `CallDetector` / `BrowserRoom` / `AppDelegate` + UI | ~3 400 | `CoreAudio`, `AppKit` | ❌ |

**818 строк из 5 451 (15 %) — «мозг протокола», остальное завязано на macOS.**

**Решение: переносится контракт, а не код.** Бот пишется на TypeScript (Node) — потому что его
сердце это Playwright, который живёт в экосистеме Node, а не Swift. Переписать 300 строк HTTP-клиента
дешевле, чем тащить Swift-toolchain в Linux-контейнер ради экономии этих 300 строк. Контракт при этом
остаётся единственным источником истины: он описан в `SwarmTypes.swift` и повторяется в типах бота.

## 4. Пять вещей, которых сейчас нет

### 4.1 Сервер не знает, куда заходить 🔴 блокер

[meeting-current/index.ts:71](../../../supabase/functions/meeting-current/index.ts#L71) отдаёт
`identity_key`, заголовок, участников и времена — **и ни одной ссылки на звонок**. Рекордеру она не
нужна: человек уже в звонке. Боту ссылка — единственный способ попасть на встречу.

**Что делаем:** `meeting-current` дополнительно отдаёт `conference: { url, platform }`, извлекая её из
Google-события в порядке: `hangoutLink` → `conferenceData.entryPoints[].uri` → `location` → `description`.
Платформа определяется по хосту: `meet.google.com` → `meet`, `ktalk.ru` / `talk.kontur*` → `kontur`,
`*.zoom.us` → `zoom`. Не распознали — отдаём `null` и **говорим об этом явно** (`reason: "no_conference_link"`),
а не молчим.

> Эта работа уже запланирована как **Фаза B room-match** ([BACKLOG.md:198](../../BACKLOG.md#L198)) —
> там нужен ровно тот же парсинг ссылок. Один блок закрывает две цели.

### 4.2 У бота нет законной личности 🔴 блокер

`AgentIdentity` — это `{ telegramId, groupId }`, а токен привязан к человеку через
`recorder_token_hash` (`_shared/agent-auth.ts`). Если бот придёт со своим токеном, `claim_owner`
станет ботом — и **все встречи команды окажутся «его»**: очередь вычитки попадёт не тому, приватность
посчитается не от того.

**Что делаем:** новый вид токена — **бот, действующий от имени пользователя**.

- Новая колонка токена бота хранится отдельно от `recorder_token_hash` (бот — не рекордер и не должен
  наследовать его grace-логику).
- `verifyAgentToken` возвращает `AgentIdentity` с новым полем `kind: "recorder" | "bot"`.
- Токен бота **сам по себе не даёт прав ни на что** — он обязан указать, за кого действует:
  `POST /meeting-claim` принимает `on_behalf_of: <telegram_id>`, и **только** от токена с `kind: "bot"`.
- Сервер проверяет, что указанный пользователь существует, активен и его `group_id` совпадает с
  воркспейсом встречи. `claim_owner` = `on_behalf_of`, не бот.
- Токен бота живёт в секретах контейнера, не на машинах людей.

**Кого бот указывает как владельца:** организатора календарного события, если он есть в `allowed_users`;
иначе — первого найденного в `allowed_users` участника встречи. Никого не нашли → бот **не заходит** и
пишет об этом в лог и в уведомление, вместо того чтобы записать встречу «ничью».

> Это самая чувствительная часть дизайна: она расширяет авторизацию. Реализовывать — с
> `security-reviewer`, и обязательно с тестом на то, что токен `kind: "recorder"` НЕ может передать
> `on_behalf_of`.

### 4.3 Все реплики станут «собеседник» 🔴 блокер

[meeting-processor.ts:395](../../../supabase/functions/_shared/meeting-processor.ts#L395) размечает
говорящего по дорожке:

```ts
const speaker = p.track === "sys" ? "собеседник" : "я";
```

**У бота микрофона нет** — он не говорит. Весь звук уедет как `sys`, и все реплики всех людей получат
метку «собеседник», а «я» не будет ни разу. Тезисы на таком входе выйдут **хуже**, чем у рекордера.

**Что делаем:** `meeting-ingest` принимает третий вид данных — **таймлайн говорящих**:

```jsonc
// поле speakers: JSON-массив, времена в секундах от начала записи
[{ "start": 0.0, "end": 12.4, "name": "Василий Гарро" }, …]
```

Бот собирает его из DOM звонка (активный говорящий подсвечивается на всех трёх площадках).
`meeting-processor` при сведении сегментов ищет имя по перекрытию интервалов; не нашёл — падает в
текущее поведение (`sys` → «собеседник»), то есть **деградация мягкая**.

Это же закрывает давнюю дыру из [BACKLOG.md:249](../../BACKLOG.md#L249), где сказано, что информации
«кто» в записанных данных нет и нужна диаризация. Бот приносит **настоящие имена** вместо
«Собеседник 1/2/3» — то есть результат лучше, чем у отложенного плана диаризации.

### 4.4 Бот молча стоит у двери 🟡

Waiting room — нормальное состояние, а не сбой. Но без сигнала бот запишет тишину, и узнают об этом
только на вычитке.

**Что делаем:** если бот не впущен за 90 секунд — уведомление в Telegram владельцу встречи: «стою у
двери на <название>, впустите». Повтор один раз через 3 минуты, дальше — молча выходит и помечает
попытку неуспешной. Никаких «тихо записал тишину».

### 4.5 Бот — четвёртый источник дублей 🟡

Решение [2026-08-28-meeting-dedup-scope](../../decisions/2026-08-28-meeting-dedup-scope.md) сознательно
чинит дубли **на публикации, а не на claim**; склейка на claim осталась в issue #168. Бот добавляет
четвёртый способ увидеть встречу (`meet:` / `kontur:` / `zoom:` от бота) поверх трёх существующих.

**Что делаем:** бот **не изобретает свой формат ключа** — он использует ровно те же
`scopeRoomKey(kind, key, startedAt)` и префиксы `meet:<code>` / `kontur:<room>`, что и рекордер
(`_shared/meeting-roster.ts`, `BrowserRoom.swift:112`). Для Zoom добавляется новый префикс `zoom:<id>`
— **в обоих местах сразу**, иначе Zoom-встречи не склеятся ни с календарём, ни между собой.

Пока бот и рекордер работают параллельно (этап 1–2), дубли лечит существующий механизм публикации.
Когда бот станет единственным источником, проблема исчезает сама.

## 5. Архитектура

### 5.1 Контейнер бота — один на встречу

```
┌─ контейнер (эфемерный, живёт одну встречу) ──────────────┐
│  Xvfb :99          — виртуальный экран                   │
│  PulseAudio        — null-sink, виртуальная звуковая     │
│  Chromium          — под Playwright, заходит по ссылке   │
│  ffmpeg            — пишет с null-sink → m4a/AAC         │
│  supervisor (TS)   — адаптер площадки + клиент Swarm     │
└──────────────────────────────────────────────────────────┘
```

Одна встреча = один контейнер. Изоляция обязательна: PulseAudio-sink и дисплей — глобальные ресурсы,
два бота в одном контейнере запишут друг друга.

**Видео глушится намеренно.** Боту нужен только звук; отключение рендеринга видеопотоков снижает
расход памяти примерно с 2 ГБ до 0.6–0.8 ГБ на встречу. При замеренном пике **3 одновременные встречи**
(прод, 60 дней) это ~2.4 ГБ.

### 5.2 Оркестратор — долгоживущий, один

Отдельный маленький сервис: следит за расписанием, поднимает и гасит контейнеры, ретраит вход,
отправляет heartbeat. Не в Supabase Edge Functions — встреча длится час, а функция живёт минуты.

### 5.3 Последовательность

```
оркестратор → GET /meeting-current           → встреча + conference.url
             → docker run <контейнер>         → бот заходит по ссылке
бот          → POST /meeting-claim            → meeting_id + decision
             (decision=defer → выходим, не пишем)
             → ffmpeg пишет, режет по 25 МБ
             → POST /meeting-heartbeat (кажд. 60 с)
             → POST /meeting-ingest (sys_parts + speakers)
             → GET /meeting-status → done → контейнер умирает
```

Дальше работает существующий конвейер: `meeting-process` → тезисы → очередь вычитки → публикация.
**Ничего в нём не меняется.**

## 6. Площадки

| Площадка | Гостевой вход | Ключ комнаты | Готовность |
|---|---|---|---|
| Google Meet | по ссылке, имя + «Ask to join» | `meet:<code>` — **есть** | адаптер писать |
| Контур.Толк | по ссылке, ФИО + разрешения ([справка](https://support.kontur.ru/talk/45288-podklyuchenie_vneshnego_v_brauzere_cherez_pk)) | `kontur:<room>` — **есть** | адаптер писать |
| Zoom | веб-клиент `app.zoom.us/wc/join` | `zoom:<id>` — **НЕТ, добавить** | адаптер + префикс ключа |

Все три работают в браузере без установки — значит покрываются одним механизмом.

**Адаптер площадки — единственное место, где живёт вёрстка.** Интерфейс адаптера:
`join(url, displayName)`, `waitAdmitted()`, `activeSpeaker()`, `isAlone()`, `leave()`. Остальной код
про площадки не знает.

## 7. Отказы: всё должно быть громким

Проект уже оплатил класс молчаливых сбоев (issues #171, #175, #178, #150). Поэтому в дизайне явно:

| Ситуация | Поведение |
|---|---|
| Не впустили за 90 с | уведомление владельцу встречи, повтор через 3 мин, затем выход |
| Ссылка не распозналась | `reason: "no_conference_link"`, бот не запускается, запись в лог |
| Владелец не определился | бот **не заходит** — лучше пропустить, чем записать «ничью» встречу |
| Контейнер умер посреди встречи | heartbeat прекращается → существующий `checkRecorderHealth` ловит |
| `claim` вернул `defer` | бот выходит немедленно, аудио не пишет |
| Бот остался один в звонке | выходит через 2 минуты (встреча кончилась) |

## 8. Площадка размещения

**MUSPELHEIM сейчас.** Замер 28.08: 19 контейнеров едят 1.9 ГБ, WSL2 выделено 15.4 ГБ → свободно
~13.5 ГБ. Боту нужно ~2.4 ГБ в пике. Влезает с запасом. Публичный адрес **не нужен** — бот ходит
наружу сам, входящих соединений нет, поэтому конфликта за общий funnel-корень площадки не возникает.

⚠️ **Известный риск, принятый сознательно:** MUSPELHEIM — ноутбук с домашним интернетом. Если он лёг,
встреча не запишется. Риск приемлем **только пока бот работает параллельно с `bumblebee`**: не записал
бот — записал человек. В момент, когда бот становится единственным источником, переезд на Dodo AI
Platform обязателен, а не желателен.

Это расходится с глобальным правилом «Swarm Brain на MUSPELHEIM не разворачивать» — расхождение
осознанное, зафиксировано решением владельца
[2026-08-28-meeting-bot-platform](../../decisions/2026-08-28-meeting-bot-platform.md).

## 9. Что сознательно НЕ делаем

- **Не берём Vexa / Attendee / Recall.ai.** Ни один не умеет Контур.Толк, а свой транскрайбер и свои
  тезисы у нас уже есть — чужой стек дублировал бы половину конвейера.
- **Не делаем ассистента в звонке** (подсказки, ответы голосом). Бот молчит и пишет.
- **Не трогаем `meeting-process` и тезисы.** Бот — новый источник, а не новый конвейер.
- **Не делаем склейку на claim** (issue #168) в рамках этой работы — это отдельное решение, требующее
  ответа про приватность.
- **Не чистим существующие дубли** — решение владельца «не трогать данные» от 28.08 в силе.
- **Не выключаем `bumblebee`.** Он остаётся, пока бот не докажет надёжность на всех трёх площадках.

Порядок неслучаен: этап 1 отвечает на вопрос «работает ли затея вообще» самым дешёвым способом,
этап 2 доводит качество до уровня рекордера, и только потом расширяется охват.

## 11. Проверка

Правило прода в силе: **проверка на реальном окружении до раскатки на команду**.

- **Юнит:** парсинг conference-ссылок (все четыре поля Google-события, мусор, отсутствие);
  `scopeRoomKey` для `zoom:`; сведение таймлайна говорящих с сегментами (перекрытия, дыры, пустой
  таймлайн → мягкая деградация).
- **Безопасность (блокирующее):** токен `kind: "recorder"` НЕ может передать `on_behalf_of`; бот не
  может указать пользователя из чужого `group_id`; токен бота без `on_behalf_of` не даёт прав.
- **Живой прогон (обязателен, «собралось» не считается):** реальная встреча в Meet — бот заходит,
  впускают, пишет, `claim` → `ingest` → тезисы с именами говорящих. Затем — встреча, куда бота **не**
  впускают: должно прийти уведомление, а не тишина.
- **Регресс:** прогнать `bumblebee` после правок `meeting-current` / `meeting-claim` / `meeting-ingest`
  — это общие модули, у них есть действующий потребитель.

## 12. Имя

Рекордер называется `bumblebee` (латиница, строчная —
[решение 28.08](../../decisions/2026-08-28-recorder-renamed-bumblebee.md)). Боту нужно имя из той же
вселенной, и его выбирает владелец. В коде до этого момента — нейтральное `meeting-bot`; имя
пользовательской поверхности на архитектуру не влияет и стройку не блокирует.
