# Привязка Telegram к веб-личности (#92)

> Дизайн-спека. Решения владельца — `docs/decisions/2026-09-04-profile-connectors.md`.
> Редизайн профиля (#236) — **отдельный кусок**, здесь только плитка Telegram по месту.
> Упреждение встречи 5 мин — сделано отдельным коммитом (`LOOKAHEAD_MIN`), к этой спеке не относится.

## Задача

Человек, заведённый по e-mail и вошедший в веб, получает **синтетическую личность**
`telegram_id = -allowed_users.id` (`auth-resolve/index.ts:61`). Она навсегда закрывает ему вход
в бота (#92) и делает невозможными уведомления. Нужно: кнопка «Привязать Telegram» в профиле,
после которой реальный `telegram_id` **замещает** синтетический, а все данные человека
переезжают вместе с ним.

Масштаб на проде (04.09.2026): 2 синтетические личности, 11 реальных, 2 pending.

## Границы

- В scope: механика слияния, выдача и приём токена, подтверждение в боте, плитка Telegram в профиле.
- Не в scope: редизайн профиля пиктограммами и пинг в колокольчик (#236); отвязка рекордера от
  Telegram (#93); онбординг без Telegram (#21).

## Архитектура — три слоя

### 1. БД: `merge_identity(old_id, new_id, dry_run)`

PL/pgSQL, `SECURITY DEFINER`, `REVOKE ALL FROM PUBLIC` + `GRANT EXECUTE TO service_role`.
Грант на `PUBLIC` наследуется в `anon` и делает функцию вызываемой через `/rest/v1/rpc` —
именно так уехала GHSA-vxrp-599j-46hv. Обычный `REVOKE … FROM anon` этого не снимает.

Возвращает JSON-сводку перенесённого (`{entries: N, tasks: M, meetings: K, …}`) — из неё бот
строит текст подтверждения. При `dry_run = true` считает и **откатывает** (`RAISE EXCEPTION`
внутри вложенного блока либо подсчёт без записи) — нужно, чтобы проверить слияние на проде,
ничего не меняя.

**Единый путь для обоих случаев.** Прямой `UPDATE allowed_users SET telegram_id` невозможен:
семь FK объявлены без `ON UPDATE CASCADE`, то есть `NO ACTION` — апдейт родителя с живыми
детьми упадёт. Поэтому порядок всегда такой:

1. Убедиться, что строка `new_id` в `allowed_users` есть; нет — создать копией полей `old_id`.
2. Перевесить **все** колонки-носители со `old_id` на `new_id`.
3. Удалить строку `old_id`.

Шаг 2 обязан идти до шага 3 ещё и потому, что у `user_profiles`, `notifications`,
`task_subscriptions` стоит `ON DELETE CASCADE` — удаление старой строки просто снесло бы их.

**Колонки-носители — 17 в 11 таблицах.** Под FK: `user_profiles.telegram_id`,
`entries.owner_id`, `tasks.owner_id`, `meetings.claim_owner`, `task_labels.owner_id`,
`notifications.recipient_telegram_id`, `task_subscriptions.telegram_id`.
Без FK: `feedback.telegram_id`, `notifications.actor_telegram_id`, `projects.created_by`,
`task_comments.added_by_telegram_id`, `tasks.assignee_telegram_ids` (**массив**),
`tasks.created_by_telegram_id`, `tasks.remind_set_by`, `user_integrations.telegram_id`.
`tasks.created_by` — `text`, при реализации проверить, id там или имя.

Особые случаи внутри переноса:
- `tasks.assignee_telegram_ids` — `array_replace`, затем дедуп: если `new_id` уже был в массиве,
  появится дубль.
- `user_integrations` — уникальна пара (telegram_id, service). Тот же сервис есть у обоих →
  побеждает запись `new_id`, запись `old_id` удаляется (её refresh-token старше и, скорее всего,
  принадлежит той же почте).
- `user_profiles` — если профиль есть у обоих, слить по правилу «непустое поле побеждает пустое»,
  при конфликте двух непустых — оставить значение `new_id`.
- `task_subscriptions` — уникальна пара (telegram_id, task_id); дубли снять.

### 2. Токен привязки

Зеркалит существующий механизм агентских токенов (`_shared/agent-auth.ts`): секрет не хранится,
хранится `sha256`-hex. Две новые колонки в `allowed_users` (`ADD COLUMN` — безопасно):
`tg_link_token_hash text`, `tg_link_expires_at timestamptz`. Отдельная таблица не нужна: токен
одноразовый, живёт 15 минут и всегда принадлежит ровно одной строке.

Ручки в `swarm-api` (JWT веба, личность из токена — не из тела запроса):
- `POST /telegram-link/start` → генерит 32 случайных байта (base64url), пишет хеш и срок в свою
  строку, возвращает `{deep_link: "https://t.me/<bot>?start=link_<токен>"}`. Повторный вызов
  перезаписывает предыдущий токен — старая ссылка умирает.
- `GET /me` — дополнить полем `telegram: {linked, username}`, чтобы профиль знал, что рисовать.

Отвязки нет намеренно: она вернула бы человека в состояние, из которого мы его вытаскиваем.

### 3. Бот

`/start link_<токен>` обрабатывается **до гейта доступа**. Гейт стоит на `swarm-bot/index.ts:431`,
команды разбираются на 528 — если оставить как есть, человек с синтетической личностью получит
«Доступ запрещён» и не дойдёт до привязки, то есть фича не сработает ровно для тех, для кого
делается. Payload берётся из уже существующего разбора (`const [command, ...rest] = text.split`).

Ветвление по результату поиска токена:

| Ситуация | Поведение |
|---|---|
| Токен не найден или просрочен | «Ссылка устарела — нажми "Привязать Telegram" в профиле ещё раз». Молча не игнорируем. |
| `old_id == from.id` | «Уже привязан», токен гасится. |
| Строки с `from.id` нет | Слияние сразу, без вопросов: сливать не с чем, это переименование ключа. |
| Строка с `from.id` есть | **Подтверждение** (решение владельца): бот показывает сводку из `dry_run` — «нашёл вторую твою запись: N записей, M задач. Объединить?» — и ждёт кнопки. |

Токен гасится в момент предъявления, а намерение кладётся в `sessions` (механизм уже есть) —
иначе ссылка осталась бы живой, пока человек думает.

### 4. Профиль (минимум)

Плитка/секция **Telegram** рядом с Google-календарём в `SettingsScreen.tsx`: «✓ Привязан
@username» либо кнопка «Привязать Telegram», открывающая `deep_link`. Полный редизайн — #236.
В карточке сотрудника (`AdminScreen.tsx`) — строка статуса «Telegram: @user / не привязан»,
только показ: привязать за другого человека нельзя, подтверждение приходит от его аккаунта.

## Тестирование

- **Тест-сторож списка колонок** (главная страховка от гниения): обходит `pg_constraint` и
  `information_schema`, собирает колонки-носители и падает, если хоть одна не упомянута в
  `pg_get_functiondef('merge_identity')`. Без него следующая таблица выпадет так же тихо, как
  выпала бы `meetings.claim_owner`: её имя не содержит ни `telegram`, ни `owner_id`, и поиск по
  именам колонок её пропускает (проверено — пропустил).
- Юнит-тесты слияния на локальном контуре (`supabase db reset`): перенос без конфликта; перенос
  с существующей строкой; дубль в `assignee_telegram_ids`; тот же сервис в `user_integrations` у
  обоих; повторный вызов (идемпотентность).
- Тесты веток бота: просроченный токен, чужой токен, уже привязан, отказ от подтверждения.
- **Проверка на проде до раскатки на команду**: `dry_run` на обеих реальных синтетических
  личностях — сводка должна сойтись с прямым подсчётом строк.

## Раскатка

Миграция (`ADD COLUMN` + функция) · деплой `swarm-api`, `swarm-bot` · веб (плитка). Всё —
ночное окно 23:00–05:59 по явному «да», метка `deploy-window`. После раскатки — привязка
вживую на реальной синтетической личности, затем доклад владельцу.
