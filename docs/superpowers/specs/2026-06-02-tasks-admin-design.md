# Tasks Admin — Design Spec
_2026-06-02_

## Контекст

Система задач работает, но имеет два нерешённых вопроса:
1. **Безопасность** — MCP `get_tasks`/`delete_task`/`update_task` не фильтруют по воркспейсу если не передан `requesting_user_id`; можно читать и удалять задачи чужих воркспейсов
2. **UX** — нет подтверждения задач создателем: задачи от AI попадают в базу без ревью, нет единого места где их увидеть и разобрать

---

## Цели

- Каждая задача от AI проходит ревью создателя до того как уйдёт исполнителю
- Минимальный UX: одно касание для хорошей задачи, один уровень вглубь для правки
- Таргетинг через теги и assignees, без лишних полей
- Broadcast-уведомление исполнителям после подтверждения
- Закрыть security-баги в MCP

---

## Схема данных

### Миграция (ADD COLUMN — безопасно, без downtime)

```sql
ALTER TABLE tasks
  ADD COLUMN IF NOT EXISTS confirmed boolean NOT NULL DEFAULT false,
  ADD COLUMN IF NOT EXISTS created_by_telegram_id bigint;
```

- `confirmed = false` — задача ждёт ревью создателя
- `created_by_telegram_id` — кто создал (для фильтра «мои на проверке»)
- Все существующие задачи получат `confirmed = false` — пройдут ревью при первом входе в админку

### Теги — предзаданный набор (не свободный ввод в боте)

| Категория | Значения |
|-----------|----------|
| Страны | `Serbia`, `Bulgaria`, `Croatia`, `Hungary`, `Moldova`, `Romania` |
| Охват | `#all` — все в воркспейсе |
| Роли | `#marketing`, `#rnd`, `#bd` |

Поле `country` (уже есть) — строгий выбор из списка стран (или null для глобальных).
Поле `assignee_telegram_ids` (уже есть) — конкретные люди для пинга.

### Примеры задач

| Задача | country | tags | assignee_telegram_ids |
|--------|---------|------|----------------------|
| Заполнить отчёт за май | null | `[#all]` | [] |
| Запустить акцию в Сербии | Serbia | `[#marketing, #rnd]` | [12345] |
| Встреча с партнёром | Bulgaria | [] | [67890] |

## Источники задач и состояние confirmed

| Источник | confirmed при создании | created_by_telegram_id | Уведомление создателю |
|----------|----------------------|----------------------|----------------------|
| Claude / MCP `add_task` | `false` | `requesting_user_id` | Бот: «N задач на проверке» (одно сообщение на пакет) |
| Бот `/addtask` | `true` | `userId` бота | — (assignees пингуются сразу) |
| Granola auto-extract | `false` | тот кто импортировал встречу | Вместе с подтверждением встречи |

## UX: бот

### Точка входа

`/tasks` или кнопка в главном меню → три варианта:

```
📋 Задачи

[⏳ На проверке (3)]
[📅 На сегодня]
[📋 Все открытые]
```

### «На проверке» — список

Задачи где `confirmed = false AND created_by_telegram_id = my_id`:

```
⏳ На проверке (3):

1. Запустить акцию в Сербии · Вася · 15 июня
2. Заполнить отчёт · #all · —
3. Встреча с партнёром · Петя · —

[📋 #1]  [📋 #2]  [📋 #3]
```

### «На сегодня» — список

Задачи где:
- `confirmed = true`
- `due_date <= today` (включая просроченные)
- `assignee_telegram_ids` содержит мой ID ИЛИ `tags` содержит `#all`

```
📅 Твои задачи на сегодня:

🔴 Заполнить отчёт · просрочена (1 июня)
🟡 Встреча с партнёром · сегодня

[📋 #1]  [📋 #2]
```

### Карточка задачи

```
📋 Запустить акцию в Сербии

👤 Вася Гарро
🌍 Serbia · #marketing
📅 15 июня

[✅ Подтвердить]       [🗑 Удалить]
[👤 Исполнитель]  [📅 Дедлайн]  [🌍 Страна/теги]
```

**Правила карточки:**
- Если AI распознал исполнителя → показан сразу
- Если имя не смаплено → кнопка «👤 Исполнитель» визуально выделена (добавить `⚠️`)
- Тап «👤 Исполнитель» → инлайн-список всех пользователей воркспейса → выбрал → вернулся в карточку
- Тап «📅 Дедлайн» → ввод текстом («15 июня», «следующая пятница») → GPT парсит в YYYY-MM-DD
- Тап «🌍 Страна/теги» → список кнопок: страны + `#all` + роли

**После ✅ Подтвердить:**
1. `confirmed = true` в БД
2. Бот отправляет каждому в `assignee_telegram_ids`: *«📋 Тебе назначена задача: [название] · [дедлайн или —]»*
3. Если `tags` содержит `#all` — broadcast всем в воркспейсе

### Уведомление о пакете от Claude

После каждого `add_task` через MCP бот присылает уведомление создателю напрямую через Telegram Bot API (MCP имеет `TELEGRAM_BOT_TOKEN` в env):

```
📋 Новая задача на проверке: Запустить акцию в Сербии

[⏳ Смотреть]
```

Если Claude создаёт несколько задач подряд — придёт несколько уведомлений (приемлемо, задач обычно не больше 5-7). Группировка не реализуется — усложнение без явной пользы.

- `toolGetTasks`: сделать `requesting_user_id` обязательным; без него — ошибка
- `toolDeleteTask`: добавить проверку `task.group_id === callerGroupId`
- `toolUpdateTask`: добавить проверку `task.group_id === callerGroupId`
- `toolAddTask`: передавать `confirmed: false`, `created_by_telegram_id: requesting_user_id`

### 6. `swarm-api/index.ts`
- `POST /tasks` — передавать `confirmed: true` (Mini App = ручное создание), `created_by_telegram_id` из initData
- `GET /tasks` — добавить фильтр `?confirmed=` для Mini App

### 7. Callback-префиксы (новые)
| Префикс | Действие |
|---------|----------|
| `tc_` | Подтвердить задачу (task confirm) |

| `tasi_` | Выбрать исполнителя из списка |
| `tdue_` | Редактировать дедлайн (сессия) |

## Безопасность

- MCP `get_tasks` без `requesting_user_id` → возвращает ошибку, не данные
- `delete_task` и `update_task` → проверяют `task.group_id === callerGroupId` перед действием
- `created_by_telegram_id` пишется сервером (из `requesting_user_id`), не принимается от клиента как trusted поле

---

## Что НЕ входит в этот спек

- Mini App экран задач (отдельная фаза беклога)
- Редактирование тезисов задачи через AI (как у встреч)
- История изменений задачи (`task_history`)
- Recurring tasks
