# Спека: crash-safe чекпоинты записи рекордера (вариант A)

> Статус: **sys-инкремент РЕАЛИЗОВАН (build 12, локально, тест впереди)** — durable-папка + мягкая ротация СИСТЕМНОЙ дорожки каждые 5 мин + восстановление при запуске (переиспользует существующий upload-путь `systemSegments`). **Микрофон-ротация НЕ входит** в инкремент: требует mic_parts на клиенте (`PendingUpload.micPath` — одиночный; `SwarmClient` multipart) — отдельная задача. На команду НЕ раскатано (нет тега build-12/LATEST) до реального теста «краш посреди записи → восстановление».
> Дата: 2026-07-18. Связано: инцидент 15–17.07 (runaway-запись + зависший звук), фикс зависания teardown (build 10), беклог «Рекордер: зависание teardown, чекпоинты».

## Проблема

Сейчас во время записи сегменты (`sys`, `mic`) пишутся в volatile `FileManager.temporaryDirectory` и переезжают в durable `pending/<meetingId>/` **только на штатном стопе** (`AppDelegate.performSend` → `UploadQueue.enqueue`; `claim` тоже только там). Значит при зависании HAL / краше / ребуте до штатного стопа:
- `claim` не вызван → на сервере нет даже строки встречи;
- сегменты в temp → **стёрты ребутом**;
- текущий системный сегмент даже не финализирован (moov-атом пишется на teardown).

Итог: **встреча теряется целиком** (реально произошло 17.07). Вся durable-защита (`pending/`, ретраи, бэкап 3 суток, «не удалять до done») включается только ПОСЛЕ чистого стопа.

## Цель

При зависании/краше/ребуте терять **максимум последний недописанный кусок** (≤ интервал ротации), а не встречу целиком. Досыл — при следующем запуске рекордера (он автозапускается).

## Дизайн (вариант A)

### 1. Durable-запись с самого старта
- В `beginRecording` писать сегменты не в temp, а в durable `~/Library/Application Support/SwarmRecorder/recording/<base>/` (App Support переживает ребут — доказано застрявшей записью 15.07).
- Сразу писать `meta.json`: `{ base, status:"recording", identity (kind/key/title/attendees/startISO/endISO), micStartOffset }`. Идентичность нужна для дедупа при восстановлении (claim по тому же ключу → без дублей).

### 2. Ротация каждые ~5 минут («резать»), БЕЗ HAL-teardown
- Раз в 5 мин финализировать текущий кусок и открыть новый — **ротацией файла**, не пересборкой тапа:
  - **Система:** новый метод `SystemAudioCapturer.rotateFileLocked()` — закрыть текущий `AVAudioFile` (пишет moov), открыть новый сегмент, тап/aggregate **не трогать** (в отличие от `rebuildLocked`, который делает полный HAL-teardown — то самое зависающее место). Добавить сегмент в манифест с offset.
  - **Микрофон:** остановить текущий `AVAudioRecorder`, открыть новый файл; писать mic мульти-парт (`mic0`,`mic1`… с offset). Сервер уже поддерживает `mic_parts`.
- Каждый чекпоинт-кусок ≤5 мин ⇒ сам укладывается в серверный лимит части (≤15 мин/≤24 МБ) — отдельная нарезка `Segmenter` не нужна, кусок = готовая часть для аплоада.
- Обновлять `meta.json` (список готовых частей) после каждой ротации.

### 3. Восстановление при запуске — тихо + уведомление
- На старте приложения сканировать `recording/`. Папка со `status:"recording"`, не принадлежащая текущей сессии (осиротела после краша) → считать завершённой:
  1. `claim` по сохранённой идентичности (дедуп работает);
  2. перенос частей в `pending/<meetingId>/` + сайдкар (переиспользуем `UploadQueue.enqueue`);
  3. `drain`.
- Тихо + короткое уведомление «Восстановила прерванную запись — отправила в обработку» (команда нетехническая).

### 4. Штатный стоп и edge-cases
- Нормальный стоп: финализировать последний кусок, `claim` + `enqueue` тем же путём, **переиспользуя ту же durable-папку и идентичность** → одна встреча, без дублей.
- Теряется максимум текущий недописанный <5-мин кусок на момент жёсткого сбоя. Принято.
- 24ч/3-сут потолок и dead-letter действуют как сейчас.
- Убрать зависимость от temp — устраняет уязвимость «temp стёрся ребутом».

## Файлы (ориентир)
- `AppDelegate.swift` — durable-папка на старте, ротационный таймер (5 мин), скан восстановления на launch, конвергенция стопа на durable-папку.
- `SystemAudioCapturer.swift` — `rotateFileLocked()` (мягкая ротация файла без HAL-teardown) + аккуратная работа с манифестом под ioLock.
- `AudioRecorder.swift` — ротация mic (`AVAudioRecorder` stop/start в новый файл), мульти-парт mic + offset.
- `UploadQueue.swift` — путь восстановления (переиспользовать `enqueue`/`drain`; чтение осиротевших `recording/` папок).

## Зависимости на сервере (проверить в реализации)
- `meeting-ingest`/`meeting-process`/`meeting-processor.ts` корректно принимают мульти-парт микрофон (`mic_parts` с offset). По манифесту поддержка есть — подтвердить кодом.

## План тестирования (обязателен — это crash-safety)
1. Ротация: записать >10 мин, убедиться что части ≤5 мин, валидные m4a (moov на месте), offset монотонный, сервер сводит верно.
2. Краш посреди записи (kill -9 / ребут) → следующий запуск восстанавливает и досылает; потерян только последний <5-мин кусок.
3. Штатный стоп после ротаций → одна встреча, без дублей, все части на месте.
4. Дедуп: восстановление + повторный запуск не плодят дубль (claim по идентичности идемпотентен).
5. mic-only и sys-only записи; манёвр смены устройства (BT) во время ротации не роняет запись.

## Не входит (YAGNI)
- Live-аплоад во время звонка (вариант B) — отдельная будущая задача, если понадобится ранняя серверная обработка.
