# Спринты — дизайн

**Дата:** 2026-09-08 · **Статус:** согласовано с владельцем, к реализации
**Решение владельца:** [docs/decisions/2026-09-08-sprints.md](../../decisions/2026-09-08-sprints.md)

## 1. Что делаем

Третья вкладка в задачах — **«Спринты»** — пространство планирования по времени поверх тех же
самых задач. Слева пул «Задачи», справа обычный канбан, у спринта есть даты, а в конце —
приёмка: состав замораживается снимком, незакрытые уезжают в следующий спринт.

Доска «Проекты» не меняется ни в чём. Статус задачи один и тот же везде: закрыл в спринте —
на доске проекта задача в «Готово» в ту же секунду, потому что это одна и та же строка.

**Не входит в работу:** графики сгорания, оценки в часах и story points, шаблоны проектов
(issue #266), переименование таблицы вкладок в `board_tabs` (отложено владельцем), тумблер
«проект участвует в спринтах» (пул и так фильтруется руками).

## 2. Термины

| Термин | Что это | Где в коде |
|---|---|---|
| **Спринт** | период с датами, статусом и снимком | новая таблица `sprint_cycles` |
| **Состав спринта** | связь задача ↔ спринт, она же носитель клона | новая таблица `sprint_items` |
| **Пул «Задачи»** | задачи воркспейса, не взятые в текущий спринт | вычисляется, своей таблицы нет |
| **Приёмка (заморозка)** | фиксация клона + расчёт итогов + перенос хвостов | `POST /sprint-cycles/:id/accept` |
| **Вкладка доски** | «Паша», «Ксюша», «Гарро» на доске проектов | таблица `sprints` — **это не спринты**, имя историческое |

⚠️ Таблица `sprints` хранит вкладки доски проектов, а не спринты. Переименование отложено
владельцем («не горит»). Любой, кто читает код: спринты — это `sprint_cycles`.

## 3. Модель данных

### 3.1 `tasks.completed_at` — фундамент

```sql
alter table tasks add column if not exists completed_at timestamptz;
comment on column tasks.completed_at is 'Момент перехода в закрытый статус (done/cancelled). NULL, если задача открыта.';
create index if not exists idx_tasks_completed_at on tasks(completed_at) where completed_at is not null;
```

Заполняется **в одном месте** — `updateTask` в `_shared/tasks/db.ts` (через неё идут и API, и бот,
и MCP): переход в `done`/`cancelled` ставит время, выход из них — обнуляет.

Бэкфилл прошлого: `update tasks set completed_at = updated_at where status in ('done','cancelled')
and completed_at is null`. Это **прокси, а не факт** — `updated_at` двигался от любой правки;
записать в комментарий к колонке и в отчёте не выдавать старые даты за точные.

Без этой колонки не считаются «когда завершено» и «сколько времени над задачей работали» —
обе метрики владелец назвал обязательными.

### 3.2 `sprint_cycles`

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | uuid pk | |
| `group_id` | text | воркспейс, как везде |
| `name` | text | «Спринт 08.09 — 22.09» |
| `start_date`, `end_date` | date | рамки |
| `status` | text check (`draft`,`active`,`accepted`) | жизненный цикл |
| `created_by` | text | telegram id |
| `accepted_at` | timestamptz | момент заморозки |
| `accepted_by` | text | кто принял |
| `summary` | text | итог/ретро одним текстом |
| `stats` | jsonb | посчитанные на приёмке цифры (см. §6) |
| `created_at`, `updated_at` | timestamptz | |

`stats` считается один раз при приёмке и больше не пересчитывается — отчёт не должен «плыть»
от последующей жизни задач.

### 3.3 `sprint_items` — состав и клон

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | uuid pk | |
| `cycle_id` | uuid → `sprint_cycles` on delete cascade | |
| `task_id` | uuid → `tasks` **on delete set null** | живая задача; NULL, если её удалили |
| `in_plan` | boolean | была в составе на момент старта |
| `added_at`, `added_by` | timestamptz / text | когда и кто взял в спринт |
| `frozen_at` | timestamptz | момент заморозки |
| `frozen_title` | text | заголовок на момент приёмки |
| `frozen_status` | text | статус на момент приёмки |
| `frozen_assignees` | text[] | исполнители на момент приёмки |
| `frozen_project` | text | проект/подпроект на момент приёмки |
| `frozen_completed_at` | timestamptz | когда закрыли |

Уникальность: одна задача — одна строка в одном спринте
(`unique (cycle_id, task_id) where task_id is not null`).

**Почему связь отдельной таблицей, а не полем `tasks.sprint_cycle_id`:** задача, прожившая три
спринта, при поле оставит след только в последнем. Владелец просил считать, «сколько спринтов
задача заняла» — это невозможно без истории. Так же устроено у Plane (`CycleIssue`).

**Почему клон в той же строке, а не отдельной таблицей снимков:** снимок и состав — одно и то же
множество; вторая таблица была бы копией схемы. Plane хранит агрегат в `progress_snapshot` у
цикла — у нас агрегат в `stats`, а построчный клон в `sprint_items`, потому что владелец просил
видеть в архиве сами задачи, а не только цифры.

## 4. Правила поведения

1. **Взятие в спринт не меняет задачу** — кроме одного случая: статус `backlog` переводится в
   `open`, иначе задача не попадёт ни в одну колонку спринтового канбана (там три колонки, см. §5).
   Остальные статусы не трогаются. ⚠️ *Единственное неявное изменение данных во всей фиче —
   вынести владельцу при первой демонстрации.*
2. **Приватные задачи в спринт не попадают** ни при добавлении, ни в отчёте: `is_private` — сквозное
   правило продукта, отчёт не должен становиться каналом утечки.
3. **Состав `draft`-спринта правится свободно.** Старт (`draft` → `active`) фиксирует `in_plan=true`
   у всего, что на тот момент в составе. Всё добавленное позже — `in_plan=false`, «сверх плана».
4. **Приёмка (`active` → `accepted`)** одной операцией: проставить `frozen_*`, посчитать `stats`,
   перенести незакрытые в указанный следующий спринт. Перенос в уже принятый спринт запрещён
   (проверка как в Plane `transfer_cycle_issues`).
5. **Принятый спринт неизменен.** Состав не правится, `stats` не пересчитывается. Живые задачи
   продолжают жить: переоткрытие задачи не меняет архив. В интерфейсе архивные карточки подписаны
   «на момент приёмки ДД.ММ».
6. **Права:** создавать, стартовать и принимать спринт — админ (`ADMIN_USER_ID` /
   `allowed_users.is_admin`), как удаление вкладок сейчас. Видеть и двигать задачи — все
   участники воркспейса.

## 5. Интерфейс

Вкладка **«Спринты»** третьей рядом с «Задачи» и «Проекты» (`TasksScreen.tsx`, `view: "sprints"`).

**Шапка:** селектор спринта (активный + архив, фильтр по году), даты, статус, прогресс,
кнопка действия по состоянию — «Начать спринт» / «Принять спринт» / «Открыть отчёт»
(при реализации 09.09.2026 «Спринт принят» переименовано в «Принять спринт»: на живом спринте
прежняя подпись читалась как утверждение «он уже принят», а не как действие).

**Слева — «Задачи».** Пул: задачи воркспейса, доступные человеку и не взятые в текущий спринт.
Поиск, фильтр по проекту и исполнителю, добавление по одной и мультивыбором.

**Справа — канбан:** три колонки **Открыто · В работе · Готово**. Колонки «Бэклог» в спринте нет —
её роль играет пул слева, по решению владельца («backlog заменим на слово задачи»).
Карточки сгруппированы заголовками проектов — это группировка, не копии проектов.

**Карточка** — существующая: `TaskRow` / `TaskModal` / `TaskComments` / `TaskQuickActions` уже общие
для доски, таймлайна и списков. В спринте они те же, поэтому обсуждение и комментарии на ретро
работают без новой работы.

**Принятый спринт:** тот же канбан, но только на чтение и по клону (`frozen_*`), плюс блок итогов.

**Ре-использование канбана.** Колонки, DnD и карточка сейчас вшиты в `SprintBoard.tsx` (687 строк,
приколочен к вкладкам). Выносим канбан в отдельный компонент, который используют и доска проектов,
и спринт. Это единственная правка живого экрана — и единственное место, где возможна регрессия;
проверяем на реальном окружении отдельно (см. §8).

## 6. Аналитика

Считается на приёмке в `stats`, показывается в отчёте спринта:

| Метрика | Как считаем |
|---|---|
| План / сделано из плана / % | `in_plan=true`, из них `frozen_status in ('done','cancelled')` |
| Сверх плана (взято / закрыто) | `in_plan=false` |
| Перенесено в следующий | незакрытые на момент приёмки |
| Кто сколько закрыл | по `frozen_assignees`; задача с несколькими исполнителями попадает в строку каждого, в общем итоге считается один раз |
| Когда закрывали | по `frozen_completed_at`, распределение по дням спринта |
| Сколько спринтов заняла задача | число строк `sprint_items` у одной `task_id` |
| Срез по человеку через спринты | создано (`created_by_telegram_id`), закрыто, среднее время от создания до `completed_at` |

Фильтры отчётов по годам и кварталам берутся из дат спринтов — специально ничего закладывать не
нужно, но это работает только потому, что состав лежит отдельной таблицей, а не полем задачи.

Расчёт — чистыми функциями в `_shared/tasks/sprint-stats.ts`, под юнит-тестами, без обращения к БД.

## 7. Работы по этапам

Каждый этап самодостаточен, раскатывается отдельно и проверяется на реальном окружении.

**Этап 1 — фундамент.** Миграция `completed_at`, простановка в `updateTask`, бэкфилл, запись
`task_history` из веба (сейчас пишет только бот — в таблице одна строка за всё время).
*Полезно само по себе: чинит нынешнее «закрыл сегодня», которое считается по `updated_at`.*

**Этап 2 — модель и API.** Таблицы, роуты **отдельным модулем** `swarm-api/sprint-cycles.ts`
(в `index.ts` не лить — там 2431 строка при пределе 800, issue #265): список, создание, старт,
добавление/удаление задач, приёмка с заморозкой и переносом.

**Этап 3 — экран.** Вынос канбана из `SprintBoard.tsx`, вкладка «Спринты», пул, шапка, действия.

**Этап 4 — отчёт.** `sprint-stats.ts`, блок итогов, архив с фильтром по годам.

## 8. Проверка

- **Тесты:** чистые функции (`sprint-stats`, правила состава) — юнитами, как `smartLists.test.ts`;
  гварды доступа и приёмка — `deno test` рядом с существующими в `swarm-api/*.test.ts`.
- **Обязательный смоук на реальном окружении** по правилу проекта: после этапа 1 — что дата
  закрытия проставляется живой задачей; после 2 — приёмка на тестовом спринте через эндпоинт;
  после 3 — доска проектов **до и после** выноса канбана (та самая единственная регрессия);
  после 4 — цифры отчёта сверить руками по SQL.
- `deno check` затронутых функций, `npm run build` в `miniapp/`.

## 9. Раскатка

Порядок обязателен: **миграция → функции → веб**. Код, читающий `completed_at`, упадёт на
отсутствующей колонке; веб собирается с `main` автоматически, поэтому правки `miniapp/` живут в
ветке и вливаются в окно.

Окно — 23:00–05:59, по явному «да» владельца на каждую раскатку. Практически: PR с меткой
`deploy-window`, ночью вливает автоматика. Порций 3–4, по этапам.

## 10. Открытые вопросы

1. `backlog` → `open` при взятии в спринт (§4.1) — единственное неявное изменение данных,
   показать владельцу на первой демонстрации и подтвердить.
2. Переименование `sprints` → `board_tabs` — отложено владельцем, вернуться после спринтов.
3. Мусорная вкладка `qef` на проде (1 проект, 1 задача) — прибрать при случае.
