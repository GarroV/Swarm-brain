# Вложенные подпроекты на доске «Спринт» — дизайн

> Статус: согласован с владельцем (брейншторм 2026-08-07). Ветка: `feat/sprint-subprojects`.
> Хенд-мейд документ (дизайн-спека), не генерируется.

## 1. Проблема и цель

Сейчас доска «Спринт» имеет два уровня группировки: **спринт** (чипы) → **секция = проект** (`projects`, swimlane) → **4 колонки статусов** (Бэклог/Открыто/В работе/Готово). У каждой секции уже свой канбан.

Владелец хочет **ещё один уровень**: секция может стать **группой** (напр. «Вайб код проекты») и содержать несколько **подпроектов**, у каждого — свой канбан. Подпроекты внутри группы визуально не разбиты жёстко (единая рамка проекта, тонкие разделители), но это отдельные подпроекты со своими колонками — потому что какому-то подпроекту в будущем может понадобиться дополнительная колонка-стадия.

## 2. Модель данных

Одна аддитивная миграция (безопасный `ADD COLUMN`):

```sql
alter table public.projects
  add column if not exists parent_id uuid references public.projects(id) on delete set null;
create index if not exists idx_projects_parent on public.projects(parent_id);
```

- `parent_id IS NULL` → проект верхнего уровня (группа, если есть дети; иначе обычная секция как сейчас).
- `parent_id` задан → **подпроект** (лист).
- Глубина **ровно 2 уровня**. Подпроект не может иметь своих детей — гарантируется валидацией в API (см. §4).
- Удаление группы: `on delete set null` поднимает детей на верхний уровень (данные не теряются). Задачи по-прежнему освобождаются существующим FK `tasks.project_id … on delete set null`.

**Почему `parent_id`, а не отдельная таблица `project_groups`:** группа и проект — одна сущность-контейнер (держит либо задачи, либо подпроекты). Переиспользуем таблицу `projects`, весь CRUD и связь `tasks.project_id`. Отдельная таблица = дубль логики и лишний JOIN.

**Задачи не меняются.** `tasks.project_id` указывает на конкретный (под)проект. Задача, «висящая» прямо на проекте-группе (легаси или добавленная до создания подпроектов), рендерится в неявном ряду **«Общее»** сверху рамки группы — ни одна задача не пропадает.

## 3. Совместимость (нулевая миграция данных)

- Проект **без детей** рендерится ровно как сейчас (свой канбан). Существующие секции («тест-2», «Без секции») работают без изменений.
- Проект становится группой **автоматически**, как только у него появляется хотя бы один подпроект.
- Старый клиент (без нового поля) продолжает работать: `parent_id` для него просто новое поле в ответе.

## 4. API (swarm-api, точечно)

Файлы: `_shared/tasks/types.ts`, `_shared/tasks/projects.ts`, роуты в `swarm-api/index.ts` (~L886-927).

- **`Project` тип + `listProjects`**: добавить `parent_id: string | null` в выборку и тип. Счётчики (`task_count`/`backlog_count`) остаются per-project (каждый подпроект считается сам по себе).
- **`POST /projects`**: принимать необязательный `parent_id`.
  - Валидация: если задан — родитель существует в том же воркспейсе **и сам верхнеуровневый** (`parent_id IS NULL`). Иначе 400.
- **`PATCH /projects/:id`**: принимать `parent_id` (вложить / вынести / перенести).
  - Валидация: нельзя указать `parent_id`, если у самого проекта есть дети (был бы >2 уровня); нельзя указать несуществующий/чужой родитель; нельзя указать родителя, у которого есть родитель; нельзя указать сам себя. `parent_id: null` — вынести на верхний уровень.
- **`DELETE /projects/:id`**: без изменений (FK `on delete set null` поднимает детей к верхнему уровню).

Валидация вынесена в `_shared/tasks/projects.ts` (чистые функции — покрыть юнит-тестами), роут только парсит вход и мапит ошибки в 400/404.

## 5. UI (`miniapp/src/components/tasks/SprintBoard.tsx`)

- Строим дерево из плоского списка `projects`: `topLevel = projects.filter(p => !p.parent_id)`, `childrenOf(id) = projects.filter(p => p.parent_id === id)`.
- Рендер верхнего уровня:
  - Проект **с детьми** → **рамка-группа**: заголовок (имя, суммарный счётчик задач по всем подпроектам, кнопка сворачивания, «+ Подпроект», переименовать, удалить). Внутри:
    - ряд **«Общее»** (только если у группы есть прямые задачи `project_id === group.id`) — свой канбан из 4 колонок;
    - по подпроекту — один ряд с тонким разделителем сверху: имя подпроекта + его 4 колонки; действия подпроекта (переименовать/удалить/«+ задача»).
  - Проект **без детей** → как сейчас (одна секция + 4 колонки).
  - «Без секции» (задачи с `project_id = null`) → как сейчас, в конце.
- **Добавление**: «+ Секция» на доске создаёт верхнеуровневый проект (как сейчас). «+ Подпроект» в заголовке группы создаёт проект с `parent_id = group.id`. Первый подпроект, добавленный к обычной секции, автоматически превращает её в группу (её прямые задачи уезжают в ряд «Общее»).
- **Drag задачи** в колонку подпроекта → `updateTask({ status, project_id: subprojectId })`. Быстрый ввод — в бэклог конкретного подпроекта/ряда.
- **Сворачивание группы** — локальный стейт (по умолчанию развёрнуто). Опционально сохранять в `localStorage` по `group.id` (не обязательно для v1).
- **Новые строки** («Подпроект»/«Subproject», «Общее»/«General», «Группа»/«Group») — двуязычно через существующий `dt()` (EN приоритет, правило проекта). Более широкая i18n доски — отдельная задача бэклога.

## 6. Вне v1 (YAGNI, дверь открыта)

- **Кастомные колонки у подпроекта** («дополнительный слой обработки»). Архитектура «у каждого подпроекта свой ряд колонок» уже это допускает: позже набор колонок станет per-project конфигом. v1 у всех рендерит стандартные 4 статуса.
- Вложенность глубже 2 уровней.
- Перетаскивание подпроектов между группами мышью (в v1 — только через создание/меню).

## 8. Тестирование и проверка (реальное окружение → прод аккуратно)

- Локально `supabase start` + прогнать миграцию (`supabase db reset` ловит SQL-поломки) и реальный флоу: создать группу → добавить подпроекты → задачи → перетащить между колонками → проверить `entries`/`tasks.project_id` в БД.
- Экран доски глянуть в светлой и тёмной теме.
- DEV_MODE-моки (`miniapp/src/lib/api.ts`) — добавить вложенный пример, чтобы демо на `swarm-brain.pages.dev`/dev показывало фичу без авторизации.
- Общий модуль `_shared/tasks/*` трогаем — проверить потребителей (`swarm-bot/tasks`, `swarm-mcp/tasks`): для них `parent_id` — новое опциональное поле, поведение не меняется; убедиться, что их сборка/чек не краснеют.
