# Персональные смарт-метки для задач + пиктограммный пикер рынка

> Дизайн-документ. Дата: 2026-07-16. Статус: черновик на ревью.
> Хэндофф в план реализации — после апрува владельцем.

## 1. Обзор

**Проблема.** В веб-интерфейсе задач слева есть смарт-списки (Сегодня / Ближайшие / Все / Готовые) — это вычисляемые вьюхи по сроку и статусу. Пользователю не хватает **своих тематических списков** («Айти», «Вайбкодинг» и т.п.), чтобы организовать личные задачи по темам, а не только по времени.

**Решение.** Персональные **смарт-метки**: пользователь заводит метку (имя + пиктограмма), вешает её на свои личные задачи, и в рельсе списков автоматически появляется смарт-список этой метки — он сам собирает все задачи с ней. Метка на задаче = членство в списке; отдельного «управления составом» нет. Это ровно тот же паттерн, что существующие смарт-списки, только фильтр — по метке, а не по дате.

Заодно — **пиктограммный пикер рынка**: рынок задачи (`country`) выставляется тапом по флагу, либо «Global» (пусто). Тот же визуальный компонент, что и пикер меток. Модель данных рынка не меняется (одно значение).

**Кто пользуется.** Каждый сотрудник — для своих личных задач. Метки строго персональные: их видит и заводит только владелец.

## 2. Поверхности продукта

У Swarm Brain три поверхности (никакого «мини-аппа» — это легаси-имя каталога `miniapp/`):

| Поверхность | Технология | Роль в этой фиче |
|---|---|---|
| **Веб-интерфейс** | React в `miniapp/`, `swarm-brain.pages.dev` (Cloudflare Pages) | Полный UI: рельс списков, создание/правка меток, пикеры |
| **MCP** | `swarm-mcp/` (Claude Desktop / коннектор) | Тулзы: список меток, проставление меток по имени, фильтр задач по метке |
| **Telegram-бот** | `swarm-bot/` | **Вне охвата этой итерации** (отложено) |

## 3. Охват (scope)

**В охвате:**
- Персональные метки на **личных задачах** (`is_private = true`, `owner_id = я`).
- Модель ярлыков: одна задача может нести **несколько** меток.
- Веб-UI: рельс «Мои списки», CRUD меток, `PictogramPicker` для меток и для рынка.
- MCP: `list_task_labels`, `labels` в `add_task`/`update_task`, `label` в `get_tasks`.
- Общий движок задач (`_shared/tasks`) — единый DRY-чокпоинт для web-API и MCP.

**Вне охвата (осознанно отложено):**
- Метки на **командных/общих** задачах (владелец решил вернуться позже).
- **Общие** списки на весь воркспейс (схема зарезервирована под них, но не реализуется).
- Поддержка меток в **Telegram-боте**.
- Мультивыбор рынка (рынок остаётся одним значением или «Global»).

## 4. Модель данных

Метки вешаются только на личные задачи — их и так видит лишь владелец, поэтому членство хранится прямо на задаче массивом, без join-таблицы. Определения меток персональные и грузятся под пользователя, поэтому даже если чужой клиент получит `label_ids` задачи, он не сможет их отрисовать (нет доступа к именам/иконкам чужих меток) — утечка невозможна by design.

```sql
-- Персональные метки: имя + пиктограмма. owner_id NOT NULL = всегда чьи-то личные.
-- group_id зарезервирован под будущие общие списки (там owner_id станет nullable).
create table public.task_labels (
  id         uuid primary key default gen_random_uuid(),
  group_id   text references public.workspaces(id),
  owner_id   bigint not null references public.allowed_users(telegram_id),
  name       text not null,
  icon       text not null default 'tag',   -- имя иконки из набора RoyIcon
  color      text,                          -- токен акцента (опц.)
  sort_order integer not null default 0,
  created_at timestamptz not null default now()
);
create index idx_task_labels_owner on public.task_labels(owner_id);

-- Членство «задача ↔ метки» массивом прямо на задаче.
alter table public.tasks add column label_ids uuid[] not null default '{}';
create index idx_tasks_label_ids on public.tasks using gin (label_ids);
```

Обе операции безопасны по жёстким правилам БД проекта: `CREATE TABLE` и `ADD COLUMN` с дефолтом, без переименований/дропов. Кладутся в `supabase/migrations/` и в `supabase/schema/00_base_schema.sql` (чтобы проект поднимался с нуля).

## 5. Общий движок задач (`_shared/tasks`) — DRY-чокпоинт

Единственное место логики, которое переиспользуют и web-API, и MCP.

- **`types.ts`** — `Task` и `TaskInput` получают `label_ids: string[]` (в `TaskInput` — опционально).
- **`db.ts`**:
  - `createTask` — вставляет `label_ids` (дефолт `[]`).
  - `updateTask` — уже принимает `Partial<TaskInput>`, `label_ids` пройдёт как есть.
  - `listTasks` — новый фильтр `labelIds?: string[]` → `q.overlaps("label_ids", filters.labelIds)` (рядом с существующим `tags`).

## 6. Web-API (`swarm-api`)

Новые эндпоинты по образцу существующих `/tasks`, `/sprints/:id/tasks`. Все — под аутентифицированным `telegram_id`; доступ только к своим меткам (`owner_id = telegram_id`), проверка в коде (RLS не работает — `SERVICE_ROLE_KEY`).

| Метод | Путь | Тело / ответ | Доступ |
|---|---|---|---|
| `GET` | `/task-labels` | → `[{id, name, icon, color, sort_order, count}]` (count = число личных задач с меткой) | владелец |
| `POST` | `/task-labels` | `{name, icon?, color?}` → созданная метка | владелец |
| `PATCH` | `/task-labels/:id` | `{name?, icon?, color?, sort_order?}` → обновлённая | только владелец метки (иначе 403) |
| `DELETE` | `/task-labels/:id` | 204; **вычищает** этот id из `tasks.label_ids` владельца (`array_remove`) | только владелец (иначе 403) |

Проставление меток на задачу — через **существующий** `PATCH /tasks/:id`, который начнёт принимать `label_ids: string[]`. Правило: сервер принимает `label_ids` только если задача личная и принадлежит вызывающему (`is_private && owner_id === telegram_id`); иначе — **400** с понятным сообщением («метки доступны только на личных задачах»). Дополнительно валидируем, что все переданные id принадлежат меткам вызывающего (иначе 400). `GET /tasks` и `GET /tasks/:id` начинают отдавать `label_ids`.

## 7. MCP (`swarm-mcp`)

Метки — по **имени** (как `assignee_name`); MCP-слой резолвит имя → id личной метки владельца (`requesting_user_id`).

- **`list_task_labels`** — новый тул: `{requesting_user_id}` → список меток пользователя (имя, id, count). Чтобы Claude знал, что уже есть.
- **`add_task` / `update_task`** — новый параметр `labels?: string[]` (имена). MCP резолвит в личные метки владельца, **недостающие авто-создаёт** (иконка `tag` по умолчанию, цвет пустой — переопределяется в вебе). Проставление метки означает личную задачу: MCP выставляет `is_private = true`, `owner_id = requesting_user_id`.
- **`get_tasks`** — новый фильтр `label?: string` (имя метки) → резолв в id → `listTasks({ labelIds: [id] })`.

Рынок в MCP уже поддержан (`country` в тулзах) — доп. работы нет.

## 8. Веб-UI (`miniapp/`)

1. **Рельс списков** ([SmartListNav.tsx](../../../miniapp/src/components/tasks/SmartListNav.tsx)) — под смарт-списками добавляется секция **«Мои списки»**: каждая метка = строка `пиктограмма + имя + счётчик`; в конце «＋ Новый список». Клик по метке → активный фильтр по ней.
2. **Активный фильтр** — расширяем `useReminderTasks` и `smartLists.ts`: активной может быть либо `SmartListId`, либо метка (`{ labelId }`). Фильтрация задач по `label_ids.includes(labelId)`; счётчики меток считаются рядом с `countLists`.
3. **`PictogramPicker`** — новый переиспользуемый компонент (ряд иконок, тап = вкл/выкл), по образцу [QuickPickPopover.tsx](../../../miniapp/src/components/tasks/QuickPickPopover.tsx):
   - **метки** — мультивыбор; в [TaskQuickActions.tsx](../../../miniapp/src/components/tasks/TaskQuickActions.tsx) (строка задачи) и в карточке [TaskModal.tsx](../../../miniapp/src/components/TaskModal.tsx). Доступен только на личных задачах владельца.
   - **рынок** — одиночный выбор флагов, «Global» = пусто. Заменяет текущий country-QuickPickPopover. `country` не меняем — только UX. Флаг из ISO-кода (эмодзи), фолбэк — текст кода.
4. **Управление метками** — лёгкая форма создания/правки (имя + выбор иконки из набора RoyIcon + цвет), вызывается из «＋ Новый список» и из строки метки (переименовать/иконка/удалить). API-клиент `lib/api.ts` получает `fetchTaskLabels/createTaskLabel/updateTaskLabel/deleteTaskLabel`.

## 9. Контроль доступа и приватность

- Метки строго персональны: любой запрос к `task_labels` фильтруется `owner_id = telegram_id` (web) / `= requesting_user_id` (MCP). Правка/удаление чужой метки → 403.
- `label_ids` принимаются на задаче только для личных задач вызывающего.
- Приватность by design: чужие `label_ids` неразрешимы без доступа к чужим определениям меток (см. §4), поэтому даже случайная утечка массива ничего не раскрывает.
- Cron-триггеры и деструктив меток не касаются.

## 10. Крайние случаи

- **Удаление метки** — задачи целы, id метки вычищается из их `label_ids` (`array_remove`) для владельца.
- **Задача перестала быть личной** (`is_private → false`) — `label_ids` физически остаются, но не отрисуются ни у кого, кроме бывшего владельца (нет доступа к определениям). Безопасно; отдельной чистки не требуем.
- **Дубли имён** — у одного владельца допускаем (метки различаются по id); при авто-создании в MCP сначала ищем точное совпадение имени (case-insensitive), создаём только если нет.
- **Пустой набор меток** — секция «Мои списки» показывает только «＋ Новый список».
- **Легаси-`country` вне списка рынков воркспейса** — пикер рынка добавляет текущее значение в опции, как уже делает QuickPickPopover, чтобы выбор не «терялся».

## 11. Тестирование (соответствие правилу №2 проекта)

- **Общий движок** — `deno check` затронутых функций; юнит на `listTasks({ labelIds })` (overlaps).
- **Web-API** — смоук реального флоу: `POST /task-labels` → `PATCH /tasks/:id {label_ids}` → `GET /tasks` (метка на месте) → `DELETE /task-labels/:id` (id вычищен). Проверить 403 на чужой метке.
- **MCP** — `deno check`; проверить резолв имени и авто-создание, `get_tasks label=…`.
- **Веб** — `npm run build` в `miniapp/`; проверить рельс, пикеры и фильтр в браузере, в светлой и тёмной теме (веб-интерфейс, не «в Telegram»).
