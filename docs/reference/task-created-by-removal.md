# Подготовка удаления tasks.created_by (#238)

Статус: DDL подготовлен; применения на production эта правка не подтверждает. Issue #238 остаётся открытым до применения владельцем. Настоящий автор — `tasks.created_by_telegram_id`; его тип, значения и использование не меняются. Другие одноимённые `created_by` (например, автор спринта) сохраняются.

## Предусловия и транзакция

Порядок задан [владельцем 09.11.2026](https://github.com/GarroV/Swarm-brain/issues/238#issuecomment-6746701529): убрать чтение/запись из кода, выложить код, проверить константность и отдельной миграцией удалить колонку. Первый шаг — `a6b7c1b2` (PR #1256, merge `c4352acd`); его содержит deployed head `d67bc0e65a2482e3d7eedd069a7de158eb69cdc6`, [официальный успешный workflow 43644249401](https://github.com/GarroV/Swarm-brain/actions/runs/43644249401). Это подтверждение выкладки кода, а не выполнения нового DDL.

Файл [20261114235000_drop_unused_task_created_by.sql](../../supabase/migrations/20261114235000_drop_unused_task_created_by.sql) рассчитан на внешнюю транзакцию канонического [migrate-server.sh](../../scripts/migrate-server.sh). Внутренних `BEGIN`/`COMMIT` нет: проверка, DDL и запись версии шлюзом должны завершиться вместе. Применение требует отдельного разрешения владельца и действующего окна раскатки.

Миграция:

- Ограничивает ожидание блокировки 5 секундами, отдельную SQL-команду — 30 секундами (`SET LOCAL`, только внутри текущей транзакции).
- Допускает `read committed`/`read uncommitted`; при `repeatable read`/`serializable` отказывает с `25001`, не меняя изоляцию сессии.
- Берёт `ACCESS EXCLUSIVE` до чтения значений. После ожидания завершившийся писатель должен попасть в новую проверку; удерживаемая блокировка исключает запись между проверкой и удалением.
- Отказывает с `23514`, если хоть одно значение `IS DISTINCT FROM 'system'`, включая неожиданное `NULL`. Значения строк в ошибку не попадают.
- Проверяет автоматические зависимости точной колонки в `pg_depend` (индексы, локальные CHECK, расширенная статистика): отказ `2BP01`, кроме собственного literal default `system`. Один `RESTRICT` не защищает такие объекты от автоматического удаления. Canonical `NOT NULL` не меняется. Затем удаляет только `tasks.created_by` с `RESTRICT`, который блокирует внешние view/FK-зависимости. Повтор при уже отсутствующей колонке безопасен.

Основание проверки изоляции: [PostgreSQL LOCK](https://www.postgresql.org/docs/17/sql-lock.html) объясняет, что поздняя блокировка не обновляет уже установленный снимок `repeatable read`/`serializable`; [Transaction Isolation](https://www.postgresql.org/docs/17/transaction-iso.html) описывает новый снимок команды в `read committed` и эквивалентное поведение PostgreSQL `read uncommitted`. Миграция не меняет шлюз или его настройки. [ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html) описывает автоматическое удаление индексов и локальных ограничений при DROP COLUMN; [pg_depend](https://www.postgresql.org/docs/17/catalog-pg-depend.html) различает зависимости, удаляемые независимо от RESTRICT, и обычные внешние зависимости.

## Изолированная проверка

[created-by-removal.db.test.ts](../../supabase/functions/_shared/tasks/created-by-removal.db.test.ts) предназначен только для изолированной БД GitHub CI. Он выполняет точный SQL миграции внутри транзакций и восстанавливает собственные временные данные/схему. На Mac или общем стенде этот тест не запускается.

Проверяются константное и повторное удаление, сохранение остальных полей и настоящего автора, отказ на неконстантных/NULL значениях, зависимый view, обычный/выраженный индекс, CHECK, обычная/выраженная extended statistics и неподходящая изоляция. Два соединения воспроизводят писателя, который коммитит неконстантное значение, пока миграция ждёт блокировку. Негативные контроли исполняют реально испорченные варианты SQL: без константного guard, с CASCADE без ранней блокировки и без guard автоматических зависимостей. Они обязаны действительно выполнить опасное удаление в изоляции, после чего проверяемый контракт должен их отвергнуть; ошибка синтаксиса не засчитывается.

Совместимость проверяется текущими `createTask`/`listTasksWithTotal`/`createCycle`/`addItems`/`listItems` через изолированный PostgREST и текущим `demo_reset` в откатываемой транзакции. Две старые DB-фикстуры (`status-filter.db.test.ts`, `task-countries.db.test.ts`) больше не вставляют удаляемую колонку и её тестовый литерал. Их остальные входы, проверки и `created_by_telegram_id` сохранены; это совместимость тестовых данных, а не изменение стран или статусов.

Локальный `deno check` проверяет типы, но не заменяет actual CI/SQL. До зелёного изолированного прогона runtime миграции остаётся непроверенным. После разрешённого применения и проверки владельцем можно закрыть #238 и убрать отметку о legacy-колонке из архитектуры; подготовка PR сама по себе этого не делает.
