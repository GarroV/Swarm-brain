## Выполненная процедура

1. Получить зелёный CI PR, дождаться начала объявленной заморозки.
2. Повторно проверить запись/обработку и активность maintenance.
3. Накатить единственную новую миграцию через `deploy-migrations.yml` из ветки PR.
4. Влить PR с проверкой head SHA, запустить `deploy-functions.yml` из main:
   `dry_run=false`, `force=true`, `skip_activity_check=true` — активность до этого
   фактически проверяется напрямую на собственном сервере, поскольку legacy
   `deploy-activity.sh` в worktree привязан к отключённому облачному Supabase.
5. Дождаться production Pages именно на новом main, сверить хэши функций.
6. Проверить публичные OAuth endpoints, PKCE, MCP whoami, refresh/revoke и legacy
   static-token handshake. Временный доступ владельца выдаётся только для этого
   смоука через административный канал по его разрешению, без подделки веб-сессии
   или отметки второго шага. Клиент и доступ затем удаляются; бизнес-данные не пишутся.
7. Снять заморозку, проверить maintenance status и доступность интерфейса. Записать
   фактические версии/результаты ниже и закрыть задачу после успешного смоука.

## Подготовленный откат

Предыдущая production Pages deployment сохранена выше; штатный rollback API возвращает
её без пересборки. Проверенный read-only контроллер и подготовленный режим rollback —
`~/Documents/workbench/private/swarm-mcp-native-agent/cf-pages-control.py`.
Функции при выкладке шлюз автоматически сохраняет в `/var/backups/swarm-functions/`;
точное имя архива записывается после команды. При отказе вернуть этот архив и прежний
веб, проверить прежний MCP и API, затем снять заморозку. Аддитивную миграцию можно
оставить: прежний код не использует новые таблицы; уничтожать данные откатом не нужно.
